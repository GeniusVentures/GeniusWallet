## The token goes on `GeniusWalletColors` as an appearance-aware static getter, NOT on `GWColors`

`gw_colors.dart:67-73`'s `ponytail:` note explains the existing split: `statusSuccess`,
`statusError` and light-mode `textSecondary` live **only** on the `GWColors` extension because
their *source constants* on `GeniusWalletColors` must stay mode-invariant for ~56 already-written,
non-migrated consumers. That rationale is about **not breaking existing callers of an existing
constant**. It does not apply here: this is a brand-new token with zero existing consumers, so
there is nothing to preserve mode-invariantly.

Three reasons that make `GeniusWalletColors` not merely acceptable but **required**:

1. **`getThemeData()` has no `BuildContext`.** It is a plain top-level function, not a widget
   build. It physically cannot call `Theme.of(context).extension<GWColors>()` — that is the very
   thing it is constructing. Six of this task's eight consumers are inside `getThemeData()`. A
   `GWColors`-only token would be unusable for them. This alone settles it.
2. **The static getter resolves correctly because `getThemeData()` re-runs per toggle.**
   `main.dart:322-330` wraps `MaterialApp` in `ValueListenableBuilder<GWAppearanceMode>` and calls
   `theme: getThemeData()` inside the builder, so `GWAppearance.isLight` is re-read on every
   appearance change and the resulting `ThemeData` is a fresh `InheritedWidget`. This is the same
   mechanism `btnFilter` (`genius_wallet_colors.dart:30-31`) already relies on for its single
   `theme.dart:258` consumer — an exact precedent for this shape.
3. **The const-rebuild bug `GWColors` exists to solve does not apply.** That bug is about `const`
   *widgets* reading static getters directly and never rebuilding. Here the values are baked into
   `ThemeData`, which IS an `InheritedWidget`, so const widgets do rebuild. The one non-theme
   consumer, `gw_button.dart`, already reads `Theme.of(context).extension<GWColors>()` at `:184`
   **before** calling `_palette(gw)` at `:185` — the dependency is registered regardless, so the
   added static read inside `_palette` inherits that rebuild guarantee.

**Deliberately NOT mirrored onto `GWColors`.** Doing so costs a field + constructor arg + `copyWith`
arg + two factory entries + two assert clauses for zero consumer today. Per AGENTS.md ("no
abstractions that weren't explicitly requested"), it is added when a `const` widget outside a theme
first needs it, not before.

</token_placement_decision>

## Every `theme.dart` change, with what it can break

`theme.dart` is shared by every screen. The recorded trap (quick `260721-ed9`) is that editing a
shared theme's **shape** — `textButtonTheme`'s padding/size — silently regresses every bare
consumer. **Nothing in this plan changes a theme shape.** Every edit repoints one already-brand-
coloured `Color` property to a different `Color`, or drops a `const` qualifier. No padding, size,
shape, radius, border width, density or typography value is touched.

| Line | Change | Blast radius | Risk |
|---|---|---|---|
| `:75` | `progressIndicatorTheme.color` `brandPrimary` → token | **Every** `CircularProgressIndicator`/`LinearProgressIndicator` app-wide with no inline colour | Visible dark change `#14C8FF`→`#0AAEE6`. Deliberate; matches `0ze`'s sweep. **Called out.** |
| `:84` | `tabBarTheme.indicatorColor` `brandPrimaryStrong` → token | Every `TabBar` indicator app-wide | Dark byte-identical. Light-only fix. |
| `:103` | `datePickerTheme.headerForegroundColor` `textPrimary` → `textOnBrand` | DatePicker header label only | Both modes improve. |

Changing them would invert them. |
| `:227` | `inputDecorationTheme.focusedBorder` side → token | **Every `TextField`/`TextFormField` app-wide** — the widest blast radius here | Dark byte-identical. **`const` drops (`:74`, `:221`, `:299`, `:350`):** a static getter is not a compile-time constant,

appearance toggle, so none of this was ever canonicalised across rebuilds anyway. If the executor
finds a `const` it cannot drop without cascading, **stop and report** rather than restructuring.
