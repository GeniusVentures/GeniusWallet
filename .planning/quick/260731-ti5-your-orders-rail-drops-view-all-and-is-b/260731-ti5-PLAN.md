The planner ran a throwaway probe (`flutter test`, deleted afterwards) rather
than reasoning about the `IntrinsicHeight` trap. **Both halves of the trap are
real, and both are neutralised by the same 8-line wrapper.** Quote these numbers
in the SUMMARY as the reason this approach was chosen.

**PROBE 1 - does the real form card survive an intrinsic-height query?**
Pumped the real `BanxaBuyScreen` offline at a 1400x1400 surface, then asked the
form card's own `RenderBox`:

```
PROBE1 form card laid-out size = Size(680.0, 820.0)
PROBE1 getMaxIntrinsicHeight(680.0) = 820.0
PROBE1 DELTA = 0.0
```

It does not throw, and the intrinsic answer is EXACTLY the laid-out height. So
the form card is intrinsic-honest and a derived tight height will not overflow
it. (A non-zero DELTA would have been the "it computed but wrongly" failure and
would have forced the hand-written render box instead.)

**PROBE 2 - does the whole shape work, inside a SingleChildScrollView?**
`IntrinsicHeight` + `Row(crossAxisAlignment: stretch)` + `Expanded(form)` +
`Expanded(zeroIntrinsicWrapper(Column(header, Expanded(ListView of 40))))`:

```
PROBE2 exception = null
PROBE2 left  = Rect.fromLTRB(0.0, 0.0, 496.0, 360.0)
PROBE2 right = Rect.fromLTRB(504.0, 0.0, 1000.0, 360.0)
PROBE2 row 0 present = 1
PROBE2 row 39 present (before scroll) = 0
PROBE2 row 39 present (after scroll) = 1
```

Right height == left height == 360 (the LEFT column's own content height, with
40 rows on the right). No exception. The last row is reachable only after
scrolling, which is exactly the assertion this plan requires.

**Why this and not a third hand-written RenderBox.** `swap_seam.dart` solves a
different problem (a control centred on the seam between two cards) and has no
generalisable "child B takes child A's height" surface to reuse - its
`performLayout` is three-children-specific and its own comment forbids putting
it under `IntrinsicHeight`. `_FillHeight` at `token_info_screen.dart:1568` IS
this exact idea, and the probe proves the idea holds here. It stays PRIVATE in
each file rather than being promoted: two occurrences do not justify a shared
component (`AGENTS.md`, Rule of Three), and this one differs in intent enough
that a shared name would have to serve both. Writing a third render object with
a hand-rolled layout algorithm would be more code than a proven 8-line proxy for
no gained property.
