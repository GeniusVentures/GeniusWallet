## Why candidate 2, and why not 1 or 3

**Candidate 1 (give the slot more height) — REJECTED.** The 173px slot is not produced by any
constant this task could safely raise. It is the residue of the dashboard's own `Expanded` split
after `GWSectionTitle`'s shared 44px min header (quick `260721-baz`, which deliberately pinned ONE
geometry across all four panels) and the count footer. The only sources of extra height are the
shared header — desynchronising four approved panels — or the sibling dashboard panels. And it
does not generalise: the deficit varies with window size, so any fixed grant is a fudge that
re-opens at the next window height. It also leaves `GWEmptyState` still unable to survive a tight
slot anywhere else.

**Candidate 3 (clip / scroll) — REJECTED.** It hides a user-visible truncation on the
fresh-install screen and is not a fix. Not needed, because 2 works.

**Candidate 2 (adaptive) — CHOSEN.** It is the only option that satisfies the hard constraint
structurally rather than by luck: the compact branch is gated on `constraints.maxHeight`, so a
call site with room takes a code path that is literally the current one. Combined with the derived
276px floor on the Assets slot, "call site 2 is unchanged" becomes an argument from constraints,
not a hope. It also matches a pattern already walked and approved in this codebase.

**A fourth option was considered and rejected:** drop the `message:` at the transactions call site
(160px needed vs 173px available — it would fit). It loses user-facing information, does not
survive a narrower panel where the title itself wraps, and leaves the shared widget just as
fragile. Not taken.

## The compact layout, and the arithmetic that proves it fits

Compact metrics (every gap comes from an EXISTING token; nothing new):

```
  24  padding    space6 x2      (was 48 — space12 x2)
+ 48  icon circle               (was 72; glyph 24, was 32)
+  8  space4                    (was 16 — space8)
+ 24  title      (titleLg)
+  4  space2                    (was 8 — space4)
+ 24  message    (bodyMd, 1 line)
= 132   → 41px headroom in the observed 173px slot
```

Worst case, message bounded at `maxLines: 2`: `132 + 24 = 156` → **17px headroom at 173px**.

The `maxLines` bound is what makes this provable: it makes the compact height **independent of
width**, so it cannot be re-opened by a narrower panel the way a fixed-pixel fudge would. In
practice it never ellipsises — compact padding is 24px narrower than full, so the message has MORE
room than the 385px width at which it already fit on one line.

Threshold = **192**, which is exactly the full layout's own minimum. So compact engages precisely
when full cannot fit, and never one pixel sooner.
