# Quick Task 260731-jh9: A dev button that reaches `ComputeState.ready`

## The problem

Jakub cannot reach `ComputeState.ready` from the dev panel, so he cannot click `New processing
job` and cannot walk the job flow at all. `resolveComputeState` (`compute_state.dart:154-156`)
returns `startingUp` whenever `initPercentage != null && initPercentage < 1.0`, checked ABOVE
`ready`. `_onInitializationStatusTicked` polls the real FFI every 3s with no override armed, and
on Jakub's machine that real percentage sits around 0.52 - below 1.0 - so `SGNUS idle` (which
only arms `processing: false`) gets clobbered back to `startingUp` within 3 seconds. `SGNUS init`
arms `startingUp` by design. Neither button was ever a route to `ready`.

This is a regression from quick task 260731-hrn, which correctly fixed `armInitPercentage(37)` to
`armInitPercentage(0.37)` - `37.0 < 1.0` used to read `false`, so before that fix the panel fell
through to `ready` by accident. Fixing the fixture removed Jakub's only (buggy) route. This task
restores the route deliberately.

## What to build

A new dev button, `SGNUS ready`, that lands the compute panel in `ComputeState.ready` and HOLDS
it there against the 3s init poll, against any previously-armed `Job done`/`Feed dead` fixture,
and against a `processingCompletedAt` timestamp left over from an earlier `Job done` press.

### Every rung above `ready`, and how this button satisfies or clears it

`resolveComputeState` precedence: `noWallet` -> `disconnected` -> `notLinked` -> `unavailable` ->
`startingUp` -> `processing` -> `jobComplete` -> `ready`.

1. `hasSelectedWallet` - satisfied by `injectMockWallet(DevMockSgnus.instance.wallet)`.
2. `isNodeConnected` - satisfied by `updateConnection(DevMockSgnus.instance.connection)`
   (`isConnected: true`).
3. `nodeWalletAddress == selectedWalletAddress` - both already equal `DevMockSgnus.address` on
   the existing fixture wallet/connection; unchanged.
4. `isProcessingUnavailable` - cleared via `clearFeedUnavailable()`, in case `Feed dead` was
   pressed earlier in the session.
5. `initPercentage >= 1.0` - satisfied by `armInitPercentage(1.0)`: `1.0 < 1.0` is `false`, and
   because `_onInitializationStatusTicked`'s dev guard (added earlier today) returns the armed
   override and never reaches the real FFI read while armed, the 3s poll cannot claw this back.
6. `isProcessing` false - satisfied by `arm(processing: false)`.
7. No recent job completion inside `jobCompleteWindow` (60s) - cleared via `clearJobComplete()`
   (releases the `jobCompleteOverride` sticky flag), AND a new one-shot flag forces
   `AppState.processingCompletedAt` far enough into the past (`DateTime.now().subtract(jobCompleteWindow
   * 2)`) on the very next tick. This second part is required because `copyWith` cannot null
   `processingCompletedAt` (documented on the field itself) - if `Job done` was pressed within the
   last 60 seconds, the timestamp it wrote would otherwise survive untouched and mask `ready` behind
   `jobComplete` for up to a minute, even with every other rung satisfied.

### Implementation shape (mirrors `SGNUS idle`, `dev_tools_bubble.dart:444-475`)

New button, same four-step order (load-bearing: arm before dispatching the tick):
1. `DevMockSgnus.instance.armReady()` - a new method on `DevMockSgnus` that calls
   `arm(processing: false)`, `armInitPercentage(1.0)`, `clearFeedUnavailable()`,
   `clearJobComplete()`, and sets the new one-shot stale-completion flag.
2. `context.read<GeniusApi>().getSGNUSController().updateConnection(DevMockSgnus.instance.connection)`
3. `context.read<WalletDetailsCubit>().injectMockWallet(DevMockSgnus.instance.wallet)`
4. `context.read<AppBloc>().add(ProcessingStatusTicked())`
5. Toast stating plainly this is STICKY and released by `Clear`, matching the JOB section's
   toast wording style.

### `DevMockSgnus` additions (`lib/dev/dev_mock_sgnus.dart`)

- `void armReady()` - arms every override above.
- `bool _staleCompletionPending` + `bool get staleCompletionPending` (read-only, for tests) +
  `bool consumeStaleCompletion()` - one-shot, same idiom as `consumeInitRelease()`.
- A short comment at the fixture's definition site recording WHY a dedicated `ready` fixture
  exists: `ready` is the only state whose CTA (`New processing job`) is clickable, so it is the
  gateway to the entire job flow, and it was previously reachable only through the
  37-vs-0.37 bug this task's own history section documents.

### `AppBloc` changes (`lib/bloc/app_bloc.dart`, `_onProcessingStatusTicked`'s dev branch)

- Consume the new flag at the top, alongside the existing `releasedInit`:
  `final staleCompletion = mock.consumeStaleCompletion();`
- Add `mock.staleCompletionPending` to the branch's entry guard (defensive, mirrors why
  `initReleasePending` is in that guard).
- In the general (final) emit, add
  `processingCompletedAt: staleCompletion ? DateTime.now().subtract(jobCompleteWindow * 2) : null`.
  `jobCompleteWindow` is already importable - `compute_state.dart` is already imported in this
  file.

### `dev_tools_bubble.dart` - the new button

- Label: `SGNUS ready` - distinct from `SGNUS idle` (which only guarantees `isProcessing: false`,
  not `ready`) and `SGNUS init` (which forces `startingUp`).
- Tooltip explains the distinction: unlike `SGNUS idle`, this also forces `initPercentage: 1.0`
  and clears any stale job-completion timestamp, guaranteeing `ComputeState.ready` and an
  enabled `New processing job` CTA.
- Toast: states plainly this is STICKY, released by `Clear`.
- `Clear` button: no changes needed. `armReady()` only touches overrides `Clear` already
  releases (`clear()`, `clearInitPercentage()`, `clearFeedUnavailable()`, `clearJobComplete()`).
  The one-shot stale-completion flag self-consumes on the tick the button itself dispatches, so
  it never outlives the button press.
- Everything stays behind `kDebugMode && kShowDevTools` (unchanged - this is added inside the
  existing MOCK section, already gated at the panel's single mount point).
