## The row is 40px, not the 34px the sketch drew - so the track fits with slack

The brief inherited "the balance row is currently 34px" from the sketch. That is the
sketch's scale, not the app's, and re-deriving it is this repo's standing rule
(`compute_panel_height_test.dart`'s own header: "re-derive every inherited number
rather than quote it").

**Balance row today** (`compute_panel.dart:253-292`):

| Part | Value | Source |
|------|-------|--------|
| `GWAnimatedNumber` line box | `numericDisplay` fontSize 32, height 40/32 = **40px** | `genius_wallet_typography.dart:128-134` |
| `_UnitToggle` | `max(24 min-height, labelMd's 18px line box)` = **24px** | `compute_panel.dart:351` |
| Row height | `max(40, 24)` = **40px** | `Row` default |

The sketch's `.balrow{min-height:34px}` with a 28px `.num` is a different scale. The app
has **40px**, which is 6px more headroom than the brief assumed.

**The track, at the app's own chip geometry** (`_TimeframeTab`,
`gw_timeframe_segment.dart:126-129`: `Text` fontSize 12 / `height: 1`, padding
`symmetric(horizontal: space4, vertical: space3)`):

    chip   = 12 (line box) + 2 x 6 (space3)  = 24px
    track  = 24 + 2 x 3 (EdgeInsets.all(3))  = 30px
           + 2 x 1 (borderSubtle hairline)   = 32px

**32px inside a 40px row. Zero height growth, 8px of slack.** The brief's "32px (26px
chip + 3px padding + 1px border)" arrives at the same total by a different route - the
sketch's 26px chip at 11px type would give 34px, still under 40, so the conclusion holds
either way. **Build at 12px/`space3`, matching `_TimeframeTab` exactly**, because
conformance with the app's existing tracks is the entire argument for scheme B.

**This is not asserted, it is measured.** `test/dashboard/compute_panel_height_test.dart`
already pumps every one of the 8 `ComputeState` values at both units and both widths
against a budget derived from `kDashboardPanelSlotHeight` - it will fail on the next run
if the track costs height. Task 2 adds the sharper statement it cannot make today: that
the numeral, not the track, is still the tallest thing in the row.

## Width, and the one honest cost

Inter 12px w600, uppercase, plus 2 x `space4` chip padding:

| Piece | Estimate |
|-------|----------|
| `GNUS` chip | ~49px |
| `MIN` chip | ~39px |
| Track total (2 border + 6 padding + 49 + 2 gap + 39) | **~98px** |
| Track if the segment read `MINIONS` (~67px chip) | **~126px** - the sketch's ~132px warning, confirmed at app scale |
| Today's `_UnitToggle`, `GNUS` (labelMd 13px + 2 x space2) | ~44px |
| Today's `_UnitToggle`, `MINIONS` | ~63px |

Available width for the balance row, using the height test's own border-fold arithmetic
(`GWCard` combines `padding` with `decoration.padding`, so the inset is `12 + 1` per
side, twice, on top of `DashboardScrollContainer`'s own `13 x 2`):

| Panel width | Tile inner | Number gets, today (MINIONS) | Number gets, new |
|-------------|-----------|------------------------------|------------------|
| 320 (`_kRealisticPanelWidth`) | ~268px | ~201px | **~162px** |
| 290 (`_kNarrowPanelWidth`, a deliberate stress case below production reach) | ~238px | ~171px | **~132px** |

**So the number loses roughly 39px of allotment - about two tabular digits at 32px.**
That is the real cost of scheme B and it is stated, not hidden. Three things about it:

1. **It is not new behaviour.** The row already clips rather than overflows: the
   `SingleChildScrollView` + `NeverScrollableScrollPhysics` at `:256-288` hands the
   number unbounded width and hard-clips the excess, deliberately, and its long comment
   explains why. A large minions balance was already clipped at 290px today.
2. **`GWAnimatedNumber` uses `NumberFormat.decimalPatternDigits`
   (`gw_animated_number.dart:53`), so the rendered string carries thousands
   separators** - the minions case is wider than raw digit count suggests. Task 2 reads
   the string the widget actually renders rather than assuming a format.
3. **If the measurement shows a plausible minions balance clipping at the realistic
   320px width, that is a finding for Jakub, not a licence to shrink the chips.**
   Narrowing the chip padding below `space4` breaks conformance with the other three
   tracks, which is the one thing this task exists to avoid; and the sketch already
   names the fallback if B cannot fit - scheme A, the swap glyph, its own runner-up.
   Report it, do not silently reduce it.

## The gap: `space2` (4) becomes `space4` (8)

Jakub's requirement, in his words: "z zachowaniem odstepu od kwoty, od balansu."

4px was right for a bare run of text beside a numeral. Against a bordered hairline it is
not: the eye measures to the drawn line, not to the chip's text, so 4px reads as the pill
touching the number.

**Chosen: `GeniusWalletConsts.space4` = 8px.** Justification, from the existing scale:

- It is the smallest step that reads as deliberate separation rather than a hairline
  grazing a 32px numeral, and it doubles what is there now.
- **It equals the track's own internal chip padding** (`space4` horizontal). The air
  outside the control then equals the air inside it, so the track reads as one balanced
  object beside the number rather than a pill glued to it. That is a reason from the
  drawing's own geometry, not a copied value - the sketch's 4px is at 28px type and a
  26px chip, a different scale, so it was re-derived rather than reused.
- It is on the 4-pt grid.

**Rejected: `space6` (12).** Optically the better choice against 32px type, and it is
what jx5 uses between a track and a link on a kicker row - but that row has slack and
this one does not. 12px costs another 4px against a number allotment already losing 39px
(above). This is the one place in the panel where horizontal width is genuinely scarce,
so the optical ideal loses to the measured constraint.

**Rejected: `space3` (6).** The grid's one deliberate exception, and only 2px above
today's value - too small a move to read as the change Jakub asked for.

## The fill step the sketch drew does not exist here, and that is deliberate

The sketch drew its tile as `--surface-menu` (`#171A21`, `index.html:45`). **The real
`_ComputeCardTile` is `gw.surfaceSunken`** (`compute_panel.dart:186`) - the same token
`GWControlTrack` uses for its own fill. So on this tile the track has **no fill step at
all**; it is delimited by its `borderSubtle` hairline alone, and the selected segment's
`surfaceMenu` is the only raised plane.

**Do not "fix" this by giving the track a different fill.** The recipe is fixed
(`CONVENTIONS.md`: "partial adoption reads as a different design language on the same
screen"), and CONVENTIONS.md itself already says the fill step is not what makes the
control visible - the hairline is. The selected state is carried by the chip's text
colour going `textSecondary` -> `textPrimary`, which is a large perceptual step in both
themes, plus `Semantics(selected:)` for AT.

If Jakub judges it too flat in the walk, the fix is one token in `gw_control_track.dart`
and it moves all four tracks together - which is exactly the benefit the extraction
bought. Raise it in the walk; do not pre-empt it here.

## The second segment reads `MIN`, not `MINIONS`

Jakub approved B as drawn, and B is drawn with `MIN` (`index.html:212`). Recorded here as
an assumption so reversing it is a one-line change (`_kMinionsLabel` in
`compute_panel.dart`).

The reasoning, and it is stronger than the sketch's:

1. **The sketch's own cost note:** `MINIONS` pushes the track to ~132px and squeezes long
   balances. Re-derived at app scale above: ~126px versus ~98px. On the 290px stress
   width that is the difference between ~132px and ~104px of number - about a digit and a
   half more lost.
2. **The app already ships this abbreviation.** `lib/wallets/view/genius_balance_display.dart:89`
   renders `widget.useMinions ? "min" : "gnus"` as the balance suffix, and has for as
   long as that widget has existed. `MIN` is therefore not a new coinage invented to fit
   a pixel budget - it is the existing short form, brought into the new control.
3. **The abbreviation costs AT users nothing.** The segment's accessible name is the full
   word `Minions` (see the semantics decision below), so a screen reader never hears the
   truncation.

**If Jakub rejects `MIN`:** the sketch's own recommendation says B becomes unbuildable at
this width and **scheme A (the swap glyph) is the right answer instead** - that is a
different plan, not a widening of this one.

<the_three_properties_that_must_not_regress>

Sketch 170's README states the finding plainly: the gap was **purely visual, and only for
sighted pointer/touch users**. All three carry forward, and two of them get better.

**1. 24x24 minimum target (WCAG 2.5.8 AA).** The 12px/`space3` chip is exactly 24px tall
and both labels are wider than 24px, so the constraint is met by construction - but "met
by construction" is how it was got wrong once before (the doc comment at `:326-330`
records the plan arithmetic correcting itself to "+8px, not 0"). Keep an explicit
`BoxConstraints(minWidth: 24, minHeight: 24)` on each segment so the guarantee survives a
future type-scale change instead of emerging from font metrics. Task 2 asserts it on the
rendered box.

**2. Semantics: two buttons with `selected`, not one button with `value`.** This is a
change, and it is the more correct shape.

Today's `Semantics(button: true, label: 'Balance unit', value: 'GNUS')` announces
"Balance unit, GNUS, button" - it describes the current state and **hides that a second
option exists and that it is called Minions**. Scheme B's whole argument is that it is
"the only scheme where you can learn that the other unit is called Minions without
pressing anything" (README). If the semantics stay single-node, that gain is delivered to
sighted users only, and the visual fix creates a new accessibility asymmetry in the very
control that had none.

So: a group node naming the control, with two explicit child nodes.

    Semantics(container: true, explicitChildNodes: true, label: 'Balance unit',
      child: GWControlTrack(children: [gnusSegment, minSegment]))

and each segment `Semantics(button: true, selected: <bool>, label: 'GNUS' | 'Minions')`.
`explicitChildNodes: true` is what stops the group label from merging the children away.
A screen reader then announces "GNUS, selected, button" and "Minions, not selected,
button" - exactly the information the sighted user now gets from the drawing.

This is also the app's established shape for a track chip: `_FilterChip`
(`transactions_slim_view.dart:785-788`) is `Semantics(label:, button: true, selected:)`,
and jx5's `_OrderToneChip` is the same. One shape, four controls.

**WCAG 2.5.3 Label in Name is satisfied by `Minions` for a visible `MIN`** - the success
criterion's match is case-insensitive substring, and "min" is contained in "Minions". The
full word as the accessible name is the correct call here, not a violation of it.

**3. `InkWell`, not `GestureDetector` - and this is where conformance is deliberately
NOT followed.**

`_TimeframeTab` (`gw_timeframe_segment.dart:118`) and `_FilterChip`
(`transactions_slim_view.dart:801`) both wrap a bare `GestureDetector`. **Neither is
keyboard-focusable.** Copying their input handling would trade a WCAG 2.1.1 Level A
property this control already has for a consistency it does not need: CONVENTIONS.md
fixes the track's *geometry*, and geometry is what conforms here. Input handling is
strictly better.

So each segment keeps `Material(type: MaterialType.transparency)` + `InkWell`, exactly as
`_UnitToggle` has today. Two details:

- `hoverColor: Colors.transparent` on the `InkWell`, because `GWHoverable` owns the hover
  paint (the design-system "lift chip") and two hover washes would double up.
- **Leave `focusColor` at its default.** That is the visible keyboard-focus indicator
  (WCAG 2.4.7). Do not null it out while suppressing the hover.

The gap this exposes in the other two tracks is real and is filed as Task 3, not fixed
here - those files belong to jx5 and were touched hours ago.

</the_three_properties_that_must_not_regress>

<the_state_shape_decision>

## `VoidCallback onToggleUnit` becomes `ValueChanged<bool> onUnitChanged`

The brief says prefer the smaller diff unless the larger one removes a real bug. **It
removes a real bug**, and the larger diff is three call sites.

A segmented control sets a value. Keeping `VoidCallback` forces every segment to guard
`onTap: selected ? null : onToggleUnit`, and that guard reads `useMinions` from the
last-built frame. Two taps on `MIN` inside one frame - a double-tap, a stuck touch, a
fast test pump - both see `selected == false` and both fire, so the control **flips to
Minions and back to GNUS**. A segmented control that returns to the other option when you
press the same target twice is wrong, and the callback's own name would be lying about
what the control does.

Value-based makes it structurally impossible: setting Minions twice leaves Minions.

**The diff, in full - there are only three call sites:**

- `compute_panel.dart`: `ComputePanel` and `_BalanceTile` take
  `ValueChanged<bool> onUnitChanged` instead of `VoidCallback onToggleUnit`; each segment
  calls `onUnitChanged(false)` / `onUnitChanged(true)` unconditionally.
- `wallet_overview.dart:91-93`: `_toggleUnit()` becomes
  `_setUnit(bool useMinions)` with an early return when the value is unchanged, so a
  redundant tap costs no rebuild.
- `test/dashboard/compute_panel_height_test.dart:142` and
  `test/theme/compute_contrast_test.dart:49`: `onToggleUnit: () {}` becomes
  `onUnitChanged: (_) {}`.

`bool` rather than a new enum: there are exactly two units, `_useMinions` is already a
`bool` and is the single source of truth (`wallet_overview.dart:42`), and inventing a
`BalanceUnit` enum for two values is the abstraction `./CLAUDE.md` says not to write.

`lib/components/wallets_overview.dart` (the plural, legacy file with its own
`ToggleButtons`) is a different widget and is **out of scope** - do not touch it.

</the_state_shape_decision>
