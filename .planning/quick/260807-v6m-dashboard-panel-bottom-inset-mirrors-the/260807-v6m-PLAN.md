<the_shape_and_why_it_survived_review>

The requested shape is what is built. Three things were checked against it and it held; a
fourth forced one addition. All four are recorded here so the executor does not rediscover
them mid-task.

**1. Why a fixed pad cannot work, in one table.** The measured trailing insets (see Task 1)
are 0, 4, 8, 13.25, 15.63 and 24. A constant 12 charged by the container would render 12,
16, 20, 25.25, 27.63 and 36 - the identical failure mode the top side had before
2026-08-06, when a fixed `space8` rendered 26 / 34 / 38 / 42.75 / 46. The parameter is not
ceremony; it is the only shape that produces one rendered number.

**2. The card's own padding cancels, so one gap serves both widths.** Rendered bottom =
cardPad + pad + contentBottomInset = cardPad + 12. Rendered top = cardPad + edgePad(2) +
slack(10) = cardPad + 12. The card pad differs by width (6+1 phone, 12+1 desktop) and it
appears on BOTH sides, so it cancels exactly the way the host inset cancels for R1. One
number, both widths, no breakpoint in the derivation.

**3. The gap is R1, stated in code.** `kDashboardPanelBottomGap = kGWSectionTitleBoxGap`
where the latter is `kGWSectionTitleEdgePad + kGWSectionTitleSlack`. If R1 ever moves, the
bottom follows it without an edit. A bare literal 12 would be a second copy of a frozen
number, which is how the top drifted in the first place.

**4. The addition the audit did not anticipate: two panels have MORE THAN ONE possible last
element, and a single static declaration is wrong for them.**

- Transactions ends in a `TransactionRow` (inset 4 phone / 8 desktop), an end-of-list label
  on the page (inset 4), or a `GWEmptyState` (inset 24). Declaring the row's 4 at the
  container would charge the empty branch 8 more on top of its 24, taking it from 31 to 39
  measured from the border - making the one branch the audit already flagged as too LOOSE
  visibly worse.
- Assets ends in a `CoinCardRow` (inset 15.63) or, when the wallet's total is zero, the
  Receive / Buy GNUS strip (inset 0). **That second shape is what Jakub's own wallet
  renders** - `coins_screen.dart:262` records his balances are all zero - and the audit did
  not list it.

So those two panels pay their own trailing gap where the branch is known, using the same
exported derivation, and declare it as already-paid at the container. For Transactions that
is `_body` in `transactions_slim_view.dart`, which is precisely where the TOP-side twin of
this decision already lives (`underSectionTitle ? 0 : space4` on the first day label). The
symmetry is the argument: the widget that knows which branch it took is the widget that
owns the gap on that branch.

**What this shape deliberately does NOT do.** The pad floors at zero, so a panel whose last
element already brings more than 12 keeps what it has: Assets rows render 15.63, Markets
rows 13.25, every empty and error state 24. That is the exact behaviour Jakub approved on
the top side, where `contentTopInset` above 16 overshoots to `slack + C` (Assets at 30,
Markets at 26.75). It also protects the case the audit flagged: an empty state with no
title above it is symmetric by construction, and a floored pad leaves it untouched.
