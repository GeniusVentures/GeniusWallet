Sketch 184 - the Menu page

S7 moves the menu out of the bottom bar and into a hamburger in the header. This is what the hamburger opens. Every row here was found in the code first - route, screen and call site - and anything that could not be found is not drawn. Every phone already shows its own variant - tap a row and the child screen is real, which is the whole argument about page versus sheet. The hamburger closes the menu and shows the dashboard behind it. Use the DEV TOOLS switch under each phone.

exists already in the codebase adapted existing component, new arrangement new nothing like it ships today
The menu has four rows. That is the finding.

The instruction was that the menu may contain only what exists, with logic behind it. So the contents were derived rather than designed. Start at _allDestinations (responsive_overlay.dart:41), subtract the S7 bottom bar - Home, Assets, Swap dock, Activity, News - and what is left is Markets, Web, Feedback, Settings. Four rows.

The overflow is derived, not written (_moreDestinations, responsive_overlay.dart:110). Nobody has to maintain this list. Take a destination onto the bar and it leaves the menu on its own.

Four things in the brief that the code does not have
Settings is not a preferences screen. SettingsScreen (lib/settings/settings_screen.dart) contains exactly three cards: Log Config (per-logger spdlog levels), Network Config (PubSub port, bind address, UPnP, high/low water) and CRDT Config (backup interval, keep count, auto-restore). It writes JSON overrides into the SDK directory. There is no appearance, no security, no currency, no language and no notifications setting anywhere in lib/. Those four section rows from the brief are deleted, not deferred.
There is no version and no About. pubspec.yaml says 1.0.0+1 and nothing in lib/ renders it - no PackageInfo, no showAboutDialog, no licence page. So the Support section is one row: Feedback.
Appearance is the one genuine grey area, and it is worth stating precisely. The logic is complete and persisted - GWAppearance is a ValueNotifier that writes to the Hive preferences box and re-skins the whole app live (gw_appearance.dart:40). Its only user-facing control is inside the dev-tools bubble (dev_tools_bubble.dart:1219). Its own doc comment says it is "toggled from the Preferences sheet (Appearance row)" - a sheet that does not exist. So the row is drawn only inside the DEVELOPER section, where its control really lives today. Promoting it to a user-facing row is a one-line decision this sketch is not authorised to take.
No wallet section, and no Accounts row. Sketch 181-F puts the wallet icon 12px from the hamburger. _MoreSheetBody ships an Accounts row today (responsive_overlay.dart:528); under F it must go, or two adjacent icons open the same drawer. Its absence is the design, and it is why the menu is four rows and not five.
Sections, renamed to fit what is there

The brief's Explore / Settings / Support / Developer does not survive the inventory: the Settings section would hold one row called Settings, which is a group header over its own child. What the four rows actually divide into:

SectionRowsWhy it is a group

Two of the four sections hold one row. That is not a drafting problem to tidy away, it is the shape of the app's current surface area, and variants B and C exist partly to show what one-row groups look like at 1:1. Variant A takes the other view and refuses to group four things at all.
News is deliberately absent. Under S7 it owns a tab. A tab and a menu row to the same route are two answers to "where does News live". The derived _moreDestinations removes it automatically, so this costs nothing to honour.
The rule this menu is held to
The menu holds what you do rarely or once. Anything you do often belongs on a tab or in the header. If a row here turns out to be reached constantly, that is a signal to promote it to the bar, not evidence that the menu is wrong.
Page or sheet, re-argued against a four-row menu

The brief gave three reasons for a full page. Measured against the real inventory, one is strong, one is neutral and one is weaker than claimed, and it would be dishonest to keep quoting all three at the same weight:

ArgumentHolds?Why
The menu has childrenholds, strongly/settings, /markets, /web, /logs are all full screens. A sheet that opens a screen loses the sheet's own dismiss gesture and stacks a push behind a modal. Tap Settings in tab E and watch what has to happen first.
A sheet has a height ceilingweak at four rowsGWBottomSheet passes isScrollControlled: true (gw_bottom_sheet.dart:14), so the ceiling is nearly the full screen. Four rows never reach it. Seven rows with DEV ON do at a 62% sheet - which is the only place this argument bites, and it bites in a build nobody ships.
A menu is a place you look around inweak at four rowsFour rows is a pick-one-and-return list, which is exactly what sheets are good at. This argument earns its keep only if the menu grows.
So the honest case for a page rests on the first row of that table plus a bet on growth - and E is drawn at 1:1 so the bet can be judged rather than asserted.
Conventions every variant respects
  • One GWPageHeader, at the top, and no GWSectionTitle under it. The duplicate-title defect Jakub flagged on Transactions is called out in assets_screen.dart:354. Sections are GWKicker, which is a label, not a header.
  • No fills, no gradient decoration. Nothing in this menu is a commitment, so nothing is filled. The dock stays the app's only gradient fill; the View all links were just reverted from gradient to flat grey (gw_view_all_link.dart), and a menu is the last place to reintroduce it.
  • The control track in the Appearance row is surfaceSunken + hairline + radiusPill + 3px pad, per CONVENTIONS.md.

C - kickers and hairlines, no boxes
C - the structure is typographic ★

No cards at all. GWKicker names each section, rows sit straight on surfaceBase, and a single borderSubtle hairline closes each group. The page is a list with headings, which is what it is.

Flip DEV TOOLS ON. The DEVELOPER group appears under its own kicker, below its own rule, and nothing else on the page moves or restyles. That is the same edit B needs a fourth card for.
Built from

  • exists the control track for the Appearance row - surfaceSunken + hairline + radiusPill + 3px, per CONVENTIONS.md
  • adapted a bare hairline as a group terminator. The app rules between rows (GWDetailGrid) but has not used a rule to end a group; sketch 065 drew exactly this as variant D and did not pick it, so this is a deliberate reopening, not an oversight
  • new nothing
It spends nothing on saying what the kicker already says. Given that surfaceElevated measures 1.01:1 against the page, a card here is a hairline pretending to be a container. C draws the hairline and skips the pretence.
A one-row section stops being embarrassing. A kicker over one row is a label; a bordered box over one row is a container with nothing in it. With two of four sections holding a single row, that difference is most of the page.
It is the only variant that scales in both directions. Rows can arrive under an existing kicker, a kicker can arrive with its rows, and nothing needs re-boxing.
Honest cost: the hairline that terminates each group measures 1.36:1 and cannot be relied on. It is decoration, and the kicker at 6.01:1 is what actually separates the sections. That is fine - the rule carries no information the label does not - but it does mean C's structure is entirely typographic, and typographic structure is the first thing to go wrong at large text sizes.
D - two-up tiles
D - four things, four tiles

Rows become tappable GWCards in a two-column grid, with hoverLift: true - the flag gw_card.dart already carries. The instinct is reasonable: four rows on an 844px page look thin, and a grid fills the top of the screen.

Hover a tile. That lift is the shipped GWCard hover, not a new effect. Then turn DEV ON and watch the grid go to seven, which is three and a half rows.
Built from
  • exists GWCard(onTap:, hoverLift: true)
  • adapted a tile layout - icon over label over sublabel - which no surface in this app renders today
  • new the grid itself, its column rule and its odd-count behaviour; and a second visual language for "a place you can go", competing with GWSelectRow, which every other list in the app uses
The one thing D genuinely buys: the page does not look empty. With four rows that is a real problem and D is the only variant that solves it rather than admitting it.
It solves it by making the menu look important. A grid of tiles is the visual weight of a dashboard, and this is the least-visited surface in the app. The governing rule says the menu holds what you do rarely; D dresses it as what you do first.
It also breaks grouping. Sections in a two-column grid need either full-width kicker rows between grid bands or no sections at all, and with 3 developer tiles the last row is odd. Two new components and a new visual language, to fix a whitespace problem that a page with four rows is allowed to have.

E - what ships today, minus one row

The control, not a strawman. GWBottomSheet.show with _MoreSheetBody: surfaceMenu #171A21, radiusXl top corners, a handle, four GWSelectRows. The only edit from the live app is the Accounts row leaving, per 181-F.

Built from
  • exists all of it - GWBottomSheet, _MoreSheetBody, GWSelectRow
  • new nothing. E is a deletion, not a build
At four rows E is defensible and it is the cheapest thing on this page. Two of the three arguments for a page are weak at this size, and pretending otherwise would be arguing backwards from a conclusion. If nothing is ever added to this menu, E is right.
What it cannot do is hold children. Every row here opens a full screen, and a sheet that opens a screen must destroy itself first. On iOS the sheet also owns the swipe-down gesture that the pushed screen then wants for back, which is the nesting the brief warned about.
DEV ON is where it breaks. Seven rows in a 62% sheet scroll internally - the exact behaviour phase 25 spent a phase removing from the dashboard. It only happens under GW_DEV_TOOLS today, so it is a warning about growth rather than a shipping defect.
Where I land
★ Ship C - the full page, kickers and hairlines, no boxes. It is the only variant that is honest about all three facts at once: the menu has four rows, two of its sections hold one row, and a GWCard on this page is a 1.01:1 fill carried by a 1.36:1 hairline. A kicker over one row is a label and costs nothing; a box over one row is a container with nothing in it. C uses GWPageHeader, GWKicker and GWSelectRow exactly as they ship, adds no component, and is the only variant where turning GW_DEV_TOOLS on adds a named group without restyling anything above it.

Runner-up: A - the flat list. Genuinely close, and it wins outright if you accept that four things do not need headings. A is _MoreSheetBody given a page: zero new anything, and the smallest diff in this sketch. Take A over C if the DEVELOPER group can live behind a rule rather than a name, because that is the single point on which they differ. A is also strictly inside C - adding kickers to A is C, so nothing built for A is wasted.

Explicitly rejected: D - the tile grid. Two new components and a second visual language for "a place you can go", to fix the fact that a four-row page has whitespace. The menu is the app's least-visited surface and D gives it the visual weight of a dashboard, which inverts the rule the whole sketch is built on. If the page looks thin, that is information about the app, not a defect to decorate away.

On E, which is not rejected. At today's four rows the sheet is defensible and it is the cheapest option here, because two of the brief's three arguments for a page are weak at this size and only the children argument holds. Ship the page anyway - but for the one reason that survives: every row opens a full screen, and a sheet that opens a screen destroys itself to do it. If that reason ever stops mattering, E is the honest fallback and it is a deletion rather than a build.

Still open
  • Does Appearance get promoted out of the dev bubble? The logic ships and persists; the control does not exist for users, and gw_appearance.dart:12 documents a Preferences sheet that was never built. One row would close a stale comment and give the menu its first thing that is not a destination. Not taken here.
  • Is "Settings" the right label for a screen containing spdlog levels, PubSub ports and CRDT backup intervals? Under GW_DEV_TOOLS the menu would then hold two developer groups with one of them called Settings. Renaming is out of scope; noticing it is not.
  • Where does the page go back to? The hamburger toggles in this mock. A pushed /menu inside the shell has no back affordance of its own, and Transactions and Assets both push without one today.
  • No device verification - this is a browser at 1:1, not Jakub's iPhone. Light mode not computed, per the dark-first rule.
