070 · The coin page, on the components the app already ships

Design question: sketch 061 owns this page’s chrome - the missing navbar, the frame, the header - and its recommendation A says the internal layout stays as it is. This is the layer underneath: what do the Convert card and the Info card look like when every element maps to a component the app already has? Two of the defects below were fixed elsewhere in the app on 2026-07-28 and this screen never got the change.

Not in scope: TokenActionBar is already a proper component with three real states, and _buildSectionTitle is already GWKicker. Both stay.

Where every element comes from

Findings from the code

1 · Both Convert fields use the notched Material floating label. label: on the price, labelText: "Token Amount" on the amount (token_info_screen.dart:561). This is the only pattern of its kind in the app besides custom_drop_down.dart. Everywhere else - GWTextField, swap_field, submit_logs_screen, and every drawer shipped this week - the label sits above the box at labelMd / textSecondary / space4. Two field grammars in one app, and this screen is on the minority one.
2 · Token Amount lights a FLAT brandPrimaryStrong on focus. Visible in the shipped screenshot as a blue notch and a blue 2px border. That is the one thing the global accent rule forbids - and it is structural, not an oversight: a BorderSide takes a single Color, so no InputBorder can ever be a gradient. That is precisely why GWFocusRing exists, and why GWTextField grew a focusRing flag on 2026-07-28 for the SDK dialogs. This screen has the same defect and did not get the same fix.
3 · The Info card is GWDetailGrid written by hand. _MarketDataInfo.statRow is padding 11/12, a 22px leading glyph slot, key at 14/textSecondary, value at 14/tabular/textPrimary. That is the component that shipped the same day for the transaction receipt, minus the recessed well and the hairline rules. Six rows with no separators at all.
4 · Copy-address exists twice, one day apart. Here it is an inline compact IconButton at the end of the value. The receipt shipped _CopyRow, where the whole row is the target and the glyph is present at rest - because an affordance you have to hover to discover is not one. Same idea, two implementations, and the smaller target is the older one.
5 · Total: $63,504.00 is a bare right-aligned bodyLarge. The one computed result on the card, and the only element with no structure around it. It reads as a caption rather than an answer.

Network is the tell. It is the single glyph in the set that flips with the canvas (#14C8FF dark → #0A6885 light), and it is the single glyph that still reads in light mode. The other five are raw constants. So the honest choice is not “rainbow or not” - it is:

(a) keep the rainbow and give every colour a light-mode counterpart, the way brandPrimaryOnSurface already has one - five new tokens; or (b) one accent, which is brandPrimaryOnSurface and is already correct in both modes - zero new tokens.

Use the Glyphs toggle above to see both. Then switch to Light. That is the whole argument.
And one thing colour is NOT doing here. Red on Total Supply carries no meaning - nothing is wrong with a total supply. Every row is already fully identified by its label, so under 1.4.11 these glyphs are decorative, which is why none of this is a WCAG failure. It is a legibility and a semantics question: statusError is the app’s error tone, and it is being spent on a neutral number.

Two measured results that decide between A and B.

(1) B puts an input inside the grid well, and the field edge fails there in light mode: 2.85:1 against a 3.0 threshold. A control’s border is not decoration - it is what identifies the control - so this is a real 1.4.11 failure, not an aesthetic one. B would need a fourth border token to exist. That is what kills it.

(2) The key text on the light well lands at 4.23:1, under 4.5. This is inherited, not new: the transaction receipt shipped the same pairing today. It is a light-mode finding for the dedicated light pass, and it is recorded here rather than fixed, per the standing dark-first order - but it applies to GWDetailGrid everywhere, not just this screen.

Recommendation

★ A · On components. It closes all four defects with zero new components - GWTextField(focusRing, fill), GWDetailGrid and the receipt’s copy row all shipped this week and all have consumers already. The Convert card and the Info card end up speaking the same language as the transaction receipt, which is the screen a user reaches from the same page.

Runner-up: C · Minimum. The right answer if the coin page should not be reopened beyond its defects - it fixes the two things that are actually wrong (the notched label, the flat blue focus) and touches nothing else. It is not the pick only because finding 3 leaves a hand-written copy of a component that exists, which is exactly the drift this whole week has been removing.

Rejected: B · One well. The prettiest of the three and the one I would have picked on looks. The contrast table kills it: an input inside the well measures 2.85:1 in light mode against a 3.0 threshold, so it would ship a control whose boundary is not identifiable, or force a fourth border token into the system to serve one card.
