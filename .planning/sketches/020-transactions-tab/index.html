020 · Transactions tab — layout, filters, empty states

What is actually wrong — from the code, not the eye

The tab does not have a weak design. It has no page design at all: it mounts the homepage panel verbatim and lets it float. Three concrete causes, each one line.

Cause 1 · width

The page is capped at panel width

transactions_slim_view.dart:177 caps itself at GeniusBreakpoints.medium = 768px, because it is a dashboard panel. transactions_screen.dart:26 wraps it in a Center.

On a 2000px window that is a 736px column with ~630px of dead base surface on each side. The sibling tab markets_screen.dart:70 caps at xxl = 1536px and scales its column count with width. Transactions is the odd one out.

Cause 2 · header

A panel title is doing a page title's job

transactions_slim_view.dart:192 uses GWSectionTitle — the 18px panel header with its shared 44px min-height, designed to sit inside a card next to Assets and Markets.

Every other full page in the app (markets_screen.dart:73, crypto_news_screen.dart:50, swap_screen.dart:228) uses GWPageHeader — 24px headlineLg. So "Transactions" renders one size smaller than every other page title in the product.

Cause 3 · no surface

The list sits on the raw base colour

On the dashboard the same widget is wrapped in DashboardScrollContainer (dashboard_screen.dart:322) — GWDecorations.surface, radiusLg, borderSubtle, space6 padding.

The tab wraps it in nothing. The rows hang on surface-base with no edge, which is exactly why the screenshot reads as an unfinished screen rather than a sparse one.

Cause 4 · empty state

The empty block is pinned to the vertical midpoint

gw_empty_state.dart:129 returns a Center, and both call sites hand it an Expanded (transactions_slim_view.dart:208). In a ~1400px-tall slot the icon lands 700px down, below the fold, with a void above and below it.

Second defect in the same screenshot: the filter bar is still rendered on a wallet with zero transactions — five controls offering to filter nothing.

Recommendation and what each one costs

SchemeWhat the width buysFiles touchedRisk
A · Page frame Nothing extra — it stops the stretch at 1024 and frames the result so the margin reads as intentional. transactions_screen.dart only (~15 lines). Zero changes to row, filters, badges, tests. None. Also the fallback if B is rejected — B is A plus a rail.
B · Filter rail recommended All nine filters visible with live counts, no popup. The ⋯ menu disappears from the page. transactions_screen.dart + one private _FilterRail (~60 lines) reusing filterCounts() and badgeGlyph(). Row untouched. Two filter presentations exist — chips on the dashboard panel, rail on the page. Standard responsive answer, but it is a divergence and should be named as one.
C · Wide table Real columns; best scanning at 1536px. transaction_displays.dart gains a second layout, plus a header row, a status pill, and new tests. Breaks Phase 12's locked "one anatomy for all seven types". Largest diff, and the drawer would then disagree with the row it was opened from.

Pick B for the tab and E3 for both empty states. B is A with ~60 extra lines and it is the only cheap variant that turns the width into something usable; if the two-filter-presentation divergence bothers you, A ships in twenty minutes and nothing is lost — B is a strict superset of it. C is the right answer for a different product, and it costs the row rule Phase 12 just paid for.
