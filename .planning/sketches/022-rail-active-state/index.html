2 · The one open decision — the active rail row

All five share the identical rest and hover states (_menuItem geometry, sketch 008 "lift chip" hover) and all five leave the glyph untouched — the rule locked at transactions_slim_view.dart:525. Only the active mark differs. Toggle Light in the toolbar before deciding: every gradient in this app degrades to flat #0A6885 on light surfaces, because brandCta's own stops measure 1.65:1 and 2.28:1 there.

A · Leading rail Adapted
2px gradient bar on the left edge + gradient label. The navbar's active-tab indicator, rotated to vertical.
navbar indicator + _activeLabelShader
Against: the bar sits outside the row's padding, so it reads as a margin ornament rather than as part of the item. Rotating a horizontal mark to vertical is the weakest kind of "precedent".
B · Underline Adapted recommended
Gradient label + a 2px gradient underline under the label itself. This is the navbar's mark used as it is — same orientation, same 2px, same gradient, same relationship to a word.
navbar active tab, unrotated
For: a rail item and a nav tab are the same thing — a persistent destination-like selection with a label. Nothing is re-oriented or reinterpreted. Against: the underline width tracks the word, so the mark's length varies row to row.
B2 · Underline only Existing recommended
The same 2px gradient underline, but the label is never recoloured — it just goes w700 textPrimary, exactly like an active nav tab.
navbar active tab, copied outright
This is what the navbar actually does. Look at "Transactions" in the top bar: white and bold with a gradient rule under it — the text is not gradient. B adds a second gradient the navbar never had. Also: no light-mode text degradation to keep in sync, because the label is never brand-coloured.
C · Gradient count New
Label goes plain w700; the count becomes the gradient. The number is what the filter actually changes, so the mark lands on the payload rather than the name.
no precedent — the app has never marked state on a numeral
Against, and it is serious: the counts do not change when you filter — filterCounts() is computed over the unfiltered list on purpose — so a gradient number promises movement that never happens. It is also the quietest of the five at exactly the moment you need the loudest.
D · Underline + count Adapted
B plus C: gradient label, gradient underline, gradient count. Everything the row owns turns brand at once.
navbar indicator + _activeLabelShader + new numeral treatment
Against: three marks for one boolean. When every element shouts, the row stops having a hierarchy — and it inherits C's problem of gradient-ing a number that never moves.
E · Gradient wash New
"Current solution but in gradient colour" — the row background becomes a low-alpha brandCta wash, label w700 textPrimary.
no precedent — this is 020's rejected brand-fill with a gradient in it
Against: a 16% wash measures well under the 3:1 WCAG 1.4.11 wants for a UI-state boundary, so it cannot be the only mark — the w700 is doing the real work. It also collides with the hover surface: hover fills the row too, so hover and active become the same gesture in two tints.

B vs B2 — the decision, side by side

You asked for the underline without the recoloured text, and it changes my recommendation. Go and look at the top bar of the app: the active tab is white and bold with a gradient rule under it — the label itself is not gradient. So B2 is the navbar's mark copied outright; B is the navbar's mark plus a second gradient the navbar never had.

And it is the same argument I used to reject D. If the underline already says "selected", a gradient label says it a second time — redundant state marking, which is exactly what made D worse than B. By my own reasoning, B2 beats B. It also has one fewer moving part in light mode: the label is never brand-coloured, so there is no text degradation to keep in sync with the underline's.
