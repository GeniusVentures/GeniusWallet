101 · Magazine, tuned — three refinements of 100 B

100 B won. All three variants below keep it: photo-led, hero on top, cards under. What differs is only how B answers the one objection it lost on — the live feed returns 30 items and B shows ~4 per screen, so today's design is eight screens of scrolling. Every part is annotated with the component it maps to; the component table is at the bottom, and it has one real gap in it.

B1 · Tight

zero new widgets

Nothing structural moves. The hero drops 280→230px, the grid goes 3→4 columns at ≥1200px with 130px photos, and the dek is one line instead of two. Same design, tuned metrics. ~7 stories on the first screen instead of 4. Still 30 items, so still a long page — this variant accepts that and just makes the scroll shorter.

B2 · Hero + Next up

reuses GWSectionTitle

The hero keeps its size but stops owning the whole first row: beside it sits a Next up column of three headline-only rows — no photo, just number, headline, timestamp. The first screen carries 4 stories with one still clearly the lead. Grid below stays 3-column and full-size, so the photo-led feel is untouched.

B3 · Head & tail

recommended reuses GWSectionTitle

Magazine where it is looked at, list where it is scrolled past. Hero + 6 cards is one full magazine screen; then a GWSectionTitle('Earlier') and the remaining 23 items as compact rows with an 88×60 thumbnail. The whole day fits in about three screens instead of eight, and the photos still lead the page. The row is the one from sketch 100 A, so nothing is invented twice.

What each part is built from

You asked to lean on what exists. Here is the honest map — including the one thing that does not exist yet.

PartComponentStatus
Page title + RefreshGWPageHeader(title:'Crypto News', trailing: …) exists The trailing slot is already in the API (gw_page_header.dart:10) and already owns the space8 gap below — the screen must not add its own spacer.
Hero card · news cardGWCard(onTap: …, radius: radiusLg) exists Gives the sheen gradient, hairline border and elevation.card for free. Today's news card hand-rolls all three in a raw Container (crypto_news_screen.dart:116-121).
Card hover (lift chip)— none missing GWCard has no hover state at all. Passing onTap wraps it in an InkWell (gw_card.dart:62-71), which paints Material's grey highlight — not the 008 D lift. Today's card works around it with its own MouseRegion + a black scrim (crypto_news_screen.dart:110-126, 154-185). Fix it once in GWCard (a hoverLift flag) and every card in the app — Assets, Markets, Transactions — gets the standard hover. That is the highest-leverage line in this sketch.
"Earlier" divider (B3) · "Next up" (B2)GWSectionTitle(title: …, trailing: …) exists 18px titleLg, letterSpacing -0.2, reserves the shared 44px header height and owns its space8 gap (gw_section_title.dart:21-66). Documented as the panel-level analogue of GWPageHeader — exactly this use.
Search fieldGWTextField(hint:'Search headlines', prefix: Icon(Icons.search)) exists prefix and onChanged are already on the API (gw_text_field.dart:19, 25). Leave label null so it renders without the label row above.
Refresh controlGWButton(variant: ghost, size: sm, leading: Icon(Icons.refresh)) exists ghost and sm are both in the enums (gw_button.dart:9-24). No new button needed.
PhotoCachedNetworkImage exists Already the dependency in use. All 30 feed items carry <enclosure>, so imageUrl is never null in practice — but keep the errorWidget anyway; the CDN can still 404.
LoadingPulsingSkeleton(height:, width:) exists Hero + card shapes can be assembled from it (pulsing_skeleton.dart). Sketch 102 draws the arrangement.
Empty · errorGWEmptyState · GWErrorState exists Both take title, message, an action/retry. Today the screen uses bare Text instead (crypto_news_screen.dart:55-70).
GridGridView + SliverGridDelegate…MaxCrossAxisExtent stdlib Replaces StaggeredGrid.extent. Drops the flutter_staggered_grid_view dependency — nothing else in the app imports it.
Tail row (B3 only)— new, ~40 lines new A Row of thumbnail + title + meta. Same anatomy as the transaction row, but it is not worth generalising the two into one widget yet.

Density, measured against the real 30-item feed

B1 · Tight
~7 on the first screen · ~5 screens total
Cheapest possible change — it is 100 B with different numbers. No new widget, no new section. Downside: the 4th column at 1280 leaves each card ~296px, so a 102-char title (the measured max) runs the full 3-line clamp and the cards get visually noisy.
B2 · Hero + Next up
~4 on the first screen · ~7 screens total
Best first impression — the top of the page reads like a front page. But it barely touches the real problem: items 5-30 still scroll as full-size cards. Solves the hero's loneliness, not the length.
B3 · Head & tail
~5 on the first screen · ~3 screens total
The only variant that changes the shape of the whole page rather than the top of it. Photos lead where a photo earns attention; past item 7 nobody is browsing pictures, they are scanning for a headline they missed. Costs one new row widget.

What to look for

1. Hover any card in any variant — this is the lift chip, and it is the treatment GWCard would gain. Compare it to today's black scrim. 2. Switch to 900, then scroll each variant to the bottom. That is the real comparison: how long is the page. 3. Switch to 420 — B1's grid goes single column, B2's Next up column drops below the hero, B3's tail rows stay readable at 88×60. 4. In B1, read the longest headline in the 4-column grid; decide if 296px per card is too tight.
