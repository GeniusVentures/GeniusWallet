072 · The coin page's actions, holding only what the code can do

Jakub’s rule, verbatim: “dla CTA, dla których nie ma nic zbudowanego […] nie możemy tego używać. Nie budujemy tego […] Jeśli czegoś nie ma w kodzie, to nie uwzględniamy designu.” No new features, no speculative affordances.

Use the “Arrived from” switch - it is the whole point of this sketch. The same page has a different number of live actions depending on which of the four routes you took to reach it, and today’s fixed four-tile row cannot say so.

Findings from the code

1 · Send does not exist at any layer a user can reach. No screen, no route. lib/reown/send_transaction_details.dart is a dApp asking you to sign, not a transfer you start. GeniusApi.transferTokens(amount, address, {tokenId}) is real (genius_api.dart:879) and has zero callers in the entire repository - a native transfer capability with no UI above it. By Jakub’s rule the button leaves the design.
2 · More is dead on THREE of the four ways into this page, and that is the finding that reframes the sketch. isGnusWalletConnected is hardcoded false at markets_screen.dart:58 and dashboard_markets.dart:83, and markets_search_bar.dart:93 does not pass the key at all (so null → false). Only coins_screen.dart:296 forwards a real value.

So arriving from Markets - the main route - exactly ONE of four buttons does anything. The page ships an action bar that is 75% inert on its primary path, and no screenshot of it looks broken.
3 · Three different truths, one grey box. _ActVariant.disabled renders Send, Swap and a GNUS-gated More identically: “nobody built this”, “this works, it just is not connected here” and “this only applies to GNUS” are not the same message. Variant A dissolves this rather than solving it - with nothing dead in the row there is no grey box to disambiguate.
4 · Swap can be wired today, but preselection cannot. SwapScreen takes no parameters at all (const SwapScreen({super.key})), so tapping Swap opens an empty swap form and the user re-picks the token they were just looking at. The pattern for fixing that is next door - BridgeScreen(fromToken: walletCubit.state.selectedCoin) - but it is a change, so no variant here draws a preselected swap. The honest cost: a fromToken param, a state.extra read, and mapping a Coin to a SquidTokenInfo by symbol + chain, which is the real work.
5 · Buy is reachable in code, and is NOT proposed. BanxaBuyScreen takes initialCryptoCode and initialWalletAddress, and /createOrder accepts them - so a per-coin Buy exists. But two todos are already filed against that path: the app’s existing Buy CTA opens the order history instead of a buy screen, and the Banxa orders fetch uses a hardcoded placeholder customer id. Adding a Buy button to this page would be putting a new door on a corridor that is already reported broken. Drawn in the menu variant as a disabled candidate only, so the option is visible without being taken.
Which of these are design choices and which ride with any variant. Defects, not choices: Send leaving the page (finding 1), and the three hardcoded isGnusWalletConnected: false call sites (finding 2) - that one is a bug to fix in the callers, not something a layout can paper over, and it should be filed whichever variant wins. Choices: how the row handles a count that changes by route, and whether unavailable actions are absent or shown disabled.

Recommendation

★ A · Only what works. It is the literal answer to the rule that prompted the sketch: the row contains what the code can do and nothing else, so there is no disabled state to design, no grey box collapsing three meanings, and no promise the app cannot keep. It needs no new pattern - GWButton at natural width, left-aligned - and it makes the count honest on every route, which is finding 2 made visible rather than hidden.

Runner-up: B · One CTA + menu. The right answer if the action list is expected to GROW - it is the exact discipline 069-A settled for the SDK rows (one menu, same items, same order, inapplicable ones disabled rather than absent), and Buy would slot into it without a redesign. Not the pick today because with two live actions a menu is a heavy way to hold one item, and because the growth it is designed for is speculative - which is what the rule forbids.

Rejected: C · Into the header. Reclaims ~74px and looks tidy, but GWPageHeader’s trailing slot already holds the price and its change pill (071-B, shipped today). Putting actions there means the price moves or the actions become unlabelled icons - and on a narrow window the page’s ONLY live action ends up as a 16px glyph next to a 28px number.
