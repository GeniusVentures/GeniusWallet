What the rail is — and isn't

It is not a progress bar. Measured, the SDK climbs for ~750 ms and then stalls at 52.5% on "Initializing blockchain service" — still stuck 40 s later. A bar wired to that number would sit half-full forever.

So the rail claims nothing while waiting: it holds at zero, then sweeps to full as the app hands over to the dashboard. It reads as "done", not as "x% complete" — and because the sweep happens after the freeze lifts, it is the one thing on this screen that genuinely animates.

Everything the dashboard needs is already loaded at 141 ms (wallets 0 ms, transactions 140 ms, balances 141 ms). The only real wait is the freeze.

The closing run — and what it costs

Three lines over ~1.5 s: Wallets ready → Balances ready → Markets ready. Each is a confirmation, not a progress claim, so every line is true at the moment it appears — they all actually completed back at 141 ms.

Be clear-eyed about the cost: this adds ~1.5 s to a boot that is already 9.6 s. It buys a resolution beat — after a long dead screen, a burst of activity reads as "arriving" instead of an abrupt cut to the dashboard.

It is not pure theatre, though. The run also covers the markets/chart fetch, which is real network work of variable length. Treat 1.5 s as a minimum hold: if markets take longer, the run stretches; if they fail, it ends on cached data rather than waiting.
