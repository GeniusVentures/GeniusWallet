191 - seven filter treatments inside 190-C

Jakub, 2026-08-09: C one panel for transactions, but the filters as shown are terrible - do five to seven designs. Every tab below is the same 190-C page: one panel, control at the top, kicker with the count, rows. Only the control changes. Real tokens, real Inter, 390 x 844 at 1:1, every filter live, and each scheme reports the vertical it spends and how many of the nine filters it can reach without a second tap.

Today - as shipped, drawn correctly this time

A correction to my own sketches first. 188 and 190 drew a small count on each chip. There is no count on the chip in the code. _FilterChip draws badgeGlyph and nothing else; the counts map reaches only the overflow menu's rows. What ships is thinner than what I showed you.

The wide page already solved this

_FilterRail - the same nine filters as a `Column` of rows with icon, label and live count - is what a 1280px window gets. Its own doc says the popup exists "ONLY because a 376px dashboard panel cannot show nine filters". But this is the page, not the panel, and the phone page inherited the panel's control anyway. The phone is the only surface in the app that hides these labels.

A seventh problem, which is not visual and survives whichever scheme wins. Filters is ONE enum mixing two orthogonal axes - seven types (Sent, Received, Mint, Jobs, Escrow, Swap, Purchase) and two statuses (Pending, Failed) - and selection is a single value. So choosing Pending un-chooses Sent, and "my failed sends" is not a question this control can ask. Scheme F7 is the only one that fixes it; every other scheme inherits it. Worth deciding on its own.
F1 - labelled scrolling track  recommended

Every filter says its own name. All + nine chips, each icon + label + count, in one horizontally scrolling row. No overflow menu, no hidden filters.

F1 - say the names

The smallest change that answers all six complaints at once: keep the chip, give it a label and a count, put All first, and let the row scroll instead of amputating five filters into a menu. It is the rail's content in the track's shape.

The one real cost: an edge

A scrolling row hides its tail. The mitigation is drawn, not hoped for - the last visible chip is deliberately clipped by the card edge and a short fade sits over it, which is the standard signal that a row continues. Turn RULER on and look at the right edge. If that still reads as "there is nothing more", F1 is wrong and F2 or F3 is right.

A zero-count filter stays visible and goes quiet

Escrow has 0 in this data. It renders at 42% opacity and does not respond - the same treatment the rail gives it. Hiding it would make the control's contents change shape as the wallet's history changes, which is worse than a dim chip.

Recommended. It is the only scheme that fixes all six without changing what kind of control this is: same GWControlTrack family, same chips, same tap semantics, everything reachable in one gesture. The diff is a label, a count, an All chip and the deletion of the popup.
F2 - wrapped, nothing hidden

All ten on screen at once. Label-only chips wrapping onto three lines. No scroll, no menu, no edge - if it exists, you can see it.

F2 - the honest one

F1's weakness is that a scroll edge can be missed. F2 removes the edge by removing the scroll: every filter is laid out at once and the block simply gets taller. Nothing about the control is conditional, which makes it the easiest to reason about and the easiest to test.

What it costs, measured under the phone

Three rows of 32px chips plus two 6px gaps is 108px against F1's 38px. On a 628px viewport that is 11% of the first screen spent on a control most sessions never touch, permanently, on every visit. Read the vertical meter - it is measured from the rendered DOM.

Why the icons go

With ten chips wrapping, an icon in each adds ~20px per chip and pushes the block to four lines. The label already identifies the filter; the icon was doing that job only because there was no label. Dropping it is what keeps F2 at three rows.

Take F2 if the scroll edge in F1 fails on the device. It is the same idea with the ambiguity traded for height. It is also the scheme that ages worst: an eighth type makes it four rows, and nothing about it degrades gracefully.
F3 - one full-width select

Where Assets puts its search field, Transactions puts its filter. One 44px full-width control saying what is showing; tapping it opens a sheet with all nine, labelled and counted.

F3 - the literal twin of Assets

This is the strongest reading of "the same language as Assets". Assets' panel 2 opens with a full-width 44px control (GWSearchField) and the kicker under it. F3 puts a full-width 44px control in the same slot, with the same height, radius, fill and hairline. The two panels become the same object with a different verb.

What it gives up

Glanceability. With F1 you can see that Mint has 1 and Jobs has 1 without touching anything; with F3 you see only what you have chosen. For a control most people use rarely that is a fair trade; for a control you want people to discover, it is not, because a closed select advertises nothing.

The sheet is not new

The rows in it are _menuItem - glyph, label, count, gradient label when active - which already exists and already renders exactly this. What changes is the container: a bottom sheet (ResponsiveDrawer, sketch 018) instead of a PopupMenuButton anchored to a 44px target in the top-right of a phone.

Runner-up, and the one to take if vertical space is the priority. It is the cheapest in pixels, the only one that scales for free, and the closest to Assets structurally. Tap the control and use the sheet before judging it.
F4 - underline tabs

No fill anywhere. Label + count, active marked by a 2px gradient underline - the mark sketch 022 already locked for the filter rail.

F4 - reuse the active mark we already decided

Sketch 022 chose B2 - underline only for the rail's active row: the label never recolours, a 2px gradient rule sits beneath it, the glyph is untouched. That decision was made for exactly this problem - how to mark selection without shouting - and F4 applies it to the phone.

Two real advantages
  • The lightest ink of any scheme. No chip fills, no borders, no track - just text on the card, with one 1px rule under the row. Next to a list of rows that is the quietest a control can be.
  • It is already the app's vocabulary - the navbar's active tab is a 3px brandCta underline, and 022 put the same mark on the rail.
And the objection, which is the same one 008 raised

Underlined tabs read as sections of a page, not as a filter over a list. A user who has learned that an underline means "you are on this page" will read Mint as a different screen. That is why the nav gradient was kept reserved. F4 spends it a third time.

Beautiful and slightly dishonest. Take it only if you are comfortable with the gradient underline meaning two different things one tap apart - a destination in the navbar, a filter here.
F5 - search leads, filter follows

The same GWSearchField Assets has, with a 44px filter trigger beside it carrying a count badge when a filter is live.

F5 - the question behind the question

Every other scheme assumes the way to find a transaction is to filter by type. On a wallet with a real history it usually is not: you are looking for the payment to that address, the 250 USDC one, the BTC one from last week. Type is a coarse axis; text is the precise one, and Assets already shipped the precise one.

What it would search

Everything the row already prints, with no new data and no network - the same shape as matchesAssetQuery: token symbol, the action word, the counterparty string (0x7a3f…9c21, Banxa, Compute reward), and the amount. Type the address fragment in the field and the list narrows.

Named honestly: this is scope, not a filter treatment. You asked for filter designs and F5 answers with a different control. It is here because it is the one scheme that would change how the page is actually used, and because the search field is the piece of Assets' panel 2 that every other scheme here quietly drops. If it interests you it should be its own decision, not a way of settling this one.
If both, then what

The drawn arrangement is search full-width with the filter as a 44px trigger to its right, opening F3's sheet. That keeps one row of vertical for two controls. The badge on the trigger is what stops a live filter from being invisible, which is the defect the ⋯ already has today.

F6 - the kicker is the control

Zero extra vertical. There is no control row. The kicker line that already counts the list carries the filter on its right: 24 TRANSACTIONS / ALL ▾.

F6 - stop spending a row on it

Assets' kicker line already carries a control on the right: VALUE ↓, the sort toggle (assets_screen.dart:444). F6 is that pattern exactly - the count on the left, the control on the right, on one 16px line. It is the only scheme that costs nothing, because the kicker is already there in 190-C.

The reason it is not the recommendation

It hides the whole control inside an 11px uppercase label. GWKicker is dense type used for captions; making it the only entrance to nine filters puts the app's smallest text in charge of its most structural control. F3 does the same job at 15px with a real 44px target.

Take F6 if the answer is "filters barely matter on a phone". That is a defensible position - and if it is the position, F6 is the honest expression of it, not a compromise. Just note that the sort toggle it copies is a two-state control, and this one has ten.
F7 - two tiers, type and status at once

The only scheme that fixes the model. Types scroll on one line; Pending and Failed sit on their own line and combine with a type instead of replacing it. Pick Sent then Failed.

F7 - "my failed sends" becomes a question you can ask

The defect is in the model, not the pixels: Filters is one enum holding two unrelated axes, and the selection is a single value. Seven of its members answer what kind of transaction; two answer how did it end. Choosing one erases the other.

What it costs to build, stated plainly

This is the only scheme whose diff is not confined to the widget. Selection stops being one Filters and becomes a type and a status; matches() becomes a conjunction; filterCounts() has to count against the other axis's current selection or the counts go stale the moment a status is live. The empty-state string (filteredEmptyTitle) has to name both. That is a real piece of work, and it is why it is a separate decision rather than a variant of F1.

Note what the second tier does to the counts

With Failed live, the type counts change - Sent drops from 3 to 1 - because the counts are now conditional. Tap Failed and watch the type row renumber. That behaviour is the whole reason this cannot be bolted onto F1 later without touching the same code twice.

Not the answer to today's question, and the right answer to a better one. If F1 ships, F7 is the natural follow-up and F1's chips become the type tier unchanged. If you want it now, it is a phase, not a tweak.
