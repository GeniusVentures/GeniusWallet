069 · The SDK Accounts section, end to end

Design question: the SDK section is one navbar chip, one drawer and five dialogs (sdk_account_manager.dart). Its footer CTAs truncate to "Add with mn…" / "Add with priv…" at the panel's real width, its row actions are split across two different affordances depending on row state, and one of its dialogs never went through GWDialog. What is the shape of the whole section on today's components?

Findings from the code

1 · The footer CTAs cannot fit and the code cannot know it. Two Expanded GWButtons in a 420px panel: 420 − 40 padding − 8 gap = 186px each, and "Add with private key" plus a 20px leading icon needs roughly 210. Flutter ellipsizes silently, so the drawer ships two buttons that say "Add with mn…" and "Add with priv…". Nothing in the widget tree is wrong; the layout is simply asking for more room than exists.
2 · "Copy mnemonic" puts a seed phrase on the clipboard with no confirmation and no feedback. onPressed: () => {Clipboard.setData(ClipboardData(text: mnemonic))} — that is the whole handler. No warning before, no snackbar after. Every other copy in the app confirms ("Address copied to clipboard"), and this is the one value in the app where a silent clipboard write is a security event rather than a convenience.
3 · Row actions are split by state across two affordances. The selected row gets a ⋮ menu with three items (Set payout address, Copy mnemonic, Show QR). Every other row gets a bare red delete IconButton and no menu. So Delete is never in the menu and the menu never appears on a row you can delete — and the code's own guard ("Cannot delete the currently selected SDK account") can never fire from the UI, because the button it guards is not rendered on that row.
4 · The payout-address result is read one frame too early. context.read<AppBloc>().add(SetSDKPayoutAddress(...)) is followed immediately by state.setPayoutAddressResult. A bloc processes events asynchronously, so that read returns the value from the previous attempt — the success/failure snackbar is reporting the last result, not this one. First call after a fresh start reports null.
5 · The QR dialog is the only one outside GWDialog. It is a raw AlertDialog with a TextButton "Cancel". Its white QR backdrop is deliberate and stays — QR codes need it to scan — but the shell around it should be the component. Also: the payout field has no validation at all, where the app already knows what an address looks like.

All three unify the row menu, and that is not a variant choice — it is finding 3. Every row gets the same ⋮ with the same four items; the ones that do not apply are disabled, not absent, so the menu's shape does not change under you and Delete stops being a separate red button that only exists on some rows. Delete stays destructive-coloured and is disabled on the active account, which is where the code's existing guard finally becomes visible.
