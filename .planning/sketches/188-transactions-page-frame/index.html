188 - the Transactions page: boxed or flat, and what Assets has to match

Sketch 187 asked whether /assets should be boxed. This one asks the same question of the tab next to it - and answers a factual question first: what does /transactions actually do today? The answer changes the recommendation in 187, so it is stated as a correction rather than buried. Real tokens, real Inter, a real 390 x 844 phone at 1:1, live filters, and the four data states.

CORRECTION to sketch 187, finding 3. That sketch says no full page uses DashboardScrollContainer - not Transactions, not Markets, not News. That is wrong, and transactions_slim_view.dart:483 is the proof. The narrow-page branch of _page() wraps the transaction list in DashboardScrollContainer - the homepage panel container, by name. The grep that produced the claim in 187 searched the two files that DEFINE the panels and missed the one that consumes it from a page. So /transactions on a phone is already boxed, and the scheme this session recommended against is the one already shipping next door.

Assets is the only unboxed list in the app. That reverses the argument in 187: boxing it is not importing a dashboard device onto a page, it is stopping one page from being the exception.

What survives from 187 unchanged
  • The back link still goes. /assets is a bar tab (nav_destinations.dart:143-146); /transactions is too, and it carries no back link - so today the two tabs disagree, and Assets is again the odd one.
  • The frame fix still stands. Transactions calls pageTitleGap / pageGutter (transactions_screen.dart:79-81); Assets hardcodes 64 and 12. Whatever wins here, that is a bug.
  • The 14px is still real - a boxed list is 348 of content where a flat one is 362. Transactions pays it today and its amount column is the one measured clipping. The cost did not vanish; it turns out to be a cost the app already accepted.

Pick one language and both tabs follow it. The states are shared: BUSY (nine rows over three days), QUIET (two rows), FILTERED EMPTY (the filter matched nothing but the wallet is not empty) and EMPTY.

A - flat

Nothing is boxed. The filter track and the rows sit straight on surfaceBase, separated by the borderSubtle rule. This is Assets' current language, moved onto Transactions.

A - the widest rows in the sketch

Row content is 362px, 14 more than B and C. On the row that prompted sketch 179 - a long lead beside a long status - that 14 is the difference between Minted to wallet fitting and ellipsising.

What it costs

A day label with no container is a heading floating on the page. Turn on BUSY and look at Yesterday and 7 Aug: with a card, the labels read as sections inside one object; without one, they read as three separate lists with no boundary. That is the argument the box actually wins on here, and it is a stronger one than the argument it wins on for Assets, which has no day grouping at all.

It is also a regression against what ships: this is the one scheme on the page that requires deleting working code (transactions_slim_view.dart:483) rather than adding to it.

Only pick A if the answer for BOTH tabs is flat - and if it is, Transactions, Markets and News all change, not just Assets. That is a four-page decision, not a one-page one.
B - as shipped today

This is the app right now, not a proposal: page title flat, filter track flat on its own row, list in one DashboardScrollContainer. Drawn so the comparison has a baseline.

B - the shipped answer

The split is not arbitrary. The track is a control and the card is content: putting the control outside means it does not scroll away with the rows it filters, and it keeps its 44px touch targets clear of the card wall. The code says exactly that at transactions_slim_view.dart:449-461 - the bar gets its own row on the phone page so the width for a real touch target exists.

Where it is weaker than C

The track floats: a pill on a bare canvas, with the card's edge starting 12px below it. At the top of the page that is fine; the moment you scroll, the pill sits over the card's top edge with nothing tying them together.

The Assets equivalent

B maps onto Assets as search and sort outside, rows in a card - which no sketch has drawn, because 187 scheme C put them inside. If B wins here, that variant needs building before Assets is touched.

Runner-up, and the safest. Zero code changes on this page; Assets then adopts the same split and the two tabs match for the first time.
C - two panels

Everything is in a panel. The filter track gets one, the list gets another, at the same space3 gap the homepage puts between its panels. This is 187 scheme C's language on this page.

C - one language, two tabs

If Assets goes boxed, this is what Transactions has to look like for the two to agree, and it is the only scheme here where the phone reads as one system: panel, gap, panel, gap, bar - the same rhythm OneColumnDashBoardView:330 already draws on Home with SizedBox(height: space3).

The honest objection, and the answer

A panel around a single pill is a container holding one control - the box over one row critique sketch 184 made when it rejected boxed menu sections. It is a real objection and the mitigation is in the sketch: the panel is full width while the track is intrinsic, so the panel is doing something the track cannot - it gives the control a left edge that lines up with the rows below it. Compare A and C at the track's left edge: in A the pill starts at 6, in C at 14, which is the row wall.

Cost

+14px of vertical (two 6px paddings and two hairlines) and the same 348px row content as B. No new component: the container is imported, exactly as transactions_slim_view.dart already imports it.

Recommended, if the answer to 187 is C. These two are one decision. Choosing boxed Assets and leaving Transactions on B means the two neighbouring tabs draw the same list two ways.
