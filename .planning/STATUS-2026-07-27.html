The one thing worth knowing before anything else

The button labelled "Buy GNUS" does not open a buy screen. coins_screen.dart:349 pushes /buy, and router.dart:80 maps /buy to the order history. The screen that actually buys something sits at /createOrder, reachable only through a small "+ New Order" text action. A user with no orders taps a gradient CTA promising a purchase and lands on "Total Orders: 0 / No orders found." - which is the screenshot. This is a one-line routing fix and it is worth more than every other item on this list.

The Assets balance value

sketch 155

Asked: five designs for the balance figure in the Assets panel - "wyglada srednio".

What it is today: coins_screen.dart:258-284 - a 20px/w700 total over +$82.91 · +1.36%, both crammed into the trailing slot of a 44px section-title row.

Three findings, from the code

  • The same dollar figure is printed twice on that row, from two different sources. The left card shows selectedWalletBalance (the wallet's own balance); the Assets header shows assetsTotal() (a CoinGecko fold). Both carry a $, neither says what it is. They match in the dev mock because one injector sets both. Nothing makes them agree in production.
  • The two-line column is centred in a 44px row and needs ~42px, so it is wedged edge to edge - which is most of the "wyglada srednio".
  • The delta joins a rate and an amount at equal weight with a literal mid-dot, flooded with one colour.
Variants 0 Today · A Value + chip · B Eyebrow stack · C Sparkline · D Balance band · E Quiet ledger
Recommendation: A · Value + chip. The % becomes a filled pill matching the +3.20% pills in the rows directly below it, the dollars go quiet grey, the cents drop to 54%, and "today" replaces the mid-dot. Smallest diff that fixes all three findings. Runner-up D · Balance band - structurally better, but only take it if the left card is being restructured too (sketch 016), otherwise two hero balances sit 12px apart. Rejected C · Sparkline - there is no portfolio time series in this app; it would have to be faked.

Asked: where do we stand with this part - open everything we did there.

Three sketches cover this panel and all three have chosen winners. None of them has been built. What is on screen today is still the pre-design card.

Why it matters that these are unbuilt

  • The 52.5% is a lie, and it was measured. Over 161 polls across 40s the value reaches 0.525 at t=10.6s and never changes again. A determinate ring promises it will reach 100. It does not.
  • The silent death. Any exception from getProcessingStatus() cancels the timer permanently; nothing restarts it. The UI then shows "idle" in grey - pixel-identical to a healthy node with nothing to do.
  • The zero-balance red. "No funds available" renders in statusError. An empty wallet is not a broken wallet.
Nothing new to decide here. The designs are chosen and documented, including an affordance audit that names the three code changes they need (a stall detector, a restartable processing timer, and a public AccountDrawer.show). This is a planning item, not a design one: it wants a phase of its own. It also interacts with item 1 - if 016-B2 lands, the balance-band variant becomes available for the Assets header.

Drawer colours

sketch 156

Asked: the drawer is fine, but the colours - it should be darker and more compatible with the rest.

That reading is correct, and it has a measurable cause.

SurfaceTokenValue
The pagesurfaceBase#0B0D12
Every cardsurfaceElevated#0C0E14
Every drawersurfaceMenu#171A21 - two steps lighter, and the only large surface at that value
  • The input field is painted the same colour as the panel it sits on. The drawer passes gw.surfaceMenu as the field background, and the panel is already surfaceMenu. Fill contrast: 1.00:1. It is not a box, it is a hairline.
  • That hairline is white at 12%, which measures 1.43:1 against its own canvas. WCAG 1.4.11 asks for 3:1 when a border is the only thing identifying an input. White at 30% is the first step that clears it.
  • Two dark fills can never carry the boundary alone (#171A21 on #0C0E14 is 1.11:1), so the answer has to be a pair: darker panel and stronger field edge.
Recommendation: A · Card canvas - panel down to surfaceElevated, field up to surfaceMenu, field edge to white 30%. Answers both halves of the request in one move, and it is one line in responsive_drawer.dart. That one line is also the whole risk - it re-skins all ~19 drawers, and ~17 of them are unwalked since the header change. It should ride the drawer walk that is already queued, not precede it. If the walk slips, take C · Sunken field - single-drawer scope, fixes the 1.00:1 outright, and does not block A later.

The Receive drawer

sketch 159

Asked: Receive design - with a screenshot and no further words.

So the sketch answers the unasked question first: is this what was decided? Mostly. Sketch 034 round 2 chose A2 "Grouped address" and two of its four parts shipped.

  • Drift: the 4-character chunked address shipped as a middle truncation (0x9fF8C9…262e2b). Chunks were chosen precisely because a receive address is the one string a user eyeball-verifies against another screen, and truncation hides the 26 middle characters.
  • The drawer body has zero horizontal padding, so the amber network warning runs to both panel edges. Same defect class as the transaction drawer in item 3, and the same fix location.
  • A blank network name produces broken copy: "Only send -network assets to this address."
  • AssetImage("") is constructed for the QR's centre image when the network has no icon.
  • Two things are right and must not be touched: the QR keeps a solid white backing in both appearances so a phone camera can read it, and the amber uses a darkened light-mode value because the warning token fails as text on white.
Recommendation: A · A2 as decided - finish the standing decision: 20px body padding, 4-char chunks in a labelled card, QR in a rounded white tile, Copy in the footer where every other drawer's primary action lives. Build the chunking as one small component - sketch 154-D needs the same thing, so one widget pays for two sketches. Rejected D · Compact - it un-boxes the one warning standing between a user and a permanent loss of funds.

Buy GNUS - full analysis and redesign

sketch 157

Asked: full redesign of this page - analysis of what is there, what the logic is.

The flow, end to end: Buy GNUS → /buy (order history) → "+ New Order" → /createOrder (the form) → Get Quote → Create Order → /checkout or /checkoutQR → geniuswallet://banxa/callback → OrderDetailsPage (polls). Seven routes, all outside the navbar shell.

Fourteen defects were found. The ones that matter most:

  • 1. The CTA lies - "Buy GNUS" opens the order history (see the callout on page 1).
  • 2. The customer id is a placeholder - fetchOrders('your-cust-id'), hardcoded at two call sites. The list cannot show a real user's orders in any build. "Total Orders: 0" is a stub, not an empty account.
  • 3. Three conflicting status vocabularies. The filter offers six values, the colour switch handles five, the banner handles three. inProgress and expired get no colour; cancelled gets a colour but cannot be filtered.
  • 4. No design tokens at all - raw Colors.green/orange/red/grey. Nothing on this page flips with the appearance.
  • 5. The empty state reads as a failed load - two bare strings over an empty page.
  • 9. Real data thrown away - processingFee, networkFee, transactionHash and walletAddress are all parsed and none are shown. A completed purchase cannot be opened in an explorer although its hash is in hand.
  • 14. KYC is an unlabelled icon with no state - and a fiat purchase can fail on exactly that.

The constraint, and the way through it

CLAUDE.md: "Files under /banxa and /squidrouter are auto-generated. Do not change them." Six of the seven screens live there. Taken literally, no redesign is possible.

They can all be built anyway, because the generated code is layered: models, service and cubits are data; only three files are presentation. New widgets can live under lib/screens/ - where the buy form already lives, outside the fence - subscribe to the same cubits, and the router repoints to them. The generated files stay byte-identical and simply stop being mounted. Zero edits inside the fence. Worth confirming with Braian whether that note is still true or stale.

Recommendation: A · Buy first, plus E · Orders fixed - not rivals. A decides what /buy is; E decides what the history looks like. In value order: (1) repoint /buy, (2) put the Banxa routes inside ShellRoute, (3) fix the customer id - until it is real, no list design can be judged - (4) then the list rebuild. Runner-up D · Stepper beats A if KYC turns out to branch for most users, which is a product fact nobody has yet. Rejected C · Drawer - a purchase with limits, an expiring quote and a third-party handoff does not fit in 420px.

The floating swap button

sketch 158

Asked: change its location - the bottom and right gaps are not equal. Propose a design, and make one where only the outline is the gradient.

The gaps are 20 and 80 - global_swap_fab_host.dart:124-128 is literally right: space10 (20) and bottom: 80. Not a rounding slip: two numbers chosen for two reasons, and one of the reasons does not apply here.

  • The comment says the 80 "clears the 60px bottom nav". That nav is mounted only by MobileOverlay. The desktop app has no bottom bar at all - so 60 of those 80 pixels are avoiding something that is not there.
  • The two glows are offset 6px downward with a 24px blur, so the visible mass hangs ~30px below the box - which does not rescue the gap, and means the glow is clipped on the right at 20px while having 80px of room underneath.

The gradient outline - the one technical fact

A BorderSide takes a single Color. No Flutter border can be a gradient - which is exactly why GWFocusRing was built during Phase 20. A gradient-outline FAB is a gradient-filled circle with an inset circle of surface colour on top. Two consequences, both drawn in the sketch: (a) the hole is a specific surface colour, so the FAB stops being canvas-agnostic - over a card and over the mesh it reads as a disc of the wrong shade; (b) the glyph colour must change, since the brand mint measures ~12:1 on the dark canvas but ~1.6:1 in light mode.

Recommendation - placement: P1 · Equal gutter. Derive the number instead of hardcoding it: space10 + (isDesktop ? 0 : 60) + bottomInset, using the same breakpoint ResponsiveDrawer already uses. Mobile keeps exactly today's 80. Rejected P3 · optically equal - it hardcodes compensation for a shadow offset, so retuning the glow silently un-centres the button.
Recommendation - skin: S1 · Gradient ring, but judge it on the three canvases first. If the hole reads as a hole in a card, S2 · ring + tint is the same idea with the failure removed - take it without a second round. Rejected S3 · glass - a permanent BackdropFilter above the Navigator on every screen.

Found while measuring: the FAB is hidden on /checkout, /checkoutQR, /kyc and /banxa/callback - but not on /buy, /createOrder or /orderDetails. So the swap button floats over the fiat purchase flow. Product question, raised in sketch 157.
