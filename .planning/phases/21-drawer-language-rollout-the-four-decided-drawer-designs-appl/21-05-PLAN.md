<objective>
Finish the Receive pattern and close its file's other drawer.

Measured at HEAD `08f6df5`, `CryptoAddressQR` is **most of the way** to 034-A2
already: the network chip is borderless and above the QR, the QR is a contained
190px black-on-white in both modes, the amber note is `GWWarningNote`, and there
is no Share and no set-default. Two things are outstanding.

**The chunking does not exist.** The file's own docstring claims *"the full
address below as a tappable 4-char-chunked mono block (first/last chunks
emphasized)"*. The code renders `_shortAddress` — `0x1234…5678`, one unbroken run,
middle-truncated. A docstring that describes a design the code does not implement
is worse than a missing feature, because it stops anyone else noticing.

**There are three receive drawers, not two.** D-06 names `coins_screen.dart` and
`token_info_screen.dart`. A third exists at
`lib/components/wallet_information.dart:162` — *"Your {network} address"* — and it
is the only one still wrapping `CryptoAddressQR` in an ad-hoc layout: a
`Container` with `margin: EdgeInsets.only(top: MediaQuery.of(context).size.height * .15)`.
On a short window that pushes the QR below the fold; on a tall one it opens a
150px hole under the header. The other two already pass the widget bare
(`token_info_screen.dart:542-549` records removing exactly this class of wrapper),
so this is the last one.

Purpose: the address a person actually verifies with their eyes, and the third
caller nobody had counted.
Output: real chunking, one wrapper deleted, one title unified, one check.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| wallet address -> screen | The address rendered here is what a user compares against an address held elsewhere before sending funds to it. |
| address -> clipboard | Tapping the block writes to the system clipboard. |
| network name -> QR warning copy | `widget.network` is interpolated into the amber note. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-21-19 | Tampering | truncated address reaching the clipboard | critical | mitigate | Task 1 test 2 asserts the clipboard payload equals the full address, never the displayed form. Sending funds to a truncated address is unrecoverable, and nothing on screen would say it happened. |
| T-21-20 | Spoofing | an address that cannot be eyeball-verified | high | mitigate | The whole change: every character on screen, grouped in fours, ends emphasised. A middle-truncated form hides exactly the region an address-substituting clipboard attack alters. |
| T-21-21 | Denial of Service | QR unscannable in one appearance mode | medium | mitigate | The two `Colors.white` values are constrained to stay. A tokenised QR backing goes dark in dark mode and the code stops resolving on a phone camera — a silent failure with a funds-loss shape. |
| T-21-22 | Information Disclosure | address on screen | low | accept | A receive address is public by construction; publishing it is the panel's purpose. No key material is in scope in either file. |
| T-21-SC | Tampering | npm/pip/cargo installs | high | mitigate | **No package-manager install in this plan.** `qr_flutter` is already a dependency; no version change, no `pubspec.yaml` edit. |

No package-manager installs in this plan. No new dependency.
</threat_model>
