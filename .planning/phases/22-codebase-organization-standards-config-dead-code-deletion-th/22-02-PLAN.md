<objective>
Build the enforcement for the team's hard brace rule: **every `if` gets braces, with the body on
its own line**. No Dart lint can express this — `curly_braces_in_flow_control_structures` is already
enabled via `flutter_lints` and reports **0**, because it explicitly permits omitting braces when the
statement fits on one line with no `else`. All 192 violations in this repo sit inside that carve-out.
`custom_lint` was declined by the user and is in any case retired upstream.

This plan writes the gate only. It does **not** fix any violations — that is 22-04, which needs this
script to exist first in order to measure its own success.

Purpose: make an unenforceable convention mechanically checkable.
Output: `tool/check_brace_style.sh` (a gate with a built-in self-test) and `.editorconfig`.
</objective>

  <files>tool/check_brace_style.sh</files>

  <action>
    Write a bash gate that scans `lib/` and `test/` for `if` statements that break the rule, prints
    each offender as `path:line: <source line>`, and exits 1 if any are found, 0 otherwise.

    **The rule being enforced.** An `if` is compliant when the condition's closing parenthesis is
    immediately followed (same line, whitespace permitted) by `{` and nothing else on that line.
    Two violation classes:
      - **Class A — collapsed one-liner:** anything other than `{` follows the closing paren on the
        same line. This includes the fully-braced-but-collapsed form, which is explicitly NOT
        acceptable per the rule.
      - **Class B — braceless multi-line:** nothing follows the closing paren, and the next
        non-blank line does not begin with `{`.

    **Matching must be paren-aware, not regex-greedy.** `if (a && (b || c))` and `if (a) doThing(x);`
    are distinguished only by counting parentheses. Use `awk` with a depth counter that starts at the
    `if (` token and walks forward to the matching `)`. A `sed`/`grep` pattern that grabs the last
    `)` on the line will misjudge both of those cases — do not use one.

    **Strip before matching.** Remove `//` line comments, `/* */` block comments, and the contents of
    single- and double-quoted string literals before scanning, so a rule example inside a doc comment
    or an `if (` inside a string cannot trip the gate. Preserve line numbering while stripping
    (blank the content, do not delete the line) so reported line numbers stay accurate.

    **Do not flag** `else if` chains where the `if` itself is braced correctly, ternaries, collection
    `if` inside list/map literals (Dart's `[if (x) a, b]` form — the rule is about statements), or
    anything under an excluded path.

    **Excluded paths:** the same set the analyzer excludes plus generated code — `banxa/`,
    `squidrouter/`, `packages/genius_api/lib/ffi/`, `packages/genius_api/lib/proto/`, and any
    `*.freezed.dart`. Do **not** blanket-exclude `*.g.dart` by pattern: 9 files under
    `lib/components/` carry that suffix but are hand-written production widgets, and 22-03 renames
    them. Exclude generated files by their real location (`lib/hive/models/`, `lib/hive_registrar`,
    `lib/tokeninfo/token_model`) or by detecting the generated-code header, and leave a
    `ponytail:` comment noting the exclusion narrows automatically once 22-03 lands.

    Support a `--count` flag that prints only the integer violation count, so later plans and CI can
    gate on a number without parsing the offender list.

    Make the file executable (`chmod +x`), matching the three existing gates.
  </action>

  <verify>
    <automated>bash tool/check_brace_style.sh --count</automated>
  </verify>

<task type="auto">
  <name>Task 2: Prove the gate can fail — built-in self-test</name>

  <read_first>
    - `tool/check_brace_style.sh` as written in Task 1
    - `AGENTS.md` § "Dart coding standards" — the legal and illegal forms, which are the fixture cases
  </read_first>

  <files>tool/check_brace_style.sh</files>

  <action>
    A gate that has never failed is not a gate — it is an assumption. Add a `--self-test` mode to the
    same script (one file, not a second one: the test ships with the thing it tests).

    `--self-test` writes a temporary Dart file to a temp directory, runs the scanner over it, and
    asserts the verdict per case. It must cover, at minimum:

    *Must be flagged:*
      1. Collapsed one-liner with braces, body on the same line as the condition.
      2. Braceless, body on the following line.
      3. Braceless with a nested-paren condition, to prove the paren counter works.
      4. A compliant `if` followed later in the same file by a violating one — proves the scanner
         does not stop at the first compliant match.

    *Must NOT be flagged:*
      5. The compliant form: `{` on the condition line, body on its own line, `}` on its own line.
      6. An `else if` chain where every branch is compliant.
      7. A violating-looking `if` that sits inside a `//` comment.
      8. A violating-looking `if` that sits inside a string literal.
      9. A collection-`if` inside a list literal.

    The mode prints one line per case (`PASS`/`FAIL` with the case name), exits 0 only if every case
    behaves as asserted, and cleans up its temp directory on exit including on failure (`trap`).

    Cases 7, 8 and 9 are the ones that matter most: they are where a naive implementation produces
    false positives, and a gate that cries wolf gets disabled by the team within a week.
  </action>

  <verify>
    <automated>bash tool/check_brace_style.sh --self-test</automated>
  </verify>

  <acceptance_criteria>
    - `bash tool/check_brace_style.sh --self-test` exits 0 and prints a PASS line for all 9 cases.
    - Deliberately breaking the scanner (e.g. temporarily inverting its comparison) makes
      `--self-test` exit non-zero — demonstrate this once during execution and quote the output in
      the SUMMARY. Restore the script afterwards.
    - The temp directory is removed after both a passing and a failing run.
  </acceptance_criteria>
</task>

  <action>
    Add a minimal `.editorconfig` at the repo root. Keep it small: `dart format` already owns every
    whitespace decision inside `.dart` files, so the value here is for the file types the formatter
    does not touch — YAML, shell, Markdown — and for making a fresh editor agree with the repo
    before the formatter runs.

    Contents: `root = true`; a `[*]` section with UTF-8 charset, LF line endings, final newline,
    trailing-whitespace trim, and 2-space indent; a `[*.dart]` section whose `max_line_length`
    matches `analysis_options.yaml`'s configured formatter page width (currently 80) so an editor
    guide and the formatter do not disagree; a `[*.md]` section that disables trailing-whitespace
    trim (two trailing spaces are a hard line break in Markdown); a `[*.sh]` section pinning LF
    (a CRLF shebang line makes a script unrunnable on the Linux CI runner).

    Do not add per-language rules for languages this repo does not contain. Do not add an
    `[*.{yml,yaml}]` section unless it differs from `[*]` — it does not.
  </action>
