<objective>
Collapse three families of duplicated UI into shared widgets. Measured call sites on 2026-07-28:
hover wrappers **9**, percentage-change pills **7**, timeframe selector **2 (named exception)**.

Two rules govern and neither is negotiable. **Rule of Three:** two occurrences do not justify a
shared component, three do — duplication is cheaper than the wrong abstraction. **Widgets, not
helper methods:** extract to a real `StatelessWidget`, never a `_buildFoo()` returning a `Widget`. A
helper forces the whole enclosing widget to rebuild, cannot be `const`, disposes nothing, is
invisible to the DevTools inspector, and produces worse error messages. This is the single
highest-value mechanical rule of the extraction pass.

The theme work landed first deliberately, so these components are born reading `context.gw` rather
than needing a second migration pass.

Purpose: three shared widgets replacing eighteen hand-rolled instances.
Output: three new components, each goldened in both modes before any call site moves.
</objective>

  <action>
    Nine sites hand-roll the same hover pattern: a `MouseRegion` plus a `setState` boolean plus some
    visual response. Note up front that the `setState` in these is **correct usage** — state needed
    by exactly one widget belongs in `setState`, and this repo's audit confirmed hover/press state is
    the legitimate case. Do not convert it to a cubit; that is not what this is.

    Extract `GWHoverable`. Because it owns hover state, it is a `StatefulWidget` internally — the
    "StatelessWidget, not a helper method" rule is about not using `_buildFoo()`, and a widget that
    genuinely holds state is a `StatefulWidget`. What matters is that it is a real widget class with
    its own element, not a method on someone else's.

    Shape it as a builder taking the hover flag, so callers keep full control of their visual
    response rather than the component guessing. Add the cursor as a parameter only if the call sites
    actually differ on it. If eight of nine want the same response and one differs, leave that one
    alone rather than adding a flag for it — an outlier is cheaper as duplication.

    Migrate the nine sites, deleting each site's now-dead `bool _hovered` field and its `setState`
    calls. A site that still declares hover state after migrating did not actually migrate.

    Add a golden scenario for the component in both modes — at minimum resting and hovered. Existing
    goldens must stay byte-identical: this is a refactor and nothing should repaint.
  </action>

  <action>
    Seven sites render a "+2.4%" style pill. Duplication here is not merely repetitive — it means the
    zero case, the sign, and the rounding can each be handled differently on different screens, which
    is a correctness problem in a wallet, not a style one.

    Before writing the component, tabulate the seven. Where they disagree — and they will — decide
    the single correct behaviour and state it in the SUMMARY as a deliberate normalisation, with what
    each site did before. Rounding and sign display are user-visible: if normalising changes what any
    screen displays, that is a behaviour change and it must be called out explicitly, not absorbed.
    If a site's difference is genuinely intentional (a different precision because the underlying
    quantity differs), keep it as a parameter with a documented default, not a boolean.

    `GWChangePill` takes the change value and derives everything: sign, formatting, and the
    positive/negative/zero colour from the semantic status tokens. It must **not** take a colour
    parameter — the whole point is that "green means up" is decided once.

    Handle the null and zero cases explicitly. A missing value must render as absent, never as
    "0.00%" — this repo has an established rule from the swap work that a value with no data is
    omitted rather than zeroed, because a fabricated zero reads as real.

    Golden it in both modes covering positive, negative, zero, and null.
  </action>
