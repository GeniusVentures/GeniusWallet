<objective>
Finish the colour consolidation: close the primitive layer so nothing outside `lib/theme/` can reach
the raw palette, tokenize the two remaining raw-value families (the monospace font family, reached by
string literal from nine files, and the hardcoded gradient stops in `GWDecorations`), and land the
CI gate that keeps it that way.

The locked decision is explicit: **do not delete the legacy palette class** — demote it. It is the
primitive layer in the Material 3 primitive → semantic → component model, and the value of that
split is lost the moment a screen can import the raw palette.

Purpose: one way to read a colour, enforced.
Output: genuinely-private primitives, a mono type token, de-hexed decorations, and a scoped
raw-colour gate wired into CI.
</objective>

  <action>
    Dart has no package-private visibility, so "private to the theme layer" cannot be a naming
    convention — a convention is exactly what got the repo here. Use the language:

    Make `gw_colors.dart` the library and `genius_wallet_colors.dart` a `part` of it. The raw values
    then become genuinely private: prefix them with `_` and the compiler makes them unreachable from
    any other library. A `part` file carries no imports of its own, so move
    `genius_wallet_colors.dart`'s imports up into `gw_colors.dart`.

    Sequence it so the tree compiles at every step:
      1. Confirm the only remaining references to the legacy public members are inside `lib/theme/`
         plus whatever `22-11-SUMMARY.md` recorded as a deliberate survivor. If anything else shows
         up, migrate it first — do not proceed with an outstanding consumer.
      2. Convert the file to a `part`, moving imports.
      3. Rename the public members to `_`-prefixed and update the `lib/theme/`-internal consumers
         (`theme.dart`, `GWDecorations`, `nav_chip_style.dart`, and `GWColors`' own factories).
      4. Delete any member that now has zero references. A private member nobody reads is dead code,
         and this is the first moment the compiler can prove it.

    **Do not delete the class.** Do not flatten the file into `gw_colors.dart`. It is the primitive
    layer and it carries the measured contrast rationale for many values; the split is the point.

    **Preserve every doc comment**, including measured contrast ratios and `ponytail:` notes. They
    are the record of why a value is what it is.

    For any deliberate survivor outside `lib/theme/` that genuinely cannot take a `BuildContext`,
    expose exactly the field it needs through `GWColors` or a narrow named accessor. Do not re-open
    the whole palette for one consumer.

    If `GWAppearance.isLight` is still read by the primitive getters, that is fine and unchanged —
    the primitives are allowed to know about appearance. What changes is that nobody outside the
    library can call them.
  </action>

    No off-the-shelf lint can ban hardcoded colours — this was checked against the Dart linter, DCM's

    v0.1.3 with an unverified uploader and is not adoptable). A CI grep gate is the practical answer,
    the same conclusion the brace rule reached.

    Write `tool/check_raw_colors.sh`, matching `check_brace_style.sh`'s conventions exactly:
      - Flags a raw `Colors.<name>` or `Color(0x…)` occurrence in a covered directory.
      - Strips comments and string literals before matching, so a hex in a doc comment or a URL
        cannot trip it.
      - Permits `Colors.transparent` (it is appearance-neutral by definition).
      - Permits any line carrying an explicit inline exemption marker, so the documented
        always-one-mode cases (white text on a fixed dark scrim) can stay and stay visible. The
        marker must name the reason; a bare marker is not an exemption.
      - Never covers `lib/theme/` — that is where colours are allowed to be literal.
      - Supports `--count` and `--self-test`, with the self-test proving both that it fires on an
        injected raw colour and that it does **not** fire on a comment, a string, a transparent, or
        an exempted line.

    to exactly those at zero. Landing a repo-wide gate now would block its own migration — that is

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| theme layer -> application code | The primitive layer must be unreachable from screens, or the semantic layer is advisory |
| CI gate -> merge | A raw-colour gate scoped too narrowly gives false assurance; scoped too widely it gets disabled |
| font family string -> secret display | Seed phrases and addresses render in the monospace family; a silent fallback to a proportional font changes how a user verifies what they are looking at |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-22-49 | Tampering | primitive layer reachable by convention only | high | mitigate | `part`/`part of` plus `_`-prefixing makes the compiler the enforcement, not a naming rule. |
| T-22-50 | Spoofing | narrowly-scoped gate read as full coverage | medium | mitigate | `22-12-GATE-SCOPE.md` states covered vs uncovered with per-directory counts, and explicitly names the full de-hex as larger than this phase. |
| T-22-51 | Spoofing | gate that never fails | high | mitigate | `--self-test` plus a one-off injected-violation demonstration, matching the standard 22-02 set for the brace gate. |
| T-22-52 | Information Disclosure | seed phrase rendered in a fallback proportional font | medium | mitigate | Single-token family name removes the nine string literals that could each typo independently. |
| T-22-53 | Repudiation | doc comments carrying WCAG rationale lost during the demotion | medium | mitigate | Comment preservation is an explicit acceptance criterion; those comments are why several values are not "simplified" back into failures. |
</threat_model>
