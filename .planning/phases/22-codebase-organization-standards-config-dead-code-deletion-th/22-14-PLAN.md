    Extract `GWCopyRow`: a label, a value, a copy affordance, and confirmation feedback. It owns
    exactly four decisions that are currently made eleven times:

      1. **How the value is displayed** — truncation for long values (addresses, hashes) with the
         middle elided, so the beginning and end stay verifiable. Take the truncation as a parameter
         only if the sites genuinely differ; otherwise decide it once.
      2. **What is written to the clipboard** — always the *full* value, never the truncated display
         form. Get this wrong and a user pastes a corrupt address. Assert it in the test.
      3. **The confirmation** — one consistent affordance and duration.
      4. **That nothing is logged.** No `print`, no `debugPrint`, no analytics event, no Sentry
         breadcrumb carrying the copied value or anything derived from it. Not even its length.

    Tabulate the eleven sites' current behaviour before writing the component, and declare any
    normalisation that changes what a user sees.

    **The recovery-phrase screens are a deliberate exception to consider, not to assume.** Read what
    they do today. If a screen currently offers no clipboard copy for seed material, `GWCopyRow`
    must not add one — that would be new capability and a security decision nobody made. If it does
    offer one, migrate it but keep its existing warnings and confirmations exactly, and state in the
    SUMMARY that this surface copies seed material so a reviewer sees it explicitly.

    Write `test/components/gw_copy_row_test.dart` covering: the clipboard receives the full value
    even when the display is truncated; the confirmation appears and then clears; and — the one that
    matters — that no log output is produced during a copy. Use the platform channel mock for
    clipboard rather than a real write.

    Golden it in both modes: short value, long/truncated value, and the confirmation state.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app -> system clipboard | The clipboard is readable by other applications; what is written and when is a security decision |
| copied value -> logs/telemetry | A logged address or seed fragment leaves the process boundary permanently |
| navigation -> unsaved state | A shared back affordance that drops a custom pop guard can discard user input or exit a flow mid-transaction |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-22-59 | Information Disclosure | copied value reaching a log, print or telemetry sink | critical | mitigate | The component logs nothing, a test asserts no log output during a copy, and `tool/check_no_new_key_logging.sh` is an acceptance criterion. Per AGENTS.md this is not a style preference. |
| T-22-60 | Tampering | truncated display value written to the clipboard | critical | mitigate | The full value is always what is copied; asserted by a test using a mocked platform channel, not by inspection. A truncated address pasted into a send field is unrecoverable loss. |
| T-22-61 | Elevation of Privilege | adding a clipboard affordance to a seed-phrase surface that lacked one | high | mitigate | Explicitly forbidden: no surface gains a copy affordance it did not already have. Recovery-phrase screens are read and reported separately. |
| T-22-62 | Tampering | shared app bar dropping a custom pop guard | high | mitigate | Back behaviour preservation is an acceptance criterion at every migrated site, plus a live navigation check on three screens. |
| T-22-63 | Spoofing | outliers forced into the shared app bar | medium | mitigate | All 17 sites classified in writing; only the identical subset migrates; boolean-flag reconciliation is a stop-signal. |
</threat_model>
