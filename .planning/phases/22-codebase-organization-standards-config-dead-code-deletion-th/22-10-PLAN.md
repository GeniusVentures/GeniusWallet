<objective>
Move the app's ~288 colour reads from the static palette class onto the semantic accessor built in
22-09. The parity layer means each rewrite is a prefix change and nothing else — the value read is
identical by construction and proven so by 22-09's parity test.

The locked decision is to do this with `Workiva/dart_codemod` (AST-based via `package:analyzer`),
not with regex. A regex over 288 sites in ~80 files will eventually match inside a string, a doc
comment, or a longer identifier, and the failure will be silent.

Purpose: leave exactly one way to read a colour.
Output: a reusable codemod script, the bulk of the call sites migrated, and a residue list for 22-11.
</objective>

  <action>
    Add the approved package to `dev_dependencies` (or skip if the human chose the direct-analyzer
    fallback) and write `tool/codemod_colors.dart`.

    The suggestor walks the **unresolved** AST — type resolution is not needed for a static-member
    access rewrite, and unresolved suggestors are dramatically faster and need no
    `PackageContextForTest` setup. Rewrite only `PrefixedIdentifier` / `PropertyAccess` nodes whose
    prefix is the legacy palette class identifier and whose property name appears in the token map.
    Because it matches AST nodes, an occurrence inside a string literal, a comment, or a longer
    identifier cannot match. That is the whole reason for using it.

    **Hard refusals — the codemod must skip and report, never rewrite:**
      - Any occurrence inside a `const` expression or a `const` constructor invocation.
        `context.gw.x` is a runtime read; substituting it there produces "invalid constant value".
        22-05 deliberately added `const` constructors that may sit on exactly these sites.
      - Any occurrence in a context with no `BuildContext` in scope: static fields, top-level
        variables, `initState`-adjacent field initialisers, and any class that is not a widget
        (controllers, painters, models). Research names this explicitly as where the migration
        breaks.
      - Anything inside `lib/theme/` itself. That is the token layer; it reads the primitives
        directly and must keep doing so.

    Emit a machine-readable refusal report (path, line, symbol, reason). That report is the input to
    Task 3's residue document, so make it complete rather than pretty.

    Run it in dry-run mode across `lib/` first and read the report before applying anything. If the
    refusal count is very large — say more than about a third of the 288 — stop and say so in the
    SUMMARY before proceeding: that changes the shape of 22-11 and the user should know before the
    diff lands, not after.
  </action>
