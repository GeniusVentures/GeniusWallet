  <files>.github/workflows/build.yml</files>

  <action>
    Add ONE new job named `quality` to the existing `jobs:` block. Do not create a second workflow
    file — this repo has one workflow and the gates belong beside the build they gate.

    Shape:
      - `runs-on: ubuntu-latest`. No container image, no self-hosted runner, no Android SDK, no
        CMake, no Apple certificates. None of these gates need the native toolchain, and attaching
        them to the heavy matrix would mean waiting for a five-platform build to learn that a file
        is misformatted.
      - `actions/checkout` pinned to the same SHA the `build` job uses. Request `submodules:
        recursive` only if a gate actually needs submodule content — read
        `verify_additive_boundary.sh` first; if it only walks `lib/`, skip submodules and save
        several minutes per run.
      - `subosito/flutter-action` pinned to the **same SHA and the same `flutter-version`** as the
        `build` job. Two SDK versions in one workflow is how "green on CI, red locally" starts.
      - `flutter pub get`.
      - Then the gates, cheapest and most specific first so a failure names itself:
        1. `dart format --output=none --set-exit-if-changed lib test`
        2. `flutter analyze lib test`
        3. `bash tool/check_brace_style.sh`
        4. `bash tool/check_no_new_key_logging.sh`
        5. `bash tool/check_onboarding_seed_safety.sh`
        6. `bash tool/verify_additive_boundary.sh`
        7. `flutter test --coverage --report-on lib`

    Give every step an explicit `name:` stating what it enforces — the step name is what a developer
    reads on a failed check.

    Pass no analyzer flags. `flutter analyze` already treats infos and warnings as fatal by default
    (`fatal-infos` and `fatal-warnings` both default to true in flutter_tools), which is the opposite
    of `dart analyze`. **Do not add `--no-fatal-infos`**: it was explicitly rejected because it still
    treats `@Deprecated` as fatal (flutter#154922) while hiding everything else — the worst of both,
    and directly in conflict with the deprecation-based migration path this project plans to use.

    Do **not** add `continue-on-error` or any allowance that lets a gate fail without failing the
    job. A gate that cannot fail the build is decoration — the same reasoning that made 22-02's
    self-test mandatory.

    Leave the existing `build` job completely untouched.
  </action>

  <action>
    Two things can make this job red on its first run, and both are environmental rather than code
    defects. Find out which apply by running it, not by reasoning about it.

    **1. SDK version skew.** The analyzer's diagnostic set changes between Flutter releases. Analyze
    is 0 on the local SDK; it may not be 0 on the pinned CI version. Trigger the job (via
    `workflow_dispatch`, or a branch push — note that a PR touching only `.github/**` will not fire
    it, because of the existing `paths-ignore`). Read the actual output.

    If analyze is non-zero on CI:
      - Fix the reported issues if they are real. That is the preferred outcome.
      - If they are diagnostics that only exist in one SDK version, align the versions: prefer
        bumping the workflow's pin to the SDK the team develops on, since a CI that analyzes an
        SDK nobody uses locally produces findings nobody can reproduce. Record the decision.
      - Do **not** suppress with a flag, an ignore comment, or an exclude.

    **2. Native dependency of the test suite.** `packages/genius_api` contains FFI bindings. If any
    test causes a `DynamicLibrary` load, `flutter test` will fail on a runner that has not built the
    native artifacts. Run it and see.

    If the test step fails for that reason and only that reason, the fallback is explicit: move the
    `flutter test --coverage` step out of `quality` and into the existing `build` job, immediately
    after its `Build Flutter` step, gated to one platform (Linux x64) so it runs once rather than
    five times. Keep format, analyze, the brace gate and the three security gates in the fast
    `quality` job regardless — none of them need native artifacts. Record which shape was chosen and
    the evidence for it.

    **Optional, evaluate locally first — randomized test ordering.** Research recommends
    `--test-randomize-ordering-seed random` because it catches inter-test state leakage. This suite
    has never run randomized. Try it locally first. If it is green, add it to the CI step. If it
    surfaces failures, do **not** add it and do **not** fix the leakage here — that is behaviour
    work and belongs in Phase 23. Record the finding with the seed that reproduced it.
  </action>

    Add `codecov.yml` at the repo root encoding the locked policy: `project` status at target `auto`
    with a small threshold (no regression on overall coverage), and `patch` status at target 80%
    (new code must be tested).

    This shape, not Very Good Ventures' 100%, is deliberate: a 100% gate on an existing 40k-LOC app
    is a big-bang backfill, and the phase's job is to stop the bleeding, not to retro-test the whole
    application. Record that reasoning in a comment at the top of the file so nobody "fixes" it later.

    Add the coverage upload step after the `flutter test --coverage --report-on lib` step. Pin the
    upload action to a full commit SHA, never a floating tag — a mutable third-party action in CI
    is a supply-chain hole, and this repo already pins its other actions by SHA. Follow that
    existing convention rather than introducing a second one.

    Guard the upload so a missing `CODECOV_TOKEN` skips it with a message instead of failing the
    build. Forks and first-run branches will not have the secret, and a hard failure there teaches
    the team to ignore red checks.

    `--report-on lib` is already on the test command and matters: it measures coverage of source,
    not of the test files themselves, which otherwise inflate the number.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| third-party GitHub Action -> CI runner | Any action runs arbitrary code with access to the workflow's secrets |
| repository secret -> workflow | `CODECOV_TOKEN` is exposed to whatever step references it, including on PRs from forks if misconfigured |
| CI verdict -> merge | The gates are the boundary between broken code and the default branch |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-22-30 | Tampering | coverage upload action | high | mitigate | Pin the action to a full commit SHA, matching the existing convention in this workflow (checkout and flutter-action are already SHA-pinned). Never a floating tag. |
| T-22-31 | Information Disclosure | `CODECOV_TOKEN` in a fork PR | high | mitigate | Reference the secret only in the upload step and skip that step when the secret is absent; do not expose it to any step that runs untrusted PR code. |
| T-22-32 | Spoofing | a gate that cannot fail | high | mitigate | `continue-on-error` is banned by acceptance criterion, and Task 2 requires observing a real CI run rather than inferring success from local results. |
| T-22-33 | Denial of Service | quality job blocked by missing native artifacts | medium | mitigate | Task 2 names the explicit fallback (relocate only the test step to the `build` job) rather than the tempting one (drop the test step or mark it non-blocking). |
| T-22-34 | Repudiation | "green locally" standing in for "green on CI" | medium | mitigate | Acceptance requires quoting the real GitHub run result. |
</threat_model>
