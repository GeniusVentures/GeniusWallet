## D-1 Ordering a holding with a balance but no market data

**Rule, stated as a total order.** A row is an **unpriced holding** when `balance > 0` AND no market
data resolves for its symbol (or the resolved `currentPrice` is 0). Everything else has a
well-defined `value = balance * price`, which is 0 when either factor is 0.

Descending (the default):

1. every unpriced holding, above every priced row
2. within the unpriced block: larger balance first
3. within the priced block: larger value first
4. tie-break: GNUS first
5. tie-break: symbol A to Z, case-insensitive

Ascending is the **exact mirror of steps 1 to 3**: priced rows by value ascending (so the `$0.00` rows
lead), then the unpriced block LAST, ordered by smaller balance first.

Steps 4 and 5 are **direction-independent on purpose.** Flipping the direction should flip the
ranking, not scramble rows that rank equally. Two consequences, both wanted and both tested:

- In a wallet where every balance is zero, every priced row ties at value 0, so the list is GNUS then
  alphabetical, and **tapping the toggle changes the arrow but not the order.** That is correct -
  nothing has value to rank - and it is on the on-device check list so it is not mistaken for a dead
  button.
- Steps 4 and 5 make the comparator total, which matters because `List.sort` in Dart is NOT stable
  (`coins_screen.dart:238` documents this exact trap). Without a total comparator the zero-balance
  wallet would reorder itself between rebuilds.

Why the unpriced block goes on top when descending: "you own this and we cannot price it" outranks any
priced row - it is the one row on the page that needs the user's attention. That is the proposal on
file in the sketch README and in BRIEF.md, taken as-is.

Why ascending mirrors rather than pinning: if the block stayed glued to the top in both directions,
tapping the toggle would leave the top of the list unchanged and the control would read as broken.

**Agreement with 25-01 is by construction, not by coincidence.** The comparator ships in
`lib/dashboard/assets/assets_sort.dart` as a pure function so 25-01's dashboard top-5 can call the
identical code. 25-01's spec (BRIEF.md Target table) is "top 5 by holding value in USD, descending",
which under this rule is exactly `sorted.take(5)`. If 25-01 rolled its own ordering instead, the fix
after both land is a one-line swap to `compareAssetsByValue`, and the disagreement is visible on
device - the phase walk names it as check **W-7**.

## D-2 The empty wallet, and every other state

Five states, and the two that matter are genuinely different from each other. Jakub's real wallet
holds every balance at zero, so a page that only looks right when full looks broken most of the time.

| # | Condition | Search + sort | Body |
|---|---|---|---|
| S1 | `coinsStatus == loading` AND `coins.isEmpty` | hidden | `Loading()`, centred |
| S2 | `coinsStatus == error` AND `coins.isEmpty` | hidden | `GWErrorState(message: 'Failed to load your assets.', onRetry: getCoins)` |
| S3 | `coins.isEmpty` | hidden | `GWEmptyState(icon: account_balance_wallet_outlined, title: 'No coins yet', message: 'Your holdings will appear here once you receive a token.')` plus the Receive / Buy GNUS pair |
| S4 | coins present, query matches none | **shown** | `GWEmptyState(icon: search_off, title: 'No assets found', message: 'Nothing matches that search. Clear it to see all your assets.')`, no CTA |
| S5 | coins present, at least one match | **shown** | the rows |

The load and error branches are gated on `coins.isEmpty` so a refresh over an already-populated list
never blanks the page.

**S3 vs S4 is the distinction the prompt asks for, and it is structural, not just copy.** S3 has
nothing to search, so the controls are not mounted at all - a search box over an empty wallet is a
control that can only ever fail. S4 keeps both controls mounted, because the query is the reason the
list is empty and the user needs the field to edit or clear it. S4 offers no CTA: the user is not out
of assets, they are out of matches, and a Buy button would be answering a question nobody asked.

**S3 carries the Receive / Buy GNUS pair** because sketch 177's variant D renders it and because
`coins_screen.dart:353-389` already shows exactly this pair when total value is 0 - same
`GWButton(gradientOutline)` + `GWButton(gradient)` recipe, one filled gradient on the surface, which
is what the CTA weight rule allows. Receive opens the same `ResponsiveDrawer` + `CryptoAddressQR`
drawer. That is a duplication of `coins_screen.dart`'s `_showReceive`; it cannot be extracted because
that file is fenced. `ponytail:` note it at the call site with the upgrade path (promote to a shared
`showReceiveDrawer(context, state)` after 25-01 lands).

**The all-zero wallet is NOT an empty state.** It is S5: eight real rows, every one reading `$0.00`,
ordered GNUS then alphabetically per D-1. `CoinCardRow` already paints a zero balance at
`textPrimary80` (12.4:1) rather than the old `textPrimary38` (3.54:1) precisely so this state reads as
a wallet with no funds and not as a broken wallet. Do not dim it further.

**The total.** `GWPageHeader.trailing` carries it: `assetsTotal(...)` currency-formatted at 20px w700,
with the `+/-$x - +/-y%` 24h line only when total > 0. This is byte-for-byte the trailing block
`coins_screen.dart:288-311` builds for the dashboard. Deviation from the sketch, stated: variant D
draws a 40px hero total in its own block under the header. On a 390pt phone that is a second title-
sized element before the first row, the app already renders this exact total-in-a-header pairing on
Home, and a hero total is variant E's idea - E was not chosen. Header trailing costs zero vertical
space and keeps the two surfaces consistent.

## D-3 Search and sort reset on every visit. Nothing is persisted.

Both live in the page's `State` and are born at their defaults each time the route mounts: query
empty, direction descending.

- Nothing outside this page needs to read them, so persisting means inventing global state (a Hive
  box or a cubit field) that nobody asked for.
- Default descending IS the answer to "what do I hold", which is the reason the page exists. Landing
  on a page still filtered by a query typed days ago is the classic stale-filter defect.
- Sketch 177's D holds `st.q` and `st.sort` in a per-phone object created on mount. Per-visit is what
  was chosen.

Two things that must still hold **within** a visit, and both are free once the state lives in `State`
rather than in a `build` local: the query and direction survive a rebuild (keyboard opening, market
data arriving, an appearance toggle), and they survive a round trip to `/token-info` and back, because
the route is still on the navigator stack and its `State` is never disposed.

## D-4 The sort affordance: where it sits, and how its two states are told apart

**Placement.** One control row directly under the search field and directly above the list, which is
the sketch's `.sortbar`. It is a single `GWKicker`:

```
GWKicker('<n> assets', dense: true, trailing: <the sort toggle>)
```

`GWKicker.trailing` is documented as "a right-aligned companion (a count, a chevron)", so this is the
slot's intended use rather than a stretch of it. The label reads `8 ASSETS`, or `3 OF 8 ASSETS` while
a query is active. Pass it lower-case - `GWKicker` upper-cases it itself and its doc forbids callers
pre-calling `toUpperCase()`.

**The control.** Label `VALUE` in `GWKicker.style(gw, dense: true)` at `gw.textSecondary`, plus a
direction arrow. Descending shows `↓`, ascending shows `↑`, as text arrows in the same Row - the same
glyphs `markets_table.dart:145-153` already uses, so the app carries one sort-arrow vocabulary.

The sketch draws `⇅`. That is a sortABLE hint, not a state: it shows both directions at once and so
says nothing about which one is active. The shipped control shows the CURRENT direction, because that
is the fact the user needs to read.

**How the two states are told apart, in three independent channels:**

1. **Shape.** `↓` vs `↑`. A shape difference, not a colour difference, so it survives colour
   blindness and satisfies WCAG 1.4.1 without a second cue.
2. **Contrast.** The arrow is painted at `gw.textPrimary`, the loudest ink the app has, because the
   arrow IS the state indicator and a state indicator should be the loudest thing in its control.
3. **Semantics.** The whole control is wrapped in
   `Semantics(button: true, label: 'Sort by value, highest first' | 'Sort by value, lowest first')`.
   Not decoration: a glyph-only direction is invisible to VoiceOver, and Jakub reviews on an iPhone.

**Contrast, measured against the real tokens in `genius_wallet_colors.dart`, not assumed.**
Dark canvas is `surfaceBase` `#0B0D12` (relative luminance 0.00403). If the control ends up over
`surfaceElevated` `#0C0E14` (0.00443) instead, every figure moves by under 0.05.

| Element | Token | Hex | vs `surfaceBase` | Requirement | Verdict |
|---|---|---|---|---|---|
| Arrow (the state indicator) | `textPrimary` | `#FFFFFF` | **19.4:1** | 1.4.11 wants 3:1 | passes with 6.5x headroom |
| Label `VALUE` | `textSecondary` | `#8A8F9D` | **6.01:1** | 1.4.3 wants 4.5:1 (it is text) | passes |
| Ink of the count kicker | `textSecondary` | `#8A8F9D` | **6.01:1** | 4.5:1 | passes |

The 6.01:1 figure is the same number `coin_card_row.dart:145-147` already records for this token on
this canvas, so the arithmetic is corroborated by the codebase and not only by this plan.

**Rejected alternatives, with the numbers that rejected them:**

- **Runner-up: a gradient arrow via `GeniusWalletGradient.brandCtaText(gw.surfaceBase)`.** Light-safe
  by construction (the helper collapses to `brandPrimaryOnSurface` `#0A6885`, 5.61:1, on a light
  canvas) and it is what `markets_table` speaks. Rejected only because in `markets_table` the gradient
  means "THIS is the active key" - it distinguishes one header from six inactive ones. Here there is
  exactly one key, permanently active, so the gradient would carry no information and would spend the
  brand accent on a control that is never off. Adopt it the day a second sort key arrives.
- **Rejected: raw `GeniusWalletGradient.brandCta` as the arrow shader**, which is what
  `markets_table.dart:146` does. On dark its stops measure 10.5:1 and 7.5:1 against `surfaceBase` -
  fine. On the light canvas `#DCE0E6` the same stops measure **1.40:1 and 1.95:1**, i.e. invisible.
  `genius_wallet_gradient.dart:38-42` already records the equivalent failure on the light menu surface
  (1.65:1 and 2.28:1) and is the reason `brandCtaText` exists. `markets_table`'s raw use is
  pre-existing light-mode debt; this plan declines to add a second instance of it. Logged as a named
  item for the light pass, not fixed here (dark mode first).
- Note that `textPrimary` is the only one of the three that passes in **both** themes: on the light
  canvas `#DCE0E6` the light ink `#10131A` measures **14.0:1**. Choosing it means this control needs
  nothing from the light pass.

**Tap target.** The toggle's hit area is at least **48x48** logical pixels - Material's own minimum,
which the app already relies on for `GWTextField`'s `leadingIcon` gutter (its doc names the 48x48
box). `GWKicker`'s dense line box is 16pt tall, so the label alone is nowhere near it: wrap the
tappable child in `ConstrainedBox(constraints: BoxConstraints(minWidth: 48, minHeight: 48))` with the
content centred. 48 is on the 4-pt grid; it is a target size rather than a spacing value, so it takes
a named local constant with this comment and not a `space*` token.

**Hover** (macOS / desktop builds only; iOS is the review surface): `InkWell` with
`borderRadius: BorderRadius.circular(6)`, matching `markets_table`'s own sort header. The element must
not change size under the cursor - `gw_back_link.dart`'s doc states that rule for interactive chrome.

## D-5 Fresh market data with no second refresh timer

Accepted cost 1 says the page assembles its own list because `CoinsScreen` exposes no ordering hook
and owns a 1-minute periodic refresh that must not be duplicated. So:

**This page starts no periodic refresh at all.** Freshness comes from four places instead:

1. **One fetch when coins arrive.** A `BlocListener<WalletDetailsCubit, WalletDetailsState>` that
   calls `getCoins()` when `coinsStatus == initial && selectedNetwork != null`, and resolves market
   data when `coinsStatus == successful`, guarded by an `_isFetching` bool exactly as
   `coins_screen.dart:83-86` guards its own.
2. **The Hive cache does the rest.** `fetchCoinsMarketData` is backed by a 3-minute Hive cache shared
   process-wide (`coin_gecko_api.dart:14, 107-141`), so whichever surface fetches first refreshes
   both, and a mount fetch usually costs zero network calls.
3. **An explicit `RefreshIndicator`**, the same pull-to-refresh gesture `/transactions` already
   offers. A deliberate user gesture beats a hidden timer.
4. **Whichever surface is alive keeps its own cadence.** If 25-01 navigates with `context.push`, the
   dashboard stays mounted and its 1-minute timer keeps running and keeps the shared cache warm. If
   it uses `context.go`, the dashboard unmounts and its timer is disposed. Either way there is exactly
   one timer in the process, and it is never this page's.

**The page must never write wallet balance back into the cubit.** `CoinsScreenState._fetchMarketData`
ends by calling `_calculateTotalValue`, which writes the total into `WalletDetailsCubit`. An executor
copying that method wholesale will bring that call along and create two competing writers for one
piece of state. The page is READ-ONLY with respect to the cubit, with exactly one exception:
`selectCoin(coin)` on row tap, which is load-bearing for `/bridge` (`router.dart:360` reads
`selectedCoin`). Task 2 carries a grep gate for this.

**Mock mode is mirrored, deliberately.** `coins_screen.dart:75-81` short-circuits to
`DevMockHoldings.instance.marketData` when `kDebugMode && cubit.mockMode`. Without the same
short-circuit here, the dev bubble's scenarios light up the dashboard and leave `/assets` blank, and
the page is unwalkable on Jakub's zero-balance wallet.

## D-6 Back affordance, and the route shape

The page mounts `GWBackLink(label: 'HOME', onTap: ...)` as its first child, the app's one
breadcrumb-style way back (`token_info_screen.dart:319` is the precedent). Its `onTap` is

```
() => context.canPop() ? context.pop() : context.go('/dashboard')
```

The fallback is not defensive padding. `dashboard_markets.dart:68` navigates with `context.go`, so if
25-01 copies that shape for Assets there will be nothing to pop, and a deep link has nothing to pop
either. **Cross-plan note for the phase walk:** `/markets` uses `go` because Markets IS a nav tab.
Assets is not - the bar is Home / Markets / dock / Activity / More - so `context.push('/assets')` is
the correct call for 25-01 to emit. The route works either way; the note is for check W-6.
