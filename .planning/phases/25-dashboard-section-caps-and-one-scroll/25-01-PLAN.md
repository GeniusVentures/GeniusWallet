<the_mechanism_this_plan_is_about>

## Read this before Task 3 or the layout will assert instead of scrolling

The four scroll areas the BRIEF measured are not four separate bugs. They are
one structural fact: every panel is handed a BOUNDED height by
`OneColumnDashBoardView`, and a panel handed a bounded height has to put its
overflow somewhere. Each solved that independently, so the page ended up with
four scrollables competing for one finger.

**The rule this plan installs, stated once and applied four times:**

> A dashboard panel HUGS its content when its host gives it unbounded height,
> and FILLS AND SCROLLS when the host bounds it.

Removing the one-column `ConstrainedBox` caps flips every panel to the first
branch. That is what frees the gesture - not deleting scroll views.

**Why deleting the inner scroll views is the WRONG fix, and what actually
protects the Compute panel (the BRIEF asks this directly).** A `Scrollable`
whose min and max scroll extents are equal installs no drag recognizer at all
(`ScrollPhysics.shouldAcceptUserOffset` returns false when
`minScrollExtent == maxScrollExtent` and `pixels == 0`);
`wallet_overview.dart:159-166` already records exactly this and relies on it.
So once the cap is gone:

- the Compute panel's `SingleChildScrollView` (`wallet_overview.dart:178`) has
  zero extent, enters no gesture arena, and cannot steal the page's drag;
- it CANNOT throw an overflow either, because overflow needs a binding
  constraint to exceed and there is none in the one-column layout;
- and it stays load-bearing for the reason it was actually added - an enlarged
  text scale, where the panel simply grows taller and the PAGE scrolls.

The "quietly scrollable inside its own box" failure mode the panel's own doc
comment records is therefore not replaced by a throw. It is **removed on mobile
and left exactly where it is on desktop**, where the cap still exists and
`compute_panel_height_test.dart` is still the alarm. Nothing needs a new guard.

The same argument covers Assets: `CoinsScreen`'s `SingleChildScrollView`
(`coins_screen.dart:255`) goes inert on mobile and stays load-bearing on
desktop, where `ContributionsDashboardView` still sits in a 340 slot. **Neither
of those two scroll views is removed by this plan.**

**Markets and Transactions are the two that DO need code**, and for a precise
reason: they use `Expanded`, and `Expanded` under an unbounded main-axis
constraint is a RenderFlex assertion, not a layout. `RenderFlex` errors with
"children have non-zero flex but incoming height constraints are unbounded"
whenever `totalFlex > 0` and `maxMainSize` is infinite - and that is true for
`Flexible` as well, so loosening the fit does not save it. Both panels need a
hug branch that carries no flex child.

`TransactionsSlimView._panel` already has the mechanism (`hug`) and already has
the `LayoutBuilder` to feed it - it just reads `widget.page` and ignores
`constraints`. `DashboardMarkets` has neither and gets both.

**The Chart is deliberately NOT in this plan.** `ChartDashboardView` keeps its
`ConstrainedBox(maxHeight: 350)`: it contains no scrollable (nothing in
`crypto_live_chart.dart` registers a drag or pan), so it steals no gesture, and
its content is a chart in an `Expanded` that genuinely needs a bounded box.
Capping it costs the user nothing. Do not uncap it "for consistency".

### D1 - Ordering lives in a pure helper, in the file that already owns Assets math

`assets_totals.dart` already computes the per-holding number this ordering needs
(`holdingValue(balance, price)`, line 11) and is deliberately import-free so it
is unit-testable without constructing the heavy `CoinGeckoMarketData` model. The
ordering goes there, as a GENERIC function taking accessor callbacks, which
keeps that file's zero-import property intact.

Not in the widget: sketch 177's component audit lists `assets_totals.dart` among
the seven things the `/assets` page reuses AS-IS, so a widget-local sort would
guarantee the two surfaces disagree. Not in the cubit: `WalletDetailsCubit` owns
fetch order for every consumer (`read_asset`'s native-first order), and
`coins_screen.dart:238` already records that display order is scoped to display.

### D2 - A funded holding with no price sorts ABOVE priced rows

Matches sketch 177's proposal verbatim ("keep it above priced rows in descending
order, since 'you own this and we cannot price it' outranks any priced row"), so
the dashboard and `/assets` agree.

**One refinement, and it is the proposal read precisely rather than a
divergence:** the proposal says "a holding that has a BALANCE but no market
data". A holding with a ZERO balance and no market data is not something you own
and does not outrank anything - it sorts to the bottom with the other zeros. So
the rank is:

1. GNUS (pinned, see D3)
2. balance is non-zero AND no known price - value unknown, incoming order
3. everything else, by `holdingValue` descending
4. ties anywhere keep the caller's incoming order

**The cap-specific cost, recorded because it is real:** on a five-row panel an
unpriced dust token can push a genuinely valuable row off the surface entirely,
which cannot happen on the uncapped `/assets` page. Accepted, because a holding
the app cannot price is the one the user most needs to see, and because two
surfaces ordering differently is the defect the BRIEF names. If Jakub prefers
priced-first on the dashboard, it is one line in the rank function - and it must
then change on `/assets` too.

### D3 - GNUS stays pinned first in Assets

`coins_screen.dart:236-243` floats GNUS to the top today, as a stated display
decision. Jakub's request names a value sort and says nothing about the pin, and
silently dropping a shipped decision while implementing an adjacent one is the
regression pattern this project has already been bitten by.

It is also the coherent reading: the Markets cap in the very same request pins
GNUS explicitly. A dashboard that pins GNUS in Markets but lets it fall out of
Assets - which it would, constantly, since Jakub's real wallet has every balance
at zero - would be inconsistent with the request rather than faithful to it.

Flagged on the on-device list so Jakub can overrule it in one sentence.

### D4 - View all is hidden when the section is EMPTY, never when it is merely short

The BRIEF asks whether to hide it below the cap. No: a link that appears and
disappears as balances move is a moving target and reads as a bug, and Markets
already shows it unconditionally, so a rule holding for two sections out of
three is the inconsistency this phase exists to remove. `/assets` is a full view
with search and a sort even when it lists the same three rows.

It IS hidden on an empty section, and that is not a new rule - it is
`transactions_slim_view.dart:290-304`'s shipped rule applied to a second control:
"a control that filters an empty set is an offer the app cannot honour". Viewing
all of nothing is the same offer. Each section already has the machinery:

- **Assets** returns `GWEmptyState` before the title is built at all
  (`coins_screen.dart:219`), so there is nothing to hide.
- **Markets** returns its own `GWEmptyState` in `MarketsDashboardView.onData`
  before `DashboardMarkets` is constructed, likewise.
- **Transactions** reuses the EXISTING `scoped.isEmpty ? null : ...` guard on
  the trailing. `scoped`, never `txs` - `transaction_filters_test.dart` pins
  both directions and getting it backwards strands a filtered user.

### D5 - The link sits at the FAR RIGHT in all three sections

Markets puts it at the panel's top-right corner today. Assets and Transactions
match, so the link occupies the same pixel region in every section and the eye
learns one place. In Assets that means the total moves inboard of it:
`Row(mainAxisSize.min, [totalColumn, SizedBox(width: space12), GWViewAllLink])`.

Measured headroom, because this narrows a slot that had no guard: at 390pt the
title row's content box is 336 (390 - 2*space3 ListView padding - 2*(space6 + 1px
border) container inset - 2*space4 title inset). "Assets" takes about 58 and the
link about 86, plus the space12 gap, leaving about 168 for the total block. The
widest realistic pair - a `$1,234,567.89` amount at 20px and its change line at
13px - measures roughly 143 and 126. It fits, with the ceiling recorded rather
than claimed: above roughly ten million the change line starts to crowd.

### D6 - Transactions cannot keep the filter bar AND gain a View all in the same row

Measured, not assumed: the title text is about 112, the filter bar is pinned at
183 (`transaction_filters_test.dart:467`, an explicit width assertion), and the
link is about 86. That is 381 against 336 available. They do not both fit on a
phone, and there is no token-grid tweak that closes a 45px gap.

This is a collision between two of Jakub's own decisions, not a scope question,
so it is **Task 1, a blocking decision checkpoint**, with a recommendation and
both implementations fully specified. It is placed before any code is written
so nothing has to be rebuilt.

### D7 - `context.push('/assets')`, and the link is inert until 25-02 lands

`push` rather than `go`, matching what `coins_screen.dart:326` already does for
`/token-info`, which lives in the same router block. It works whether or not
25-02 puts the page in the nav shell. If 25-02 registers `/assets` as a bottom-nav
tab, switch this one call to `go`.

Until 25-02 lands, tapping Assets' View all hits an unregistered route. That is
expected and it is why the on-device step for it is explicitly gated.

### D8 - No minHeight floors replace the removed caps

Considered and rejected. A floor would stabilise the page while the async
sections load, but today's caps are `maxHeight` only, so the page already
reflows as Markets and Assets resolve - a floor would not fix a new problem, it
would create one: Jakub's real wallet is empty everywhere, so four floored
panels would give him four tall empty boxes. Panels size to their content, short
when empty and tall when full. The load-time settle is on the on-device list so
its new magnitude gets looked at rather than assumed.
