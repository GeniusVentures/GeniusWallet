# Phase 25 walk, 2026-08-07

## The goal, and the verdict on it

The phase existed for one reported feeling, as Jakub put it on 2026-08-06: he dislikes that sometimes,
instead of the page going down, some section scrolls instead.

**Approved on device 2026-08-07: the scrolling is fine, he closed the item.**

The dashboard had four independent scroll areas - Compute and Assets each in a
`SingleChildScrollView`, Markets a `ListView.separated`, Transactions a `ListView.builder`, every one
of them inside a fixed-height `ConstrainedBox`. A drag starting inside any panel was eaten by that
panel and never reached the page. That is now one page scroll.

The mechanism, recorded because it is the reusable part: a panel hugs its content when the host gives
it unbounded height, and fills-and-scrolls when the host bounds it. Removing the caps made Compute's
and Assets' inner scroll views **inert rather than removed** - `ScrollPhysics.shouldAcceptUserOffset`
returns false when min and max scroll extents are equal, so no drag recognizer is installed and no
overflow can throw. They stay load-bearing on desktop. Only Markets and Transactions needed code,
because `Expanded` under unbounded height is a RenderFlex assertion.
