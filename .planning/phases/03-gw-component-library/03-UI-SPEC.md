# Phase 3 — UI Design Contract

> Visual and interaction contract for the `gw_*` component library port. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker.

**Framing.** This is a **port of an already-authored, adopted design system** — not a design
exercise. Every component, prop and default below is extracted from `DESIGN_SYSTEM.md` (v1.0,
Adopted, worktree `GNUS-compare/GeniusWallet-3514`) and its actual Flutter implementation at
`GeniusWallet-3514/lib/components/*`. Nothing here is invented. Phase 2 already landed the token
vocabulary this phase's components consume (`02-UI-SPEC.md`) — this document does not re-derive
colors, spacing, radius, typography, elevation, gradients or motion; it only decides **which files
land, which are excluded and why, and how fidelity is proven** before any screen depends on them.

The answer to "what must each ported primitive honour" is: **the exact prop/behavior contract its
source file already defines** (§2), rendered pixel-faithfully in an extended `/design_gallery`
(§5) that a human checks against the Release exe at `GeniusWallet-3514`, with zero regression to
any currently-reachable screen (§1).

## 1. Additive-Only Mechanism (inherited from Phase 2 §1, restated for this phase)

### 1.1 The rule, unchanged

> A file lands in Phase 3 only if it is a **new path** that does not exist on develop today, or a
> **new asset** an additive file requires. No file that already exists on develop (a "collision
> file") is modified this phase. Screens that would consume these primitives are ported in Phases
> 4–10; until then, nothing imports them from any currently-reachable code path.

This is not a restatement of intent — it is verified below by an exact three-way diff (not the
approximate "82 additive files / 43 under `lib/components/`" estimate the orchestrator prompt
carried in). Running
`comm -23/-12/-13` between `lib/components/**` on `GeniusWallet-3514` (design source) and on this
repo's current tree produced:

- **58 additive files** under `lib/components/` (design-only, zero collision) — the authoritative
  set for this phase, itemized in §2.
- **22 collision files** (exist on both, differ) — explicitly **not touched this phase**; several
  carry the behavior findings 13/15/16/25/26 target (§4).
- **2 develop-only files** (`loading.dart`, `wallet_overview.dart`) untouched by the design branch
  — GAP-06 territory (Phase 5), not this phase's concern.

### 1.2 What's excluded from the 58, and why

Three groups of the 58 additive files are **excluded from this phase's port** despite being
design-source-additive, because landing them here would violate the additive-only rule in spirit
(they wire into shell/app-level state, not a screen-independent primitive) or would pull in
out-of-scope capability (WIRE-02):

| Excluded group | Files | Reason |
|---|---|---|

Porting these 9 files now would either sit dead (fine) or tempt an executor to wire them into `main.dart`, which is squarely NAV-01/NAV-02 (Phase 4, "the frame every screen mounts into"). **Owned by Phase 4.** |

Porting `GWAiFab` would require also porting or stubbing `lib/ai/`, which this milestone explicitly defers to product. **Excluded entirely**, not deferred to a phase — re-evaluate only if `lib/ai/` is ever scoped into a future milestone. |

**Net scope this phase: 47 files** (58 − 9 nav-shell − 1 AI FAB − the header-wrapper pair stays in,
already counted in the 58). See §2 for the itemized 47.

### 1.3 Why "nothing may change visually" holds

No collision file is edited. No new route is reachable from a normal build (the one new route,
`/design_gallery`, is gated exactly like Phase 2's `/dev/token-probe` — see §5.2). No existing
screen imports any of the 47 files (verified per-file in §2's caller-trace column, where relevant).
Walking the app top to bottom before and after this phase must show zero pixel difference — the
same criterion Phase 2 established and the same verification discipline (§7).

## 4. Findings Bound to This Phase (13, 15, 16, 25, 26) — what actually changes, and what doesn't

**The load-bearing fact for all five:** every file these findings describe as regressed
(`responsive_drawer.dart`, `custom_future_builder.dart`, `crypto_address_qr.dart`) is a **collision
file this phase does not touch** (§1.1). Verified by reading develop's current version of each:
**all three already implement the correct, non-regressed behavior today.** The regressions the
findings describe exist only in Alex's fork (`GeniusWallet-3514`, the `HEAD` in each finding's
diff) — a version of these files that has not yet, and under this phase's additive-only rule
cannot, land on develop. So there is nothing to *fix* this phase. There is something to **prove
(it's already true) and bind (don't let a later phase regress it when it finally touches these
files for real)**.

### 4.1 Findings 13, 25, 26 — the drawer (`responsive_drawer.dart`)

Verified line-by-line, develop's current `lib/components/bottom_drawer/responsive_drawer.dart`:
- `showDialog(..., useRootNavigator: useRootNavigator)` and `showModalBottomSheet(..., useRootNavigator: useRootNavigator)`, both defaulting `useRootNavigator = true` → **finding 13 already satisfied.**
- `enableDrag: enableDrag` parameter, default `true` → **finding 25 already satisfied.**
- `MediaQuery.sizeOf(context).width >= GeniusBreakpoints.medium` where `GeniusBreakpoints.medium =
  768` (`lib/utils/breakpoints.dart`) → **finding 26 already satisfied** (not the hardcoded 800 Alex's
  fork introduced).

**Binding rule for this phase and every later one:** `bottom_drawer/bottom_drawer.dart` (§2.5, new
this phase) is ported as **content chrome only** — its header/footer visual treatment. It must be
demonstrated by calling develop's **existing, unmodified** `ResponsiveDrawer.show()`, passing
`BottomDrawer(...)` as the `child`, and **omitting `title`/`actions` on the `ResponsiveDrawer.show()`
call** (so `_ResponsiveDrawerScaffold` renders no competing `AppBar` — `BottomDrawer` supplies its
own header). Do **not** port Alex's `responsive_drawer.dart` file wholesale, this phase or any
later one — it is the regression, not the fix. Whenever a later phase (Phase 4, nav shell) wires
`BottomDrawer` into a real screen's drawer, it must keep calling develop's `ResponsiveDrawer.show()`
with its current defaults (`useRootNavigator: true`, `enableDrag: true`,
`GeniusBreakpoints.medium` = 768) — never reintroduce Alex's hardcoded `800` / `enableDrag: false`.

**Gallery verification (§5):** open a drawer from `/design_gallery` using
`ResponsiveDrawer.show(context: context, child: BottomDrawer(title: '...', children: [...]))`.
Confirm it mounts above the whole app (not clipped to the gallery's own navigator), can be
swiped down to dismiss on mobile width, and flips to the desktop side-dialog at exactly 768px
(resize the window across the boundary — not 800px).
