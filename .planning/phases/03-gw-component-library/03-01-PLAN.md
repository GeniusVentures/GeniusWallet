  <name>Task 2: Record the shadow-name baseline and build the mechanical additive-boundary guard</name>

This is the technical gate for the phase's worst hazard class: **a file this phase adds declares a
public class whose name already exists on develop at a different path.** Different import paths mean
no compile error and no analyzer warning — an import repointed by a later phase (an IDE auto-import,
a careless find/replace, or an executor skimming a table) silently swaps one widget for another.

The UI-SPEC (§2.4) documents ONE such pair (`Loading`). A mechanical scan of all 50 in-scope files
against develop's `lib/` found **three pairs, four class names**. The other two are not in the
UI-SPEC and are recorded here for the first time. Do not treat this list as the SPEC's — it extends
it.

**A. Write `.planning/phases/03-gw-component-library/03-SHADOW-NAMES.md`** recording the baseline,
its derivation command, and the binding rule. Content, verbatim facts (all independently verified
this planning session — re-verify each before writing, do not copy on trust):

| Shadow class | New path (this phase adds) | Canonical path (develop has today) | Canonical importers | Why it matters |
|---|---|---|---|---|
| `Loading` | `lib/components/loading/loading.dart` | `lib/components/loading.dart` | **18** files | Both are `StatelessWidget` with an identical `{String? text}` constructor. Alex's uses Phase 2 tokens; develop's uses raw values. A repointed import compiles and silently re-skins a loading state. Detonates in Phases 5/6/9, not here. |
| `Splash` | `lib/components/splash.dart` | `lib/screens/splash.dart` | **1** (`lib/navigation/router.dart:30`) | Develop's is a `StatelessWidget`; Alex's is a `StatefulWidget`. The single importer is the **splash route** — i.e. the app's boot path. Alex deleted `screens/splash.dart` on his branch, so a later phase "finishing the move" would swap the startup screen. |
| `WalletsOverview`, `WalletsOverviewState` | `lib/components/wallets_overview.g.dart` | `lib/components/wallet_overview.dart` | **1** (`lib/dashboard/home/view/dashboard_screen.dart:19`) | **The most dangerous of the three.** Filenames differ by one letter (`wallets_` vs `wallet_`). The shadow is a `.g.dart` file, so `flutter analyze` is blind to it (`analysis_options.yaml:5`). The canonical file is GAP-06 — **Phase 5 will re-skin it**, on the dashboard, which is exactly the phase most likely to repoint the import. The shadow is orphaned dead code even on Alex's own branch (UI-SPEC §2.8). |

Derivation command to record in the doc (this is the evidence, not a claim):

    git diff --diff-filter=A --name-only develop..origin/ui-redesign-3.514 -- lib/components/

filtered to the 50 in-scope files (minus the 9 nav-shell files and `buttons/gw_ai_fab.dart`), then
for each declared public class name, `grep -rlE "^(abstract )?class <Name>\b" lib/` against develop.

**Binding rule to record:** the canonical path wins for every existing caller. No phase may repoint
an existing import from a canonical path to a shadow path as an incidental edit. Migrating a caller
is a deliberate act that requires updating this baseline in the same commit, with a stated reason.

**B. Write `tool/verify_additive_boundary.sh`** — a bash script (Git Bash; the whole verification
recipe already assumes it), no arguments, prints each check's result, `exit 1` on any violation.
Three checks:

**Check 1 — shadow import boundary.** For each of the 3 pairs, assert the exact set of files
importing the canonical `package:genius_wallet/...` path equals the recorded baseline set (store the
baseline as a sorted literal list in the script, not just a count — a count alone passes if one
caller is repointed and another is added), AND assert the set of files importing the shadow path is a
subset of that pair's allowlist. Allowlist: `lib/dev/design_gallery_screen.dart` for `Loading` and
`Splash` (plan 03-09 demos both in the gallery); **empty** for `wallets_overview.g.dart` (nothing may
import it — it is dead code being preserved for completeness only). The one exception is plan 03-04's
compile canary, `lib/dev/generated_closure_canary.dart`, which imports every `.g.dart` in the set by
design — put that single path on the `WalletsOverview` allowlist. If plan 03-04 lands the canary at a
different path, update the allowlist in that same commit.

**Check 2 — duplicate-class-name census (the generic gate).** Re-derive, from the working tree, the
set of public class names declared in more than one file under `lib/` (including `.g.dart` files —
this check must NOT honor `analysis_options.yaml`'s exclude, that blindness is the whole point).
Assert that set is a **subset** of the 4 recorded names. A subset check, not equality, so the script
passes both before the shadow files land (census is empty) and after (census is the 4) — no mid-phase
edit needed. If a later phase introduces a 5th duplicate public class name anywhere in `lib/`, this
trips. This is the check that generalizes the hazard rather than guarding three known instances.

**Check 3 — WIRE-01 standing rule.** `grep -rn "WIRE-" lib/` must return nothing. Verified clean
across all 50 in-scope files this planning session, and clean on develop today, so this is a cheap
standing tripwire for every later phase rather than a live risk now.

Make the script's own head comment state what it is for, why the analyzer cannot do this job, and
that it must be re-run by every phase that touches `lib/components/`, `lib/screens/splash.dart`,
`lib/navigation/router.dart` or `lib/dashboard/home/view/dashboard_screen.dart`. Reference the script
from `03-SHADOW-NAMES.md` and vice versa.

Run it. It must exit 0 against the current tree (before any component lands).

**Scope honesty:** this is a guard a phase must *run*, not a hook that fires unbidden — this repo has
no pre-commit hooks and its only CI workflow (`.github/workflows/build.yml`) is a build matrix that
does not run `flutter analyze` or any check step. Wiring the script into CI is a real option but is
out of this phase's scope and would need its own decision. Record that limitation plainly in
`03-SHADOW-NAMES.md` rather than implying the gate is automatic; every plan in this phase runs it in
`<verify>`, and plan 03-10 records its final state.
