This is the technical gate for the phase's worst hazard class: **a file this phase adds declares a
public class whose name already exists on develop at a different path.** Different import paths mean
no compile error and no analyzer warning — an import repointed by a later phase (an IDE auto-import,
a careless find/replace, or an executor skimming a table) silently swaps one widget for another.

The UI-SPEC (§2.4) documents ONE such pair (`Loading`). A mechanical scan of all 50 in-scope files
against develop's `lib/` found **three pairs, four class names**. The other two are not in the
UI-SPEC and are recorded here for the first time. Do not treat this list as the SPEC's — it extends
it.

**A. Write `.planning/phases/03-gw-component-library/03-SHADOW-NAMES.md`** recording the baseline,
its derivation command, and the binding rule. Content, verbatim facts (all independently verified
this planning session — re-verify each before writing, do not copy on trust):

| Shadow class | New path (this phase adds) | Canonical path (develop has today) | Canonical importers | Why it matters |
|---|---|---|---|---|
| `Loading` | `lib/components/loading/loading.dart` | `lib/components/loading.dart` | **18** files | Both are `StatelessWidget` with an identical `{String? text}` constructor. | `Splash` | `lib/components/splash.dart` | `lib/screens/splash.dart` | **1** (`lib/navigation/router.dart:30`) | Develop's is a `StatelessWidget`; Alex's is a `StatefulWidget`. **Binding rule to record:** the canonical path wins for every existing caller. No phase may repoint
an existing import from a canonical path to a shadow path as an incidental edit. Migrating a caller
is a deliberate act that requires updating this baseline in the same commit, with a stated reason.

**Also record, in its own section, the 4 pre-existing legitimate duplicates** (`GoBack`,
`PinConfirmFailed`, `PinConfirmPassed`, `PinCreated` — parallel onboarding bloc events, see Check 2
below) and why they are NOT hazards: different supertypes, never co-imported, not substitutable at any
call site. State plainly that develop's duplicate-class census was **already non-empty before this
phase started**, so the guard's baseline is captured, not assumed empty. The next reader must not
mistake these for shadows and "clean them up".

**B. Write `tool/verify_additive_boundary.sh`** — a bash script (Git Bash; the whole verification
recipe already assumes it), no arguments, prints each check's result, `exit 1` on any violation.
Three checks:

**Check 1 — shadow import boundary.** For each of the 3 pairs, assert the exact set of files
importing the canonical `package:genius_wallet/...` path equals the recorded baseline set (store the
baseline as a sorted literal list in the script, not just a count — a count alone passes if one
caller is repointed and another is added), AND assert the set of files importing the shadow path is a
subset of that pair's allowlist. Allowlist: `lib/dev/design_gallery_screen.dart` for `Loading` and
`Splash` (plan 03-09 demos both in the gallery); **empty** for `wallets_overview.g.dart` (nothing may
import it — it is dead code being preserved for completeness only). The one exception is plan 03-04's
compile canary, `lib/dev/generated_closure_canary.dart`, which imports every `.g.dart` in the set by
design — put that single path on the `WalletsOverview` allowlist. If plan 03-04 lands the canary at a
different path, update the allowlist in that same commit.

**Check 2 — duplicate-class-name census (the generic gate).** Re-derive, from the working tree, the
set of public class names declared in more than one file under `lib/` (including `.g.dart` files —
this check must NOT honor `analysis_options.yaml`'s exclude, that blindness is the whole point).
Assert that set is a **subset of a captured baseline**, stored as data in `tool/shadow-baseline.txt`.

**Critical, and the reason this check needs a captured baseline rather than a hardcoded list of the 4
shadow names: develop's census is NOT empty today.** It already returns 4 duplicated public class
names, all legitimate:

    $ grep -rhoE "^class [A-Za-z_][A-Za-z0-9_]*" lib/ --include=*.dart | awk '{print $2}' | sort | uniq -d
    GoBack
    PinConfirmFailed
    PinConfirmPassed
    PinCreated

Each is a **deliberate parallel bloc event**, declared once per onboarding bloc — different supertypes,
different files, never imported together:
- `lib/onboarding/existing_wallet/bloc/existing_wallet_event.dart` → `class GoBack extends ExistingWalletEvent {}` (:51), `PinConfirmPassed` (:41), `PinConfirmFailed` (:43), `PinCreated` (:35)
- `lib/onboarding/new_wallet/bloc/new_wallet_event.dart` → `class GoBack extends NewWalletEvent {}` (:45), `PinConfirmPassed` (:41), `PinConfirmFailed` (:43), `PinCreated` (:39)

These are **not hazards and must not be "fixed"**. A shadow is dangerous when two same-named classes
are substitutable at the same call site; these have different supertypes and cannot be. Record that
reasoning in the baseline so the next reader does not delete them to make a number look tidy.

**Build the baseline by DERIVING it, not by copying the 4 names above.** Run the census against the
tree, capture whatever it actually returns, and write one line per entry to
`tool/shadow-baseline.txt`:

    # <ClassName>  <category>  <justification>
    GoBack                pre-existing     Parallel bloc event; ExistingWalletEvent vs NewWalletEvent, never co-imported
    ...
    Loading               phase-03-shadow  See 03-SHADOW-NAMES.md — canonical is lib/components/loading.dart (18 importers)
    Splash                phase-03-shadow  See 03-SHADOW-NAMES.md — canonical is lib/screens/splash.dart (boot path)
    WalletsOverview       phase-03-shadow  See 03-SHADOW-NAMES.md — canonical is lib/components/wallet_overview.dart (GAP-06)
    WalletsOverviewState  phase-03-shadow  See 03-SHADOW-NAMES.md — same pair as WalletsOverview

Two categories: `pre-existing` (already duplicated on develop, justified as legitimate) and
`phase-03-shadow` (the 4 this phase knowingly adds — add these now, before the shadow files land, so
no mid-phase baseline edit is needed).

**Every entry requires a written justification. If the census returns an entry you cannot justify as
legitimate, STOP and report it** — do not baseline it. Baselining an unexplained duplicate is exactly
how a real hazard gets laundered into "expected", and it would make this guard theatre.

The script reads column 1 of the baseline, skipping comments and blank lines (`grep -v '^#'` before
counting — a bare count over the raw file counts comment lines and the header, which is how this kind
of check quietly self-invalidates). Then: `census ⊆ baseline` → pass; anything else → fail, printing
the offending name(s).

Why a captured baseline rather than widening the list to 8, or scoping the census to
`lib/components/`: both would destroy the property that makes this worth having — that a **5th,
unforeseen** shadow anywhere in `lib/` trips it. A `lib/components/`-only census would have missed
half the `Splash` pair's context (the shadow is at `lib/components/splash.dart`, but its canonical
twin is at `lib/screens/splash.dart`), and a hand-maintained list of 8 rots the moment someone adds a
legitimate parallel bloc event. With a captured baseline, a future legitimate duplicate is a
deliberate one-line addition with a justification and a reviewer looking at it — not a silent pass,
and not a broken build.

**Check 3 — WIRE-01 standing rule.** `grep -rn "WIRE-" lib/` must return nothing. Verified clean
across all 50 in-scope files this planning session, and clean on develop today, so this is a cheap
standing tripwire for every later phase rather than a live risk now.

Make the script's own head comment state what it is for, why the analyzer cannot do this job, and
that it must be re-run by every phase that touches `lib/components/`, `lib/screens/splash.dart`,
`lib/navigation/router.dart` or `lib/dashboard/home/view/dashboard_screen.dart`. Reference the script
from `03-SHADOW-NAMES.md` and vice versa.

Run it. **It must exit 0 against the current tree, before any component lands.** This is not a
formality — it is the half of the guard's contract that was wrong in an earlier draft of this plan.
A guard that fails on a clean checkout gets disabled by the first person who hits it, and then the
real hazard (silent widget impersonation on the boot path) walks straight through an assertion
everyone believes is covering them. If it does not exit 0 on the untouched tree, the baseline is
wrong — fix the baseline, do not fix the tree.

**Scope honesty:** this is a guard a phase must *run*, not a hook that fires unbidden — this repo has
no pre-commit hooks and its only CI workflow (`.github/workflows/build.yml`) is a build matrix that
does not run `flutter analyze` or any check step. Wiring the script into CI is a real option but is
out of this phase's scope and would need its own decision. Record that limitation plainly in
`03-SHADOW-NAMES.md` rather than implying the gate is automatic; every plan in this phase runs it in
`<verify>`, and plan 03-10 records its final state.
  </action>
