# Phase 4 — UI Design Contract

> Visual and interaction contract for the navigation shell, theme wiring, Settings, SDK account
> manager, wallet drawer, and the build-time-exception recovery screen. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker.

**Framing.** Like Phases 2 and 3, this is a **port of an already-authored, adopted design
system** — not a design exercise. Every visual value below is extracted from Alex's
`GeniusWallet-3514` reference worktree and Phase 2/3's already-landed token/component layers.
Nothing here is invented. This document's job is narrower than it looks: **wire the
appearance-aware theme first (D-01/D-02), then re-skin four surfaces on top of it** — the
nav shell, Settings, the SDK account manager, and the wallet drawer — while carrying develop's
existing behavior and 8 already-verified findings forward unregressed.

**The single most important fact this research turned up:** every one of the 8 findings this
phase's traceability names (2, 4, 5, 11, 12, 23, 27, 35) is **already true on today's develop**,
verified by direct inspection, not assumed. See §4. This phase's job for all 8 is **verify + bind
+ re-skin without regressing** — the same shape Phase 3 established for findings 13/15/16/25/26.
Do not "fix" any of them; do not let the re-skin accidentally drop what already works.

## 1. Sequencing (D-01/D-02) — theme first, everything else depends on it

**Plan 04-01 is theme-only, full stop.** No shell/screen re-skin work happens in the same plan as
the theme wire. This is not a style preference — Phase 3's own verification record
(`03-VERIFICATION.md` criteria 1/3, both PARTIAL) proved that mounting `gw_*` components against
develop's current `ThemeData(brightness: Brightness.dark)` (hardcoded, no `textTheme:`) produces 5
observable defects (text not flipping, icons not flipping, button font unstyled) that are **not
port defects** — they are the absence of the theme this phase exists to land.

### 1.1 What 04-01 must do, concretely

1. Reconcile `lib/theme/theme.dart` (develop, 276 lines) against
   `GNUS-compare/GeniusWallet-3514/lib/theme/theme.dart` (Alex, 309 lines) — take Alex's visual
   wholesale where it does not collide with a behavior develop depends on (see §1.2 for the one
   confirmed exception). This is the milestone's single largest reconcile (~329 changed lines);
   HOW (line-by-line vs. wholesale adopt) is the planner/executor's call per CONTEXT.md, bounded by
   "take the visual, not new behavior."
2. Wrap `MaterialApp.router` at `lib/main.dart:294` in
   `ValueListenableBuilder<GWAppearanceMode>` on `GWAppearance.instance`, exactly the mechanism
   already proven twice in this repo (`lib/dev/token_probe_screen.dart`, Phase 2;
   `lib/dev/design_gallery_screen.dart`, Phase 3 — both wrap their own `Scaffold`, not
   `MaterialApp`; this is the first time the wrap happens at the `MaterialApp` level so the whole
   app rebuilds, not just one screen). Call `GWAppearance.instance.load()` once before `runApp`
   (or in the wrapper's `initState`-equivalent), matching the existing pattern.
3. Revert the design gallery's `Scaffold(backgroundColor: surfaceBase)` (a 03-09 workaround,
   `244b71e`) back to `Scaffold(backgroundColor: Colors.transparent)` once the ambient theme
   supplies a correct background — this un-does a dev-only patch, it is not itself a screen
   re-skin.

### 1.2 The one confirmed collision: `floatingLabelBehavior`

**Do not adopt Alex's `inputDecorationTheme` wholesale — it silently drops a behavior develop
depends on.** Verified by reading both files directly:

- develop's current `theme.dart:159`: `inputDecorationTheme: InputDecorationTheme(...,
  floatingLabelBehavior: FloatingLabelBehavior.always)`.
- Alex's reference `theme.dart` (lines 168-181): its `inputDecorationTheme` has **no
  `floatingLabelBehavior` line at all** — the property is absent, not merely different.

This is finding 36 (Phase 2's own success criterion 5: "form-field labels stay pinned above the
field on every existing TextField ... `floatingLabelBehavior: always` survives the theme
rewrite"), already confirmed holding on develop's pre-Phase-4 theme. **Binding rule: whichever
reconciliation strategy 04-01 uses (line-by-line or wholesale-adopt-then-patch), the resulting
`InputDecorationTheme` must include `floatingLabelBehavior: FloatingLabelBehavior.always`
explicitly** — carrying it forward is this phase's job, not assuming Alex's version is a strict
superset.

### 1.3 The WCAG choice to preserve, not "fix"

Alex's `theme.dart` sets `onPrimary: GeniusWalletColors.textOnBrand` (near-black, `#000B18`) in
**both** the light and dark `ColorScheme`, with an inline comment: "white on the bright brand fill
failed WCAG AA for Material widgets in dark mode." This is a deliberate accessibility decision, not
an oversight — 04-01 must carry it forward exactly, never substitute `Colors.white` or
`Colors.black` for it, in either appearance.

### 1.4 The re-walk gate (D-02) — before any shell/screen re-skin starts

After 04-01 lands, re-walk `/design_gallery` in both appearance modes (same protocol as
`03-09-SUMMARY.md`'s walk) and derive the dark-only component **count** Phase 3 recorded as NOT
DERIVABLE. Expect most of the 5 theme-confound findings to evaporate (token row / wallet card /
empty-error text color, button font, icon flip). What should remain and is **not** a bug — Alex's
own real design choices, all byte-identical ports, all confirmed by Phase 3:

| Item | Status |
|---|---|
| `GWCanvasBackground` grain gated `if (!isLight)` | Design choice — do not remove the gate |
| `GWMeshBackground` blobs invariant brand colors over a flipping backdrop | Design choice |
| `GWSwitch` disabled visually identical to off | Design choice (`gw_switch.dart:27` computes `disabled`, never uses it for color) |
| `GWSwitch` off-thumb reads near-black in light (`inactiveThumbColor: textPrimary`) | Design choice, token behaving as designed |

Two items from the 03-09 walk have **no established root cause** and must get a real repro at
this re-walk, not a guess: `Screen wrappers` (`AppScreenView`) blank in **dark** mode (light-mode
blankness is explained by the theme confound; dark is not), and the disabled `GWCheckbox`
invisible in dark (`btnDisabled = Color.fromRGBO(188,188,188,1)`, **not appearance-aware** —
confirm whether this is actually consumed by the disabled-checkbox path before concluding it's the
cause). Do not fold either into the "design choice" bucket without a repro.

**Gate:** no shell, Settings, SDK-account-manager, drawer, or exception-screen work (04-02+) starts
until this re-walk is performed and the count is recorded.

## 2. Navigation Shell Re-Skin (NAV-01)

### 2.1 What exists today on develop — the re-skin target

`lib/navigation/router.dart`'s `ShellRoute` renders `MobileOverlay`/`DesktopOverlay` from
`lib/components/overlay/responsive_overlay.dart` (a collision file, last touched by Phase 2's
`ca556e4` dev-gating commit — do not re-derive that as a Phase 4 leak). **This file is what gets
re-skinned.** It currently uses pre-redesign tokens throughout: `GeniusWalletColors.deepBlueCardColor`
/ `deepBlueTertiary` (hardcoded dark constants, not appearance-aware), `Colors.greenAccent`,
`Colors.white`, raw `TextStyle(fontSize: ...)`. **Re-skin means: replace every one of these with
Phase 2/3 tokens** (`GeniusWalletColors.surfaceElevated`, `brandPrimary`, `textPrimary`/
`textSecondary`, `GeniusWalletTypography.*`) so the shell participates in the appearance flip
04-01 just wired — a shell that still reads `deepBlueCardColor` after this phase is an unfinished
re-skin, not a deferred detail, because light mode is a shipping surface (D-03).

`responsive_overlay.dart`'s current destination list (8 items, exact order): **Dashboard,
Transactions, Swap, Web (hidden on Linux), Markets, News, Feedback (`/logs`), Settings.** This
order and membership is **locked** — re-skin, never restructure (NAV-01: "every existing route
still reachable").

### 2.2 The visual reference — and the ambiguity this contract flags rather than resolves silently

Alex's branch carries **two generations** of nav-shell files, verified by direct inspection, not
assumed identical in vintage:

**Generation A (legacy tokens, closer destination count):** `overlay/desktop_overlay.dart` +
`overlay/desktop_tab_bar.dart` + `overlay/destinations.dart` (`GeniusTabDestinations`, 7 items:
dashboard/transactions/swap/web/markets/news/logs — missing only Settings) +
`overlay/genius_destination.dart`. Uses `GeniusWalletColors.deepBlueCardColor` (hardcoded dark,
**not appearance-aware** — do not carry this token into the re-skin) and `brandGreen`/
`textPrimary60` (both appearance-safe aliases, fine to use).

**Generation B (current design-system tokens, reduced destination count):**
`overlay/mobile_overlay.dart` + `overlay/gw_bottom_nav.dart` (4 items only: Home/Markets/
Activity/Discover — **no Swap, no Settings, no Feedback tab**). Uses
`GeniusWalletColors.brandPrimary` (selected)/`textSecondary` (unselected)/
`GWDecorations.surfaceSheen` (top border gradient)/`GeniusWalletTypography.labelMd` — the same
token vocabulary `theme.dart` now uses app-wide.

**Binding rule: take Generation B's token vocabulary and interaction pattern (selected =
`brandPrimary`, unselected = `textSecondary`, top hairline via `GWDecorations.surfaceSheen`,
`GeniusWalletTypography.labelMd` for tab labels, rounded-pill selection feel), applied to
develop's full 8-destination set — never Generation B's reduced 4-destination list, and never
Generation A's `deepBlueCardColor` background.** There is no single file in either generation that
is both current-token and full-destination-count; composing the re-skin from B's *tokens* onto
A's/develop's *destination set* is the executor's job, not a file to port wholesale. Record this
composition explicitly in the phase's SUMMARY — it is a deliberate synthesis, not an oversight if
it doesn't match either reference file byte-for-byte.

### 2.3 Desktop rail vs. mobile bottom nav — breakpoint, unchanged

Follow develop's existing `GeniusBreakpoints.useDesktopOverlay(context)` /
`GeniusBreakpoints.isMobileApp()` check in the `ShellRoute` builder (`router.dart:210-215`) exactly
as it stands today — **no new breakpoint, no adoption of Alex's `GeniusBreakpoints.medium = 768`
drawer-breakpoint logic for this decision** (that 768 number governs the drawer, §5.1, a separate
concern from the rail/bottom-nav split).

### 2.4 Top app bar / rail chrome — desktop

The desktop top bar (`_DesktopTopBar` today) hosts, left to right: logo, tab destinations, then
(right-aligned) the action row — `DevToolsWidget` (dev-gated, unchanged), `NetworkDropdownSelector`,
`SDKAccountManagerButton`, `AccountDropdownSelector`, `ReownConnectButton`, and the "Buy GNUS"
button. **Every one of these action-row widgets is unchanged in this phase** — they get the
token/type/spacing re-skin their own files need (most already use develop's current, pre-redesign
styling and are themselves candidates for a lighter touch-up), but none is restructured, removed,
or reordered. Background: `GeniusWalletColors.surfaceElevated` (appearance-aware — replaces
`deepBlueCardColor`), height: `GeniusWalletConsts.appBarHeight` (develop's existing **60**, not
Alex's **65** — carried forward from Phase 2's deferral, still not re-opened this phase; this is a
real visual delta between develop and Alex still deliberately unresolved, not this phase's call to
make).

### 2.5 Bottom nav — mobile

Selected item: `brandPrimary` icon + label, `FontWeight.w600`. Unselected: `textSecondary`,
`FontWeight.w500`. Top hairline border: `GeniusWalletColors.borderSubtle` at 0.5px width (Generation
A's `desktop_overlay` and Generation B's `gw_bottom_nav` both use a comparable subtle top border —
consistent enough to standardize on `borderSubtle`). Background: transparent or `GWDecorations.
surfaceSheen`, matching whichever the executor's composed treatment (§2.2) settles on — record the
choice, don't leave it implicit. Touch target: full-width tile per destination (already develop's
`BottomNavigationBar` pattern), minimum 44px height honored by construction.

## 8. Spacing, Typography, Color (inherited from Phases 2–3 — this phase adds no new tokens)

All re-skinned surfaces in this phase consume Phase 2's token classes exclusively
(`GeniusWalletConsts`, `GeniusWalletTypography`, `GeniusWalletColors`, `GeniusWalletElevation`,
`GeniusWalletGradient`, `GeniusWalletMotion`, `GeniusWalletDecorations`) and Phase 3's `gw_*`
primitives — **zero raw hex, zero ad-hoc `Color(0x...)`, zero raw px typography.** This is the
same non-negotiable discipline `03-UI-SPEC.md` §8 established; this phase introduces no new token
values. See `02-UI-SPEC.md` §2-§5 for the full scale.

**Every surface this phase touches must be specified for BOTH light and dark appearance (D-03) —
this is a gate, not a nicety.** A component that only "looks right" in dark mode has not completed
this phase's re-skin.

**Accent (`brandPrimary`, 10%) — reserved for, this phase:** selected nav-rail/bottom-nav item
(icon + label + indicator), `GWButton` primary/gradient fills on Settings/SDK-manager/drawer
