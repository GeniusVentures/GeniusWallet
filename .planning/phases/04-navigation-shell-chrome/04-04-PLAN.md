<objective>
Re-skin the account/wallet drawer (criterion 4) in place — the drawer row, the per-wallet context
menu, and the rename + delete confirmation dialogs — while carrying develop's wallet behaviors intact
(D-07). Delete confirmation is a pure re-skin of an existing dialog, not a behavior addition (D-06,
resolved). Also verify (no code) that stored wallets load at boot (criterion 3) and the network toast
fires (finding 35).

Purpose: Criterion 4 — from the drawer a user can rename/delete a wallet, the keep-one guard fires, a
deleted selected wallet re-selects another, and rows update live; plus criterion 3's boot wallets and
finding 35's toast. Re-skin, never restructure: the logic is develop's and already correct.

Appearance-color access path (04-02 alignment): this drawer surface is one of 04-02's DEFERRED
`migration_surface` readers — 04-02 deferred it precisely because THIS plan rebuilds it. The drawer row
is built by `_buildDrawerRow` (a non-const `ListTile`) inside a `BlocBuilder<AppBloc, AppState>` that
does NOT depend on `Theme`; reading appearance-aware colors from `GeniusWalletColors` static getters
therefore renders STALE on a live toggle while the drawer is open (the 04-02 D-02 failure applies even
though the row is non-const, because no Theme dependency is registered). So all appearance-aware
surface/text/border colors MUST be read via `Theme.of(context).extension<GWColors>() ?? GWColors.dark()`
(the fail-soft pattern from 04-02, lib/theme/gw_colors.dart). Mode-invariant brand/status tokens
(brandPrimary, textOnBrand, statusError) stay on the static getters. GWColors already carries every
appearance-aware field this surface needs (surfaceElevated/surfaceMenu, textPrimary, textPrimary70,
textSecondary, borderSubtle) — no new GWColors field is required.

Output (artifacts this plan produces): a token-correct, appearance-aware `account_dropdown_selector.dart`.
</objective>
