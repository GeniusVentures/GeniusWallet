<objective>
Make `SubmitJobCubit` tell the truth about what happened to the user's money, and split its single
error field into channels that match what the UI has to do about each failure.

Purpose: today a user can burn GNUS on a successful bridge, have the job fail to start, and be left
with a red toast and no transaction hash - the hash exists in a local variable four lines above the
branch that throws it away. Separately, a user holding exactly the job cost is refused, and a user
whose job has not been priced yet is told they do not have enough money. All three are one-branch or
one-character defects sitting behind state that cannot express the distinction.

Output: an outcome discriminator, a preserved bridge hash, three error channels, and a pure CTA
ladder in the house style.
</objective>

<task type="auto" tdd="true">
  <name>Task 1: Preserve the burned-token hash, and say which outcome it belongs to</name>
  <files>lib/submit_job/cubit/submit_job_state.dart, lib/submit_job/cubit/submit_job_cubit.dart, test/submit_job/submit_job_outcome_test.dart</files>
  <behavior>
    - A bridge that fails leaves the outcome marked bridge-failed and both hash fields empty. Nothing
      was spent, so there is nothing to prove.
    - A bridge that succeeds followed by a job that fails to start leaves the outcome marked
      bridged-only AND the bridge hash non-empty. This is the case the shipped code loses.
    - A bridge and a job that both succeed leave the outcome marked done and the transaction hash
      non-empty.
    - The bridged-only outcome does not set the success hash field, so nothing downstream that treats
      a non-empty success hash as proof of a started job is fooled.
    - Resetting returns the outcome to its initial member and empties both hash fields.
  </behavior>
  <action>
`bridgeTokens` at `lib/submit_job/cubit/submit_job_cubit.dart:156-222` has three terminal branches and
they map one to one onto three outcomes the user experiences. Today only two of the three are
representable in state.

Add to `submit_job_state.dart` a non-nullable outcome enum field with four members - not submitted,
done, bridged but not processed, and bridge failed - defaulting to not submitted. Add a separate
non-nullable bridge-hash field defaulting to the empty string. Wire both through the constructor and
`copyWith`.

**A separate field, not a reuse of the existing hash field.** `submit_job_screen.dart:48` treats a
non-empty value in the existing hash field as the signal that the job succeeded. Writing the burned
hash there without a discriminator would raise a success message on a failed job - a worse bug than
the one being fixed. The outcome enum is the discriminator, and a distinct field makes the two
meanings impossible to confuse at a glance.

Now edit the three branches:

At `:195-204`, the bridge itself failed and nothing was spent. Set the outcome to bridge-failed
alongside the existing message.

At `:210-218`, the bridge succeeded and the job did not start. This is the branch that matters. The
hash is bound at `:193`, proven non-null and successful by the guard at `:195`, and is in scope at
`:211`. Pass it into the bridge-hash field, and set the outcome to bridged-but-not-processed,
alongside the existing mapped SDK message.

Add the delayed balance refetch to this branch too. `:220`'s `unawaited(fetchGnusBalanceWithDelay())`
runs only on the success path, but the burn happened here as well - after a burn without a job the
displayed balance is stale and nothing refreshes it. Reuse the existing method at `:225-230` rather
than duplicating its delay.

At `:222`, success. Set the outcome to done alongside the existing hash write.

Fix `resetState` at `:233-243` so it clears the new fields. Note that the existing line passing null
for the error field is dead - `copyWith` cannot clear through null - so do not copy that pattern.
Clear the outcome by passing its initial member and the hash fields by passing empty strings.

Write `test/submit_job/submit_job_outcome_test.dart` covering the five behaviours above. Drive the
cubit with a hand-written fake for the API in the existing house style rather than a mock framework;
the calls the fake must answer are the bridge call and the process call, and the test only needs to
vary their two return values to reach all three branches.

The assertion that carries the most weight is the bridged-only case: it must check the bridge hash is
**non-empty**, not merely that the outcome is set. An implementation that sets the enum and still
drops the hash would leave the user in exactly the position this phase exists to fix.
  </action>
  <verify>
    <automated>flutter test test/submit_job/submit_job_outcome_test.dart</automated>
  </verify>
  <done>
Three code branches set three distinct outcomes. The bridged-only branch writes the bridge hash and
triggers the delayed balance refetch. Reset clears both new fields. All five tests pass.
  </done>

<task type="auto" tdd="true">
  <name>Task 2: Three error channels, the message that was being destroyed, and the file trust boundary</name>
  <files>lib/submit_job/cubit/submit_job_state.dart, lib/submit_job/cubit/submit_job_cubit.dart, test/submit_job/submit_job_errors_test.dart</files>
  <behavior>
    - A picker failure lands on the file channel and no other.
    - A balance, token-info, cost-lookup, precondition or gas-estimate failure lands on the cost
      channel and no other.
    - A failure raised at commit time lands on the submit channel.
    - When the gas estimate fails because the wallet cannot cover gas, the reason that reaches state
      is the underlying one, not a generic replacement.
    - A file larger than the cap is rejected before it is read into memory, with a message naming the
      size problem.
    - Emitting after the cubit is closed does not throw.
  </behavior>
  <action>
Nine call sites in this cubit write failures into one field, and all nine surface under a toast
titled for a file picker (`submit_job_screen.dart:32`). Six of the nine have nothing to do with a file
picker, and two of them fire from `_initialize()` in the constructor - so the first thing a user can
see on opening the flow is a file-picker error raised before any picker existed.

Replace the single field with three non-nullable string fields defaulting to empty, named for what
the UI must do about each. Route the shipped call sites as follows:

The file channel takes `:104`, `:108` and `:110` - user cancelled, invalid JSON, and any other picker
throw. These are the only three that are genuinely the picker.

The cost channel takes `:37`, `:54`, `:89`, `:131` and `:149` - balance fetch, token info, cost
lookup, the missing-preconditions guard and the gas estimate. All five mean the same thing to a user:
the job cannot be priced yet. Plan 06 renders this channel inline next to the cost, not as a toast,
because it describes a state rather than an event.

The submit channel takes `:176`, `:199` and `:214`. The existing process-error field already serves
`:199` and `:214`; fold `:176` into it too. That line is raised inside `bridgeTokens` at commit time
and is today the one place the picker field is written directly rather than through the setter.

Delete the single-field wrapper class at `submit_job_state.dart:59-63`. It holds one string, has no
equality override and no subtype, so every instance compares unequal by identity - which makes the
listener guard at `submit_job_screen.dart:21` fire on every emit including the empty reset, and makes
any value-equality test impossible. Plain strings solve both.

**Stop destroying the gas message.** At `:148-151` the estimate's failure is discarded and replaced
with a generic line. The underlying call runs `createBridgeOutTransaction`, which at
`packages/genius_api/lib/web3/web3.dart:390-395` calls `hasEnoughFundsForGas` and, when the wallet
cannot cover gas, returns a specific error at `web3.dart:399` naming that exact problem. So the ETH
shortfall check already exists and already runs, at estimate time and again at submit time - what is
missing is only that its message reaches the user. Pass the response's own error message through to
the cost channel, falling back to the generic line when it is empty. This is a one-line change that
makes a whole class of failure diagnosable, and it is the reason the plan does NOT widen the GNUS
comparison to account for gas.

**Cap the file before reading it.** `:74-77` reads a user-picked file fully into memory and parses it
on the UI isolate with no size limit. The extension filter at `:69` is not a size. A large or deeply
nested file blocks the UI thread. `CLAUDE.md` names input validation at trust boundaries in the
not-lazy set, and a user-supplied file is a trust boundary. Check the file's length against a
constant before reading, and route an oversized file to the file channel with a message naming the
limit. Keep it to the length check - moving the parse to an isolate is a larger change, so mark the
remaining exposure with a `ponytail:` comment naming the ceiling as a synchronous parse on the UI
isolate and the upgrade path as parsing off-isolate.

**Guard the unguarded emits.** `fetchGnusBalance` guards with a closed check at `:42`, but the emit at
the end of `fetchGnusTokenInfo` and the emit inside the error setter do not. Both are reachable
because `_initialize()` is fired from the constructor at `:26-29` and awaits two network calls. On a
route this rarely bites because the screen stays open; plan 06 puts this cubit behind a drawer, which
a user dismisses far more casually. Add the same guard to every emit in the class.

Write `test/submit_job/submit_job_errors_test.dart` asserting the channel each of the nine origins
lands on, that the underlying gas message survives rather than being replaced, that an oversized file
is refused before it is read, and that an emit after close does not throw.
  </action>
  <verify>
    <automated>flutter test test/submit_job/submit_job_errors_test.dart</automated>
  </verify>
  <done>
Three string channels replace one wrapper object. Nine origins are routed. The gas failure carries
its own reason. Oversized files are refused before being read, with a ponytail naming the remaining
on-isolate parse. Every emit is guarded.
  </done>

  <behavior>

    - A job cost of zero resolves to cost-unknown, never to insufficient funds.
    - A cost above the balance resolves to insufficient funds and carries the shortfall as a number.
    - A failure on the cost channel resolves to cost-error, distinct from cost-unknown.
    - No file chosen resolves to its own rung, ahead of any cost reasoning.
    - Submitting outranks every other rung.
    - Exactly one rung enables the CTA.
  </behavior>
  <action>
Create `lib/submit_job/submit_job_cta_state.dart` as a pure Dart module in the same shape as
`lib/dashboard/bridge/bridge_cta_state.dart`: an enum, a resolver, a label function and an enabled
predicate, with the precedence documented at the top of the file.

Rungs, in precedence order: submitting, no file chosen, cost unknown, cost error, insufficient funds,
ready.

**Two separate bugs live in the one boolean this replaces.** `submit_job_screen.dart:65` computes the
purchasable flag as a cost that is non-zero and strictly less than the balance. Strictly less refuses
a user holding exactly the cost - that is success criterion 4. And folding the zero-cost case into the
same flag means `:167-174` renders an accusation of insufficient funds at a user whose job the app
simply has not priced yet. Separate rungs fix the second; the comparison boundary fixes the first.

The house already has the correct boundary one directory over. `bridge_cta_state.dart:62` uses a
strict greater-than so that exactly-affordable passes, and it is pinned by a named test at
`test/dashboard/bridge/bridge_cta_state_test.dart:59-69`. Submit-job is the outlier, not the norm.
Say so in the file's doc comment and point at that test.

Have the insufficient-funds path carry the shortfall as a number the UI can print, computed as the
cost minus the balance. The copy shows the figure, not the word.

Handle the type boundary explicitly. The cost is an `int` and the balance is a `double`
(`submit_job_state.dart:7, 10`). Comparing them is legal Dart and needs no cast, but a balance
arriving as a value fractionally below a whole number from a unit conversion would still refuse a
user who has exactly enough. Round both to a common precision before comparing, and mark the choice
with a `ponytail:` comment naming the ceiling - a fixed-precision compare on a value the SDK produces
- and the upgrade path, which is to compare in the token's smallest unit.

Write `test/submit_job/submit_job_cta_state_test.dart` as a near-clone of
`test/dashboard/bridge/bridge_cta_state_test.dart` - no mocks, no widget pump. Include the
exactly-affordable case as its own named test, mirroring the bridge test's wording so the two read as
a pair. Include the exhaustive-enum guard from that file's closing group: collect every enum member
the enabled predicate accepts into a Set and assert it contains only the ready rung. That single
assertion is what stops a later rung from being added and silently enabling the button.
