<objective>
Move the compute node's truth out of a widget's private `State` and into `AppBloc`, and give the
state enough shape to tell apart three conditions it currently collapses into one boolean.

Purpose: three of the eight states plan 01 defined cannot be reached from the dashboard today.
*Status unavailable* needs a flag that says the last read threw. *Starting up* needs an
initialization feed that is currently polled inside `SGNUSConnectionState`'s private fields, where no
sibling widget can read it. *Job complete* needs a timestamp nothing records. All three are data
problems, not drawing problems.

Output: `AppState` carries the compute feed; `RetryProcessingStatus` re-arms the timer; the dev
bubble can fake the two new feeds so the states can be walked.
</objective>

<task type="auto" tdd="true">
  <name>Task 1: Give AppState three outcomes where it has one boolean, and a retry that re-arms</name>
  <files>lib/bloc/app_state.dart, lib/bloc/app_event.dart, lib/bloc/app_bloc.dart</files>
  <behavior>
    - A processing read that throws leaves the feed flagged unavailable, not merely not-processing.
    - A healthy transition out of processing leaves the feed flagged live, so unavailable and idle
      are different data rather than merely different pixels.
    - Dispatching the retry event re-arms the polling timer and clears the unavailable flag back to
      its pre-read value.
    - The node reporting processing-disabled is distinguishable from the node reporting idle.
    - Processing transitioning from true to false records a completion timestamp; a transition in the
      other direction does not.
  </behavior>
  <action>
Three edits, all in the `part of` family rooted at `lib/bloc/app_bloc.dart`.

**In `app_state.dart`.** Add an enum with three members describing the processing feed: never ticked,
a tick landed, and the last read threw. Add it as a non-nullable `AppState` field defaulting to the
never-ticked member, wire it through the constructor, `copyWith` and the `props` list at
`app_state.dart:89-105`.

Non-nullable with a default is not a style preference here. `AppState.copyWith` is `x ?? this.x` on
every field (`app_state.dart:69-86`), so passing null is a no-op rather than a clear. That single
property is the mechanism behind the stale-percentage bug this phase closes; a nullable flag added
now would inherit it. State the reason in a comment on the field so the next person adding a field
sees it.

Add a nullable `DateTime` field recording when processing last finished. This one is genuinely
nullable because "no job has finished this session" is a real value, but it is only ever written, and
never needs clearing through `copyWith`, so the no-op trap does not apply. Add it to `props`.

Add a non-nullable field carrying the node's processing status as its own tri-state rather than as a
derived boolean. Keep the existing `isProcessing` boolean as well - it has other consumers and
removing it is out of this phase's fence.

**In `app_event.dart`.** Add a retry event class. The file is a plain `abstract class AppEvent` with
no Equatable (`app_event.dart:3`), so match that: an empty class, nothing more.

**In `app_bloc.dart`.** Register a handler for the new event whose entire body re-arms the poll by
calling `_startProcessingPolling()` and emits the feed flag back to its never-ticked value so the UI
stops showing the error state before the first new tick lands.

Re-arming is safe and this is proven in production rather than inferred. `_startProcessingPolling()`
at `app_bloc.dart:135-141` cancels before it re-creates, so it is idempotent by construction and
cannot leak a timer. It is already called from `_onLoadWallets` at `app_bloc.dart:123`, which
pull-to-refresh dispatches on every pull (`dashboard_screen.dart:112`). The path is load-bearing
today. Say so in a comment above the handler.

Rewrite the `catch` at `app_bloc.dart:192-195`. Today it cancels the timer permanently and emits a
state byte-identical to a healthy stop, which is precisely why a dead feed and an idle node render
the same. Keep the cancel - a feed that throws should stop hammering the FFI - but add the
unavailable flag to that same emit. That addition is the whole fix; without it the two states cannot
differ.

In the success path at `app_bloc.dart:178-191`, set the feed flag to the tick-landed value, carry the
node's tri-state status through instead of discarding it, and detect the completion edge: when the
previous state was processing and the new reading is not, write the completion timestamp. Compare
against `state.isProcessing` before the emit; after the emit the previous value is gone.

Leave the percentage emit inside its existing `if` branch. Do not attempt to null it on stop - the
`copyWith` trap makes that impossible, and plan 01's resolver already refuses to render a bar from a
state that is not processing. Fixing it at the emit would be fixing the wrong branch: the exception
path at `:194` already zeroes it, and the clean path at `:185` is the one that leaks. Put a short
comment at the emit pointing at the resolver as the place the rule is enforced, so nobody "fixes"
this later by nulling a field that cannot be nulled.
  </action>

<task type="auto" tdd="true">
  <name>Task 2: Poll the initialization feed from the bloc and carry the node's own message</name>
  <files>lib/bloc/app_bloc.dart, lib/bloc/app_state.dart, lib/bloc/app_event.dart</files>
  <behavior>
    - A tick of the initialization poll writes both the percentage and the node's message into state.
    - The poll stops once initialization reports complete, and does not restart on its own.
    - A throw from the initialization read leaves the previous values intact rather than crashing or
      zeroing them.
  </behavior>
  <action>
Add a second timer to `AppBloc` that polls `api.getInitializationStatus()` and writes both fields of
the result into `AppState`: the percentage and the message.

**Interval: 3 seconds.** Match `sgnus_connection_widget.dart:42`, which is the only shipped consumer
of this feed and therefore the only measured cadence for it. Do not use the 1000ms of
`_processingTimer` (`app_bloc.dart:138`) - that belongs to a different feed, and conflating the two
is an error that has already propagated through three planning documents.

Carry the message. `GeniusInitStatus` has always had it
(`packages/genius_api/lib/src/genius_api.dart:80-86`, populated at `:1216-1222`) and
`sgnus_connection_widget.dart:47-49` reads the percentage and drops the message on the floor. It is
the only honest sub-line the starting-up state has - the trace in
`.planning/sketches/015-boot-loading-sequence/README.md:71-82` shows it carrying real strings naming
the migration step and the service being initialised.

Copy the shipped poll's two lifecycle rules exactly, because both are load-bearing:

Cancel the timer once the percentage reaches 1.0 and do not restart it, mirroring
`sgnus_connection_widget.dart:50-53`. Initialization happens once per process.

Wrap the read in a `try`/`catch` that swallows and retries next tick, mirroring
`sgnus_connection_widget.dart:56-58`. `getInitializationStatus()` is a raw FFI call with no fail-soft
wrapper - unlike `getNodeState()` and `getTransactionManagerState()`, which route through mapping
functions with their own guards - so the caller is the only guard there is. Note that it also frees a
native string on every call (`genius_api.dart:1219`), so a throw between the read and the free is a
real path, not a theoretical one.

Cancel this timer in `close()` alongside `_processingTimer` at `app_bloc.dart:452-457`.

**Two decisions to record in the SUMMARY rather than leave implicit.**

First: use `getInitializationStatus()`, not `getNodeState()`. `getNodeState()` is tempting - it
enumerates eight explicit lifecycle values instead of a float, it is already fail-soft through
`_mapNodeState`, and being an enum it cannot stall at a percentage the way the shipped ring does. It
also has **zero callers anywhere in `lib/` or `packages/`** (verified: the only match is its own
definition at `genius_api.dart:1230`), so its runtime behaviour is entirely unverified. Planning on
it would require a device spike first, and a spike needs a live node and a valid macOS signing
profile - neither is a dependency this phase should acquire. The initialization feed, by contrast,
has a captured trace showing exactly what it returns. Choose the proven feed and record
`getNodeState()` as the better long-term source once someone has called it once.

Second: **the disconnected state needs no connectivity work.** `14-RESEARCH.md:713` lists state 09 as
blocked on `connectivity_plus` plumbing, reading it as "device offline". The design contract's copy
settles it the other way - `14-UI-SPEC.md:235` renders the sub-line as not connected to the SGNUS
network, and `14-UI-SPEC.md:200` resolves the state from the SGNUS connection stream's own
`isConnected` field. That stream is **already consumed directly in the panel's own file** at
`lib/components/wallet_overview.dart:172`, and `SGNUSConnection` carries `isConnected` at
`packages/genius_api/lib/models/sgnus_connection.dart:11`. So the state is free. Do not add a
connectivity stream; it would be dead code, and `connectivity_plus` being pre-installed is not a
reason to consume it.
  </action>

| T-14-04 | Denial of service | `_processingTimer` after a throw | medium | mitigate | The timer still cancels on a throw so a failing FFI call is not hammered once per second, but the retry event gives the user an explicit way back.
