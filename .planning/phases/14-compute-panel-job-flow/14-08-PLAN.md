  <name>Task 3: Raise the one shipped capability the locked design has no slot for</name>

  <action>
**This task raises a decision; it does not take one.** Do not delete a user capability on a planner's
say-so.

`lib/components/wallet_overview.dart` ships a two-option toggle at `:192-232`, driven by a
`useMinions` flag at `:34`, that switches the balance readout between GNUS and minions. It changes
the value at `lib/wallets/view/genius_balance_display.dart:33` and `:49` and the unit suffix at `:89`.
It is a real, reachable user capability on this exact card today.

**The locked design has no slot for it.** The twin-tile tree at `14-UI-SPEC.md:296-322` contains a
kicker, two tiles and an action, and neither the state table nor the copy contract mentions a unit
toggle. Nor can it simply be added: the toggle's own constraints give it a 36-pixel minimum height,
and plan 07 measured the worst state at 268 against a 274 budget - six pixels. It does not fit, and
the one padding lever that bought the budget back is already spent.

**And the capability does not survive elsewhere.** There is a near-identical file,
`lib/components/wallets_overview.dart`, declaring the same class names and carrying its own copy of
the toggle at `:155-159`, which makes it look like a fallback. It is not: its only importer is
`lib/dev/generated_closure_canary.dart`, a dev canary. Nothing mounts it. So dropping the toggle here
drops it from the running app.

That makes this a capability removal, which `REQUIREMENTS.md:66-69` places explicitly outside the
re-skin fence and reserves for a product decision.

## DECIDED 2026-07-29 by Jakub - the task now takes the decision, it does not raise it

**The balance tile's existing unit suffix becomes the toggle.** The 200x36 `ToggleButtons` block is
deleted; the unit text already rendered beside the balance is what the user taps to switch between
GNUS and minions. The capability survives, the 36px block does not.

**Correct the cost claim before building.** This resolution was first proposed - by the planner and
by the orchestrator - as costing no height. **That is wrong, and it is wrong for exactly the reason
this project already hit on the coin page's action glyphs:** Flutter sizes a tap target in layout, so
a 12px text suffix cannot become a tap target without growing to the WCAG 2.5.8 (AA) minimum of
24x24. The sub-line is 16px today. That is **+8px, not 0**.

The 8px is expected to be available, and the reason is structural rather than lucky: the `≈ $`
sub-line is dropped in precisely the states where the compute bar renders - the tall ones. In every
state where the suffix exists at all, the card is shorter than the 268px worst case. **Measure this;
do not assume it.** If any state carrying the suffix exceeds 274px, stop and report rather than
shaving another token - the padding lever is already spent, and the next thing to give would be a
locked decision.

Do this, in order:

1. Build the panel to the locked design, without the `ToggleButtons` block.
2. Make the unit suffix an interactive control with a tap target of at least 24x24, keeping the
   existing `useMinions` plumbing (`genius_balance_display.dart:33`, `:49`, `:89`) untouched - this
   is a control swap, not a behaviour change.
3. Extend the per-state height proof from plan 07 to cover the suffix-bearing states with the
   enlarged target. A state over 274px is a failure, not a rounding error.
4. The control must be reachable and operable by keyboard and screen reader, and must announce which
   unit is currently active. A tappable word with no semantics is worse than the block it replaced.

Record the decision and the corrected arithmetic in this plan's SUMMARY under its own heading. No
todo is filed - the question is answered.
