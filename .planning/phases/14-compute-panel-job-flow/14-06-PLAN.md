<objective>
Turn the job request from a flat form ending in a toast full of hex into a five-step flow whose result
is a step, and render it in both hosts.

Purpose: the success hash today is unrecoverable by construction - the screen resets before the toast
is raised, so the hash lives only in a fading toast body. And when the bridge succeeds but the job
does not start, the user is shown a red toast and keeps nothing at all. A step list fixes both,
because a step stays on screen until the user dismisses it.

Output: `JobStepList`, the five step bodies including three terminal states, a drawer host, and
`/submit_job` re-skinned as the full-screen host rendering the same bodies.
</objective>

  <action>
**The drawer host.** Create `lib/submit_job/view/job_drawer.dart` with a static show method that takes
a `BuildContext` and, explicitly, the cubit to use. Not a context-only signature - passing the cubit
in is what makes the hazard below impossible to get wrong.

Two provider facts that will otherwise be got wrong, neither of which has a single example to copy
anywhere in this repo:

The cubit is created per route at `lib/navigation/router.dart:299-312`, which is below the root
navigator. `ResponsiveDrawer.show` pushes on the **root** navigator (`responsive_drawer.dart:99`), so
a drawer body sees only providers mounted above `MaterialApp.router`. The app-level bloc, the wallet
details cubit and the API all qualify (`main.dart:325-341`); this cubit does not. **All twenty
existing drawer call sites either use a root-level provider or hold plain local state - not one
provides a bloc into a drawer, so there is no in-repo pattern to imitate and nothing will remind
anyone.** Wrap **both** the body and the footer in a value provider around the passed-in cubit. Two
separate subtrees are handed to the shell (`responsive_drawer.dart:321, 331`), so wrapping only the
body leaves the footer unable to resolve it, and the failure surfaces as a provider-not-found the
moment the user reaches a footer action.

**Do not create the cubit inside the drawer.** Dismissibility and drag are fixed when the drawer opens
(`responsive_drawer.dart:100-101`) and cannot be flipped mid-flight, so a barrier tap during the
in-flight step would destroy a drawer-owned cubit - and with it the bridge hash. That recreates,
exactly, the unrecoverable-hash bug this phase exists to close. The caller owns the cubit's lifetime;
plan 08 mounts it in the dashboard subtree. Put both of these reasons in the file's doc comment.

Because the caller owns the cubit, this host must NOT dispose it on completion. That is the opposite
of the house idiom at `swap_settings_drawer.dart:66-69`, which disposes what it creates - so state
explicitly that this drawer creates nothing and therefore disposes nothing, or someone will add the
disposal by analogy and close a cubit the dashboard still holds.

Any pop from inside this drawer must resolve on the root navigator, or it pops the route and dumps
the user on the dashboard mid-flow. `swap_settings_drawer.dart:52-63` records what that cost when it
was missed; on this flow it would cost a user their burned-token receipt.

**The full-screen host.** Rewrite `lib/submit_job/view/submit_job_screen.dart` to render the same step
list and the same bodies, per `14-UI-SPEC.md:739-758`. Adopt the standard screen frame with a content
cap of 640 and the standard page header. This deletes the hand-rolled frame the file already builds -
a constrained box at the large breakpoint wrapped in a scroll view inside an alignment widget at
`:83-88` - rather than importing a new one, which is why the deferred screen-frame sweep's objection
does not apply here. Narrow the cap to 640 because a five-step vertical list at the large breakpoint
is a very long line.

Delete the two toast listeners at `:19-57`. Errors now render inline at the step that produced them,
and the result is a step. The route keeps its own cubit instance from the router; nothing about the
route registration changes.

**The tests.** `test/submit_job/job_flow_test.dart`. Prove all three terminals are reachable and each
renders its own content, that the bridged-only terminal exposes a non-empty bridge hash and offers no
retry action, that the purchase boundary allows a cost equal to the balance and that a zero cost
renders the neutral line rather than an accusation.

Add one test for the provider hazard specifically: pump the drawer's body and footer subtrees and
assert the cubit resolves in both. It is the failure with no precedent in this repo, so it is the one
most likely to reach a user.
  </action>
