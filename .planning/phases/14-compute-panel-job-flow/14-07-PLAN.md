<objective>
Build the compute panel itself - the twin-tile layout, the status row, the bar - as a widget that
takes a view model and renders it, and prove by test that it fits its height budget and clears
contrast in both themes.

Purpose: the height budget is this phase's binding constraint and it has six pixels of slack. The
success criterion says the fit must be measured, not estimated. That is only possible without the
visual-regression tooling that was declined twice if the panel is a pure renderer taking plain values,
which plan 01 made it.

Output: `ComputePanel` plus the two tests that gate it.
</objective>

  <action>
Create `lib/dashboard/compute/compute_panel.dart` exporting `ComputePanel`, a stateless widget taking
the view model from plan 01 plus the balance value, the fiat string and the callbacks the links and
the action fire. **It reads no bloc and no stream.** Everything it needs arrives as a parameter. That
constraint is what makes Task 2's height test and Task 3's contrast test possible at all - state
that in the class doc comment so nobody later "simplifies" it by moving a bloc read inside.

Build the tree in `14-UI-SPEC.md:296-322` exactly. Both tiles use the recipe at `14-UI-SPEC.md:114-125`:
the sunken fill, a subtle hairline, not elevated, the medium radius, and horizontal padding of 12
with **vertical padding of 8**.

**That vertical 8 is the lever the whole budget rests on.** With 12 on both axes the tallest state
lands at 284 against a 274 budget - a 10px overflow, which is what the inherited arithmetic was
hiding once the real component metrics and the two card borders are counted. Both values sit on the
4-point grid. Put a comment at the padding naming it as load-bearing and pointing at the height test,
because it reads like an arbitrary token and someone will otherwise normalise it to the sibling value.

Map the view model's dot role onto theme tokens here, where the theme is in scope. The module the
roles come from is deliberately Flutter-free.

**The amber question, and the default to take.** The warning role has no theme token - the colour set
carries success and error but not warning, and the raw warning primitive is fill-tuned: it measures
about 12:1 on the dark card but only about 1.6:1 on a light one, which means the dot is simply absent
in light mode. The warning-note component hit this first and solved it with a locally darkened amber,
and its own comment records the ceiling and names an appearance-aware token as the upgrade path.

Adding that token is the better fix, and it is also an edit to a file another phase owns, which
`14-UI-SPEC.md:579-585` says must be raised before it is taken. **No such approval has been given, so
take the documented default:** a file-local constant in this panel mirroring the warning note's
derivation, selected on appearance exactly as that component does. Mark it with a `ponytail:` naming
the ceiling - a third hand-derivation of one value - and the upgrade path, which is the shared token.
Do not ship the raw fill-tuned primitive as a light-mode dot. Record the promotion as a follow-up in
the SUMMARY.

Four height rules from `14-UI-SPEC.md:174-186` that must be in the code, not only in the spec:

Every sub-line is single-line with ellipsis overflow. A wrap adds a line box and blows the budget
silently, and the longest sub-line belongs to a state with six pixels of slack.

A sub-line carrying an inline link is a row of a flexible truncating text plus the link, not one text
run. The reason truncates; the affordance never does.

The status row stays at an 18-pixel line box. That means the label and the trailing value both render
at the medium label metric. A trailing value at the small body metric is 20 pixels and silently costs
two pixels in every state that has one. `GWStatusDot` from plan 03 already enforces this - use it
rather than composing a row by hand.

Do not force the shipped stat-tile component onto either tile. It renders a string value at a fixed
type; the balance tile's value is an animated number at 32 and the compute tile's is a status row.
Compose the same shape - dense kicker, 3px gap, value - by hand. This is a fit correction, not a
design change, and the spec says so at `14-UI-SPEC.md:139-143`.

Build the 4px bar as a **private** widget in this same file. It has exactly one consumer, so it does
not clear the promotion bar - the one bar-like thing that already ships is a marker positioned on a
track and cannot migrate to a fill. Take a required, non-nullable value: there is no indeterminate
mode and no null, so a caller with no live reading cannot construct it. That is the rule from
`14-UI-SPEC.md:263-265` carried by the API rather than by a comment. Lift the track recipe from the
shipped marker track so the app has one track treatment, and degrade the fill on light exactly the
way the shipped gradient-to-flat helper does at `lib/theme/genius_wallet_gradient.dart:44-51` - the
gradient measures under the 3:1 graphical floor on a light card.

Render a zero balance as a normal number in the primary text token. `wallet_overview.dart:141-148`
paints it as an error today; a wallet with no funds is not a broken wallet, and that is one of the
five bugs this phase closes.

The action is the single filled control on this surface - starting a job spends GNUS irreversibly, so
it earns the fill, and everything else in the card is an inline link. Use the small size: it is 44
logical pixels, which is the touch floor, and the medium size costs four more that the budget does
not have. When the view model disables it, render it disabled rather than hiding it. The shipped
button vanishes entirely when the wallet is not the linked one, taking the section's primary action
away with no explanation, while holding both addresses that would explain it. Disabled controls are
exempt from the contrast minimum, which is exactly why the reason and the way out live in the compute
tile's sub-line instead.
  </action>

  <files>test/dashboard/compute_panel_height_test.dart</files>
  <behavior>
    - Rendered inside the dashboard's own container and its 300-pixel cap, every state measures within

    - The panel content itself measures within 274 in every state.
    - No state overflows at a narrow panel width.

  <action>
Write `test/dashboard/compute_panel_height_test.dart` as an ordinary widget test in the style of
`test/dashboard/transactions_page_frame_test.dart` and `test/dashboard/transaction_filter_rail_test.dart`.

Iterate every member of `ComputeState.values`, build the view model for each, pump the panel wrapped
in `DashboardScrollContainer` at a realistic panel width with an **unbounded** height, and assert two
things per state: the container measures at most 300, and the panel inside it measures at most 274.

Assert on both numbers rather than only the inner one. The outer assertion is the real constraint and
cannot be got wrong by arithmetic; the inner one is the diagnostic that tells you which side of the
container's inset a regression came from.

**Derive 274 in a comment above the assertion rather than leaving it as a magic number**, because it
is not the number the planning documents inherited. The dashboard caps the card at 300
(`dashboard_screen.dart:212`, and again at `:293` and `:298` in the single-column layout).
`DashboardScrollContainer` is a `Container` carrying a surface decoration whose border is one pixel
(`genius_wallet_decorations.dart:99-102`), and a `Container` folds its decoration's border dimensions
into its own padding - so the border costs two pixels on top of the 12-pixel inset applied on each
side by the `Padding` at `dashboard_screen.dart:342`. That is 300 minus 2 minus 24, which is **274 and
not the 276 carried by the roadmap, the sketches and the context document**. Losing those two pixels
matters because the inherited design had three pixels of slack.

Pump each state at two widths: a realistic one for the two-column dashboard layout, where the panel is
the smaller of two flexed children, and a deliberately narrow one. The narrow case proves no sub-line
wraps into a second line box, which is the failure mode the single-line rules exist to prevent and
the one that would consume the remaining slack invisibly.

Use the default text scale. The card keeps a scrolling safety net at its host, so a larger scale is
absorbed there rather than being this test's problem - note that in a comment so nobody widens the
test into territory the net already covers.

If a state exceeds the budget, **do not raise the assertion to match.** The tile padding lever is
already spent; the next move is a design change and belongs back with the design contract.
  </action>
