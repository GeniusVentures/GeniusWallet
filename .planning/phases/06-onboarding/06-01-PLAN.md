<objective>
Lay the onboarding chrome every later step screen mounts into, before any step is re-skinned: the
`/landing_screen` entry point (UI-SPEC §4.1) and the two flow shells' AppBar (§4.2). Doing these first
means each subsequent step re-skin (06-02..06-05) lands inside an already-correct entry surface and
step-bar, instead of a walk that shows a re-skinned step sitting under an un-skinned Material AppBar
on a permanently-dark screen.

Purpose: ROADMAP Phase 6 criterion 1's entry half — a fresh-install user reaching a redesigned
create/import choice. This plan owns the phase's one genuine hardcoded-dark-constant trap
(`Scaffold(backgroundColor: GeniusWalletColors.deepBlue)`), gives `GWMeshBackground` (Phase 3 §2.6,
zero callers to date) its first real consumer, and puts the inherited `GWButtonVariant.secondary`
light-mode defect on the record without absorbing it.

Re-skin, never restructure (UI-SPEC §1 — the precondition every other section of the contract depends
on): Alex's onboarding screens are a breakpoint-driven split-widget redesign (two parallel widget trees
per screen, `AppScreenWithHeaderDesktop`/`Mobile`, independent layout arithmetic). That is a structural
redesign and it is DISQUALIFIED as a structural reference. develop's single
`Center`/`ConstrainedBox`/`Column` tree is LOCKED. Take from Alex's screens only the isolated
visual/component choices §4.1 names — the `GWButton` variant mapping and `GWMeshBackground` — never the
surrounding split.

Two deliberate deviations from the letter of UI-SPEC §4.1/§4.2, recorded here rather than made silently:
1. §4.1 says set `Scaffold(backgroundColor: Colors.transparent)` behind the mesh. This plan instead
   DELETES the `backgroundColor:` argument entirely. `GWMeshBackground` paints its own opaque
   `ColoredBox` base at `StackFit.expand`, so nothing shows through either way — but deleting the
   argument leaves the Scaffold on Phase 4's wired, appearance-aware `scaffoldBackgroundColor`, which
   means the §9.1 fallback (drop the mesh) degrades to a correct surface instead of a see-through one,
   and it keeps §7's zero-raw-`Colors.*` rule intact on this file.
2. The AppBar's `backgroundColor: Colors.transparent` (§4.2) IS kept, and is the ONE sanctioned raw
   `Colors.*` in this phase — there is no token for "no fill", and `Colors.transparent` is an absence
   of color rather than a palette choice. Recorded as an exception, not an oversight.

Appearance-color access path (04-02/04-04 discipline): any appearance-aware color read in these files
MUST go through `final gw = Theme.of(context).extension<GWColors>() ?? GWColors.dark();` so a
const-instanced widget re-skins LIVE on an in-place toggle. Mode-invariant brand/status tokens stay on
the `GeniusWalletColors` static getters.

Output: a token-correct, appearance-correct `/landing_screen`; two flat, transparent flow step-bars;
and a walked, recorded decision on whether the mesh survives light mode.
</objective>
