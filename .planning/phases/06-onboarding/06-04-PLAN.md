<amendment date="2026-07-21">
**This plan was amended same-day, before execution, by `.planning/AUDIT-260721-parallel-investigation.md`
(Q2: "Q2 supersedes part of the just-committed Phase 6 plan").** The audit ran
`grep -rn "autocorrect:|enableSuggestions:|enableIMEPersonalizedLearning:" lib/` against the repo as
committed and got **zero matches app-wide** — independently re-verified during this amendment with
`grep -rn "autocorrect:|enableSuggestions:|enableIMEPersonalizedLearning:|textCapitalization:" lib/`,
also zero matches. The baseline this plan hardens against is: **no IME hardening exists anywhere in
the app**, not "PasteField is the one gap."

What was wrong with the plan as originally committed:
1. **It prescribed only two of the four flags that matter.** `autocorrect: false` and
   `enableSuggestions: false` alone leave `enableIMEPersonalizedLearning` at Flutter's default of
   `true` — and that flag, not `autocorrect`, is the one that maps to Android's
   `IME_FLAG_NO_PERSONALIZED_LEARNING`, the actual switch that stops the keyboard's learning store
   from retaining typed key material. Shipping the other two without it produces the *appearance* of
   hardening while leaving the real leak open — worse than doing nothing, because it reads as done.
   `textCapitalization: TextCapitalization.none` was also missing.
2. **It covered one field on one file** (`paste_field.dart`'s own `TextFormField`) when a direct read
   of the code turned up three key-bearing TYPED-INPUT fields across two files: `paste_field.dart`'s
   `TextFormField`, and two `GWTextField`-routed dialogs in `lib/account/sdk_account_manager.dart`
   ("Add Account with Mnemonic" and "Add Account with Private Key", :415-419 and :460-463).

Two other locations the audit named — `sdk_account_manager.dart:288-290` and
`recovery_phrase_screen.dart:104` — were read directly during this amendment and are **excluded**:
neither is a typed-input field. `sdk_account_manager.dart:288-290` is
`Clipboard.setData(ClipboardData(text: mnemonic))`, fired from a `MenuItemButton` labelled
"Copy mnemonic" — it copies an ALREADY-KNOWN mnemonic OUT to the clipboard; there is no
`TextFormField` and no IME surface at that line. `recovery_phrase_screen.dart:104` is likewise a
`TextButton.icon` calling `FlutterClipboard.copy(...)` on the already-generated recovery phrase — a
copy action, not an entry field. Neither line has anything for `autocorrect` / `enableSuggestions` /
`enableIMEPersonalizedLearning` / `textCapitalization` to attach to. (The audit's clipboard-timer /
copy-confirmation recommendation for these two copy actions is a distinct, unaddressed item — out of
scope for this amendment, which is IME-hardening-only; not silently dropped, just not this plan's job.)

Net effect of this amendment: Task 1 now applies all four flags to `paste_field.dart` (file scope
unchanged); a NEW Task 2 extends `GWTextField` with the same four flags as additive,
default-preserving optional parameters and applies the hardened values at the two
`sdk_account_manager.dart` dialogs; the former Task 2 (`import_security_screen.dart` re-skin) is
renumbered Task 3; the former Task 3 (human-verify checkpoint) is renumbered Task 4 and extended to
walk the two SDK-account dialogs against a real IME as well. `files_modified`, `must_haves`, the
threat register (`T-06-04-01`), and the `<verification>`/`<success_criteria>` gates below are all
updated to match, so no gate contradicts the plan body.
</amendment>

order relative to Task 1, but stays second so both hardening tasks land as a contiguous security-first
block before the re-skin work (former Task 2, now Task 3) begins.

**The key-bearing-field hardening is PLANNED, not deferred — and it is a deliberate behavior change on
a port.** UI-SPEC §3.6 recommends the (now-superseded, two-flag, one-file) version of it without
mandating it, and §9.2 allows filing a todo instead. This plan takes the stronger option, for reasons
worth stating rather than assuming:
- `PasteField`'s `TextFormField`, and the two `GWTextField` dialogs in `sdk_account_manager.dart`, are
  where a user TYPES OR PASTES an existing mnemonic or private key. Flutter defaults `autocorrect`,
  `enableSuggestions` AND `enableIMEPersonalizedLearning` to `true` (and `textCapitalization` to
  `sentences`), so that key material can be handed to the OS predictive-text / spell-check /
  capitalization-assist / IME-learning system while being entered. `enableIMEPersonalizedLearning` is
  the one that actually matters: it maps to Android's `IME_FLAG_NO_PERSONALIZED_LEARNING`, the real
  switch on the learning store. On a desktop wallet this is a real, if quiet, key-material leak —
  and, per the AMENDED baseline above, a leak on every key-bearing field in the app, not one.
- The phase goal is "create or import a wallet **with no loss of key safety**", and SCR-02 names key
  safety explicitly. AGENTS.md's laziness rule carves out security by name.
- On `PasteField`, the change is four named parameters on a `TextFormField` that already exists. No
  structure moves, no IA changes, no copy changes, no widget is swapped to obtain it. `PasteField`
  itself still cannot be obtained by a `GWTextField` swap — its `Stack`/`Positioned` structure is
  locked (§1) regardless of this amendment — so its fix stays directly on its own `TextFormField`,
  the minimal, local option (§4.7).
- On the two `sdk_account_manager.dart` dialogs, which already use `GWTextField` deliberately (their
  own SECURITY V6 comments call it "a pure presentation-layer wrapper... it never reads/logs the
  controller's value"), the minimal, consistent fix is to add the same four parameters to
  `GWTextField` ITSELF as additive opt-ins — every existing call site keeps Flutter's stock defaults
  unless it explicitly opts in, so this is non-breaking for every other `GWTextField` /
  `GWPasswordField` / `GWSearchField` caller in the app (Task 2).
It is nonetheless a behavior addition, not a pure re-skin, so it is recorded here, in the task actions,
in the threat register, and must be restated in the SUMMARY.

Re-skin, never restructure (§1): develop's `Center`/`ConstrainedBox(small * 0.8)`/`Column` tree,
`PasteField`'s `Stack` + `Positioned` paste-button layout, the four-tab `DefaultTabController` shape and
the `Form`/`GlobalKey` validation wiring are all locked. Alex's `paste_field.dart` is a READ-ONLY
reference for its container decoration only.

Appearance-color access path (04-02/04-04 discipline): appearance-aware colors read via
`final gw = Theme.of(context).extension<GWColors>() ?? GWColors.dark();`; `brandPrimary` as a CURSOR
colour is mode-invariant and stays on the static getter (a cursor is decorative, not text-on-fill, so
the light-mode brand-as-text trap does not apply).

Output: a hardened, token-correct `PasteField` and a token-correct four-tab import screen, with every
import dispatch, validator and failure surface preserved.
</objective>
