# Phase 6 — UI Design Contract

> Visual and interaction contract for onboarding: create-wallet, import-wallet, recovery-phrase,
> verify, legal, select-wallet-type, and PIN creation/confirmation. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker.

**Framing.** Like Phases 2–5, this is a **port of an already-authored, adopted design system** —
not a design exercise. Every visual value below is extracted from Alex's `GeniusWallet-3514`
reference worktree and Phases 2–4's already-landed token/component/theme layers. **This is also
the highest-consequence surface in the whole port** — it is where a seed phrase and a PIN exist in
plaintext in memory and on screen. Where the "re-skin, never restructure" rule and the "protect key
material" rule appear to pull in different directions, key safety wins; §2 makes every such call
explicit rather than leaving it implicit in a diff.

**No `06-CONTEXT.md` and no `06-RESEARCH.md` exist for this phase.** Every decision below is
either (a) inherited from a binding project convention, (b) verified directly from develop's and
Alex's source, or (c) a judgment call this document states and justifies inline rather than
silently making. §10 lists the handful of genuine open questions this research could not resolve
from code alone.

## 1. The single most important finding — Alex's onboarding screens are NOT the re-skin reference for structure

Verified by direct inspection of every file under `GeniusWallet-3514/lib/onboarding/`, not
assumed: every one of Alex's onboarding screens (`recovery_phrase_screen.dart`,
`verify_recovery_phrase_screen.dart`, `legal_screen.dart`, `import_security_screen.dart`,
`pin_screen.dart`, and the landing screen) is built as a **breakpoint-driven split-widget
redesign** — a `LayoutBuilder` that renders an entirely separate widget tree for
`GeniusBreakpoints.useDesktopLayout(context)` true vs false (e.g.
`_RecoveryPhraseViewDesktop`/`_RecoveryPhraseViewMobile`, each with its own state class,
`AppScreenWithHeaderDesktop`/`AppScreenWithHeaderMobile` wrapper, and independent layout
arithmetic). This is a genuine **structural** redesign, not a token-only skin: two parallel widget
trees per screen where develop has one.

**This is disqualified as a structural reference by the binding project convention "Re-skin, never
restructure"** (this phase's `<binding_project_conventions>`, mirroring the GAP treatment rule
REQUIREMENTS.md already applies to GAP-02..06): "Behavior, routing and widget structure that
develop ships stay as they are; only the skin changes." Develop's onboarding screens are a single
`Center(child: ConstrainedBox(child: Column(...)))` tree with no breakpoint split anywhere in
`lib/onboarding/`. Adopting Alex's desktop/mobile split would be a structural change with no
requirement forcing it — none of ROADMAP Phase 6's 4 success criteria ask for a responsive
relayout, and REQUIREMENTS.md's GAP treatment test ("moving or reordering items... If applying the
design language requires one of these to look right, stop, leave that part as-is") applies here by
the same logic Phase 5 §1 used to disqualify Alex's dashboard IA.

**Binding rule: develop's existing single-tree structure is locked for every onboarding screen.**
Keep the `Center`/`ConstrainedBox`/`Column` skeleton, the `Scaffold(appBar: AppBar())` wrapper each
flow (`ExistingWalletFlow`, `NewWalletFlow`) already provides, and every existing breakpoint
(`GeniusBreakpoints.small`) as-is. Only visual treatment — colors, typography, spacing, component
primitives — changes, per §5 below.

**What CAN be taken from Alex's screens despite the structural disqualification:** isolated
visual/component choices that don't require adopting the surrounding split — the `GWButton`
variant choices (primary CTA → `gradient`, secondary → `secondary`, cancel → `ghost`), `GWTextField`
for the wallet-name/paste fields, `GWCheckbox` for the two agreement checkboxes, `GWWalletCard` for
the wallet-type row (§2), `GWMeshBackground` as the landing screen's background effect, and the
monospace/token treatment of the recovery-word grid. These are named explicitly per-widget in §5.

**A second, unexpected discovery this research made:** Alex's branch has a much closer analog for
GAP-04's `select_wallet_type_screen.dart` than the ROADMAP's "no mockup" framing suggests — see §2.

## 3. Security Contract (SCR-02 criteria 2–3) — binding, not advisory

This section is binding on every plan that touches `recovery_phrase_screen.dart`,
`verify_recovery_phrase_screen.dart`, or `paste_field.dart`. Every claim below is verified by
direct source inspection this session, not assumed.

### 3.1 The recovery phrase stays read-only

**Verified true on develop today, and must stay true after the re-skin.** Every word in
`recovery_phrase_screen.dart`'s grid renders through a plain `Text` widget inside a `Container` —
never a `TextField`/`TextFormField`/`SelectableText`. There is no editable field, no
autocorrect/spellcheck surface, and no built-in text-selection affordance on the phrase display
itself. **Binding rule: the re-skin must not introduce `SelectableText` or any editable widget for
the 12 displayed words** — the only sanctioned way to get the phrase onto the clipboard is the
existing explicit "Copy to clipboard" button (§3.4), never long-press-to-select on the grid.

### 3.2 The hide-toggle — default state and what it reveals

Verified: `_RecoveryPhraseScreenState._isVisible` defaults to `true` — **the phrase is shown
in the clear by default**, not hidden-first. This is develop's existing, shipped behavior; changing
the default to hidden-first would be a behavior change this phase's re-skin scope does not include
(re-skin, not restructure) and is not named by any ROADMAP criterion. **Binding rule: preserve
`_isVisible = true` as the initial state.** The toggle itself (eye icon + "Hide seed phrase"/"Show
seed phrase" label, `TextButton.icon`) is a re-skin target like any other button — see §5.3 — its
*behavior* (masking each word to `'••••••'`) is unchanged.

### 3.3 No seed phrase reaches debug console output

Verified by direct grep across `lib/onboarding/**` and `lib/screens/pin_screen.dart`: **zero
`print`/`debugPrint` calls exist anywhere in this phase's scope today.** `NewWalletBloc` and
`NewWalletState` are the only place `recoveryWords`/`recoveryPhrase` values live in memory outside
the widget tree. One latent risk found, not currently triggered but worth binding against:
`NewWalletState extends Equatable` and lists `recoveryWords` in its `props` — `Equatable`'s default
`toString()` prints every prop, including the plaintext words, if anything ever calls `.toString()`
on the state (a future `BlocObserver.onChange` override, a debug print of `state`, or an uncaught
exception whose message interpolates `state`). **No `BlocObserver` is registered anywhere in this
app today** (verified — `Bloc.observer` is never set, so `flutter_bloc`'s default no-op observer is
active and nothing currently prints state transitions). **Binding rule for this phase and any
later one:** do not add a `BlocObserver` override, a `debugPrint(state)`, or any error-message
interpolation of `NewWalletState` without first overriding `NewWalletState.toString()` to redact
`recoveryWords`. This phase's plans must not introduce the first such call.

### 3.4 The desktop copy-to-clipboard confirmation — finding 19, verified already fixed on develop

**Finding 19, as filed, describes Alex's fork (`GeniusWallet-3514`), not develop.** Verified line by
line: develop's `recovery_phrase_screen.dart:103-111`'s copy handler already has the guard —

```dart
onPressed: () async {
  await FlutterClipboard.copy(words.join(' '));
  if (!mounted) return;
  ScaffoldMessenger.of(context).showSnackBar(
    const SnackBar(content: Text("Recovery phrase copied to clipboard!")),
  );
},
```

— `if (!mounted) return;` sits between the `await` and the `ScaffoldMessenger` call, exactly the
fix the finding recommends. Alex's fork dropped this guard specifically on the **desktop** grid
variant (`_WordsGridWithCopyAndToggleState`, `recovery_phrase_screen.dart:217-225` on his branch)
while keeping it on the **mobile** variant (`_WordsAndCopyState:324-326`) — the same
split-by-breakpoint structure §1 already disqualifies. Since develop has no such split (one screen,
one copy button, guard present), **this finding is already closed on develop and must not be lost
by the re-skin.**

**Binding rule:** the `if (!mounted) return;` line is a **lifecycle guard, not a visual value** —
it must survive this phase's re-skin verbatim, in the exact position (after the `await`, before the
`ScaffoldMessenger` call), regardless of how the button itself is re-skinned (`TextButton.icon` →
whatever token-styled equivalent §5.2 specifies). Any plan touching this method must re-confirm the
guard is still present in its diff before considering the task complete — the same "verify, don't
just diff" discipline Phase 4 §4.1 and Phase 5 §2.1 established for their own findings.

### 3.5 Screenshot / recording exposure — stated plainly, not implied

**Verified: develop has no screenshot or screen-recording protection on any onboarding screen
today** (no `flutter_windowmanager`-style secure-flag call, no platform-channel screenshot block,
searched across `lib/onboarding/**` and the app's `main.dart`/platform setup — none found). The
recovery-phrase and verify screens render the seed phrase in the clear (when `_isVisible == true`,
the default) to whatever OS-level screenshot, screen-recording, or remote-desktop tooling is active.
**This phase's re-skin does not add or remove this exposure — it is develop's existing posture,
unchanged.** Recording this explicitly rather than silently implying safety the code does not
provide: **the design assumes no screenshot/recording protection.** Adding one (e.g. Android's
`FLAG_SECURE`, Windows' equivalent) is a real security improvement but is a new capability, not a
re-skin — out of this phase's scope per the GAP treatment rule, and not named by any ROADMAP Phase
6 criterion. Recorded here as a product/security follow-up, not decided or silently added.

### 3.6 A related finding, incidental to this research: the mnemonic **import** field has no
autocorrect/spellcheck hardening

Not one of the 4 named ROADMAP criteria, but directly adjacent to §3.1's key-safety concern and
found while reading `paste_field.dart`, so flagged per this phase's brief rather than silently
designed around: `PasteField`'s `TextFormField` (used by `ImportSecurityScreen`'s "Phrase" and
"Private Key" tabs — where a user **imports an existing** seed phrase or private key by typing or
pasting it) sets no `autocorrect`/`enableSuggestions`/`autofillHints` parameters. Flutter's
`TextFormField` defaults both `autocorrect` and `enableSuggestions` to `true` — meaning an imported
mnemonic or private key can be offered to the OS's predictive-text/spell-check/IME-learning system
while being typed. **This is pre-existing on develop, not introduced by this phase**, and it is
distinct from §3.1 (which is about the *generated*, *displayed* phrase, always read-only already) —
this is about the *import* path, which is necessarily an editable field. `GWTextField` (Phase 3
§2.3) does not expose `autocorrect`/`enableSuggestions` parameters either, so routing `PasteField`
through it would not fix this by itself.

**Recommendation, not a mandate — a minimal, deliberate, security-motivated behavior addition, not
a restructure:** when re-skinning `PasteField` (§5.4), add `autocorrect: false, enableSuggestions:
false` directly to its `TextFormField` (it does not need to go through `GWTextField` for this — see
§5.4). This changes no visible structure, no IA, no wording — it only turns off two OS text-input
behaviors on a field that already exists. If the executor judges this out of scope, leaving it
unaddressed does not block any ROADMAP Phase 6 criterion (none of the 4 mention the import path's
IME exposure) — but it must not be silently "fixed" by an unrelated `GWTextField` swap that doesn't
actually address it, and it must not be silently ignored without at least a recorded todo if
skipped.

**Color check — primary CTA gradient label, both modes:** `GWButtonVariant.gradient`'s foreground
is `GeniusWalletColors.textOnBrand` (`#000B18`) on `GeniusWalletGradient.brandCta`
(`gradientBlue #0AAEE6` → `gradientGreen #0AD89C`). Computed this session (not copied from a prior
spec without re-checking, per this phase's standing lesson): `textOnBrand` on the gradient's
**darker** stop (`gradientBlue`) = **7.74:1**; on the **lighter** stop (`gradientGreen`) =
**10.66:1**. Both `textOnBrand` and the gradient stops are mode-invariant `static const` values (not
`GWColors`/appearance-aware), so **this ratio is identical in light and dark — 7.74:1 worst-case,
both modes.** This reconfirms (not blindly re-cites) the same 7.74:1 figure `05-UI-SPEC.md` §3.1
already established for `textOnBrand` on `brandPrimaryStrong` — `gradientBlue` and

`surfaceBase` (`#0B0D12`) = **7.61:1** (passes). `brandPrimaryStrong` text on light `surfaceBase`
(`#DCE0E6`) = **1.93:1** — **fails WCAG AA outright.** This is **not a defect introduced by this
phase** — it is `gw_button.dart`'s `secondary` variant itself, a shared primitive already used
across Settings, the SDK manager, and the dashboard, and the project has an existing, repeated,
explicit decision to defer light-mode `#0AAEE6`-as-text fixes to a dedicated "light pass"

**Binding rule for this phase: do not attempt to fix `gw_button.dart`'s `secondary` variant here** —

project's own dark-first sequencing decision. **But this phase's walk must not report the

`gw_button.dart`, not against onboarding's own re-skin, exactly as this section does.

### 4.5 `verify_recovery_phrase_screen.dart` (security-critical — read §3 first)

Develop's word-tile interaction (tap a chip → fills the next highlighted empty box; tap a filled

same standing gate Phase 4 §8 and Phase 5 §7 established. §4.1 records this phase's own instance of
the recurring `deepBlue`/hardcoded-dark-constant trap (`wallet_creation_screen.dart`'s Scaffold
background) and fixes it; §4.1 and §4.3 also record, rather than silently ship, the one **inherited**
light-mode failure this phase cannot fix locally (`GWButtonVariant.secondary` text at 1.93:1 on a
light surface).

**Accent (`brandPrimaryStrong`, 10%) — reserved for, this phase:** primary CTA gradient fills
(`GWButtonVariant.gradient` — Continue/Import/Create buttons), the verify screen's
highlighted-empty-box border and filled-word-tile-with-input border, the recovery-word tile cursor

body text (§4.1, §4.5's explicit "not `brandPrimaryStrong`-as-text" calls) — the same reservation

has-user-input word-tile border (§4.5) — the one place this phase uses it, matching Alex's own
exact choice.

**Destructive (`statusError`) — reserved for:** "Incorrect PIN" text (§4.9). No other destructive
surface exists in this phase's scope — onboarding has no delete/destroy action.
