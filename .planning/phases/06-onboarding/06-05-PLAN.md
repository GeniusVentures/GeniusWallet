Excluding it would leave a load-bearing piece of that criterion unskinned. Phase 3's own UI-SPEC §2.8
already anticipated this file being Phase 6's.

`create_pin_screen.dart` and `confirm_and_save_pin_screen.dart` are VERIFY-ONLY (§4.8). They are thin

this plan's `files_modified`.

**Defect found while reading develop, and the one deliberate behavior change in this plan.**
`pin_screen.dart:49-54` ships:

    onPressed: state.pinFullness == PinFullness.completed
        ? onCompleted(state.pinController.text)
        : null,

`onCompleted` is declared `Function(String)` — a DYNAMIC return type — so this expression CALLS
`onCompleted` during `build()` and assigns its return value to `onPressed`. Both call sites pass a
`void` function, so the value assigned is always null. Two consequences ship today:
1. The Continue button is PERMANENTLY DISABLED. It never fires, in either PIN step, in either flow.
2. The flow advances as a build-phase side effect the instant the PIN reaches full length — and
   re-fires on EVERY rebuild while it stays full. On a failed confirm, `displayIncorrectPin` flips,
   the widget rebuilds, and the submission fires again.

UI-SPEC §4.9's re-skin target quietly repairs this by writing `onPressed: ... ? () => onCompleted(...)
: null` — adding a closure — but presents it as a token substitution. It is not; it is a behavior
change, and this plan records it as one. The change is taken (not deferred) because the alternative is
shipping a redesigned, visibly-styled Continue button that does nothing, in the flow ROADMAP criterion
1 says must complete end to end.

The fix is paired with a permanent guard that costs one word: tighten `onCompleted` from
`Function(String)` to `void Function(String)`. Both callers already pass exactly that type, and once
the return type is `void` the analyzer rejects the invoke-during-build form outright. That is this
plan's one runnable check — the analyzer becomes the tripwire, so no future edit can silently
reintroduce the defect.

**UI-SPEC §4.9 correction — 'Incorrect PIN'.** §4.9 says to use `GeniusWalletColors.statusError`
directly and quotes light #D92D2D at 4.81:1 and dark #FF4D4D at 5.90:1. But
`GeniusWalletColors.statusError` is `static const Color(0xFFFF4D4D)` — ONE mode-invariant value. The
two values §4.9 quotes live on the appearance-aware `GWColors` ThemeExtension instead
(`gw_colors.dart:111` light, `:166` dark), which the file's own ponytail note at `:67-69` says is
deliberate. Following §4.9's literal instruction would ship #FF4D4D in light mode — roughly 3.4:1 on a
near-white surface, an AA fail — while the contract claims 4.81:1. This plan uses `gw.statusError`,
which delivers exactly the ratios §4.9 computed. Either way §4.9 is right to abandon
`theme.colorScheme.errorContainer`: Phase 4 dropped that ColorScheme slot, so it resolves to an
unverified Material 3 default.

Re-skin, never restructure (§1): develop's `Center` / `ConstrainedBox(maxWidth: GeniusBreakpoints.small)`
/ `Column(spacing: 12)` tree is locked. No `LayoutBuilder`, no breakpoint split, no
`app_screen_with_header_*` import, and no adoption of Alex's split PIN screen.

Appearance-color access path (04-02/04-04 discipline): appearance-aware title/border/fill/error colors
read via `final gw = Theme.of(context).extension<GWColors>() ?? GWColors.dark();`; mode-invariant
`brandPrimaryStrong` stays on the `GeniusWalletColors` static getter.

Output: a token-correct shared PIN screen whose Continue button works, whose error text is legible in
both modes, and whose defect class is closed by the type system.
