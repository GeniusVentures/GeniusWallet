<objective>
Re-skin the two seed-phrase screens — the highest-consequence surface in the whole port, and the only
place in this milestone where a 12-word recovery phrase exists in plaintext on screen. UI-SPEC §3 is
binding on every line of this plan, not advisory: where "re-skin, never restructure" and "protect key
material" appear to pull against each other, key safety wins.

Purpose: ROADMAP Phase 6 criterion 2 in full (the phrase stays read-only, the hide-toggle works, no
seed reaches debug console output) and criterion 3 in full (copying on desktop shows its confirmation
without throwing after the screen is dismissed mid-copy) — plus criterion 1's two seed steps.

Criterion 3 is satisfied by PRESERVATION, not by a fix. Verified line by line: develop's copy handler
already reads `await FlutterClipboard.copy(...)` then `if (!mounted) return;` then the
`ScaffoldMessenger` call — exactly the fix finding 19 recommends. The finding describes Alex's fork,
which dropped the guard on its DESKTOP grid variant while keeping it on the mobile one; develop has no
such split, one screen, one copy button, guard present. **Do not "fix" it.** Re-writing that handler
risks regressing a working guard. The job is to verify it survives the re-skin edit, in position,
between the await and the ScaffoldMessenger call.

Four binding security constraints from §3, each verified against develop's source this session and each
of which must still hold in the diff this plan produces:
- §3.1 The displayed phrase is read-only. Every word renders through a plain `Text` in a `Container`.
  Do NOT introduce `SelectableText`, a `TextField`, or any editable widget for the 12 words. The
  sanctioned clipboard route is the explicit Copy button, never long-press-to-select on the grid.
- §3.2 `_isVisible` defaults to TRUE — the phrase is shown in the clear by default. That is develop's
  shipped behavior. Hidden-first would be a behavior change no criterion asks for. Preserve the default;
  re-skin only the toggle button's appearance.
- §3.3 Zero `print`/`debugPrint` calls exist anywhere in this phase's scope today, and no `BlocObserver`
  is registered anywhere in the app (so `flutter_bloc`'s default no-op observer is active and nothing
  prints state transitions). `NewWalletState extends Equatable` and lists `recoveryWords` in its `props`,
  so `Equatable`'s default `toString()` would print the plaintext words if anything ever called it. This
  plan must not introduce the first such call — no `BlocObserver`, no state logging, no error message
  that interpolates the state.
- §3.5 develop has no screenshot or screen-recording protection on any onboarding screen, and this
  re-skin neither adds nor removes that exposure. Stated plainly so nothing downstream implies a safety
  the code does not provide. Adding a secure-window flag is a real improvement but a new capability, not
  a re-skin — out of scope, filed as a follow-up by 06-06.

Re-skin, never restructure (§1): develop's single `Center`/`ConstrainedBox(small)`/`Column` tree is
locked on both screens, as is the verify screen's `SingleChildScrollView`. No `LayoutBuilder`, no
breakpoint split, no `AppScreenWithHeader*` import. Two build-phase side effects develop ships —
`recovery_phrase_screen.dart`'s `LoadRecoveryPhrase()` dispatch inside `build()` and the verify screen's
same dispatch in `initState` — are BEHAVIOR. They are an anti-pattern, but they are not this re-skin's
to change; leave both exactly as they are.

Appearance-color access path (04-02/04-04 discipline): appearance-aware surface/text/border colors read
via `final gw = Theme.of(context).extension<GWColors>() ?? GWColors.dark();`; mode-invariant
`brandPrimaryStrong` / `brandGreen` stay on the `GeniusWalletColors` static getters.

Output: two token-correct, appearance-aware seed screens with every §3 security property re-confirmed
against the diff rather than assumed.
</objective>
