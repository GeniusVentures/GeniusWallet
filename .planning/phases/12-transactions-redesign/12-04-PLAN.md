<objective>
Close the filter coverage bug and replace the flat `SegmentedButton` with the F1 two-tier
control the design locked.

Purpose: `Filters` (`transactions_slim_view.dart:16`) is `{all, sent, received, escrow, mint}`
while `TransactionType` has seven values. `swap`, `purchase` and `process` are unreachable by any
filter today — a swap can only ever be found under "All". Sketch 011 called this out as a
coverage bug rather than a styling preference, and it is the reason the enum change has to land
WITH its UI: a longer enum in the current `SegmentedButton` would simply overflow the narrow
panel.

Output: a 10-value `Filters` enum with explicit groupings, and a private `_TransactionFilterBar`
mounted as `GWSectionTitle`'s trailing.

Requirements covered: TX-03 (enum coverage), TX-04 (F1 two-tier UI).

<task type="auto">
  <name>Task 1: Extend Filters to cover every transaction type, and prove it</name>
  <files>lib/dashboard/home/widgets/transactions_slim_view.dart, test/dashboard/transaction_filters_test.dart</files>
  <action>
Rewrite the `Filters` enum in `transactions_slim_view.dart`. Declare the values in the order the
title row uses them, then the overflow types, then the statuses:

`all` ("All"), `sent` ("Sent"), `received` ("Received"), `mint` ("Mint"), `jobs` ("Jobs"),
`escrow` ("Escrow"), `swap` ("Swapped"), `purchase` ("Purchased"), `pending` ("Pending"),
`failed` ("Failed").

Give each value two fields: `final String label` and `final TransactionBadgeKind? badgeKind`
(null only for `all`). The badge kind is what lets a chip paint the same mark as the row badge
via `badgeSpec` / `badgeGlyph` — Sent chip and Sent badge must be the same arrow or the filter
stops reading as connected to the list. Map: sent -> sent, received -> received, mint -> mint,
jobs -> job, escrow -> escrow, swap -> swap, purchase -> purchase, pending -> pending,
failed -> failed.

Extend `matches(Transaction tx)` — keep it an exhaustive `switch (this)` EXPRESSION so a future
tenth value cannot compile without a rule:
  - `all` -> true
  - `sent` -> `tx.transactionDirection == TransactionDirection.sent`
  - `received` -> `tx.transactionDirection == TransactionDirection.received`
  - `mint` -> `tx.type == TransactionType.mint`
  - `jobs` -> `tx.type == TransactionType.process`
  - `escrow` -> `{TransactionType.escrow, TransactionType.escrowRelease}.contains(tx.type)`
    (unchanged — escrow deliberately spans both, and that must not regress)
  - `swap` -> `tx.type == TransactionType.swap`
  - `purchase` -> `tx.type == TransactionType.purchase`
  - `pending` -> `tx.transactionStatus == TransactionStatus.pending`
  - `failed` -> `{TransactionStatus.failed, TransactionStatus.cancelled}.contains(tx.transactionStatus)`
    (`cancelled` is folded in for the same reason `escrowRelease` folds into escrow: a user
    looking for a transaction that did not go through does not distinguish the two)

Add three `static const List<Filters>` groupings that the bar reads and the test checks:
`primary = [sent, received, mint, jobs]` (the title row, in the locked order Sent · Received ·
Mint · Jobs), `overflowTypes = [escrow, swap, purchase]`, `overflowStatuses = [pending, failed]`.
Add `static bool isInOverflow(Filters f)` returning whether `f` is in either overflow list —
the bar uses it to decide whether the trigger takes the gradient.

Add a top-level `Map<Filters, int> filterCounts(List<Transaction> txs)` returning, for every
non-`all` value, how many of `txs` it matches. The menu shows live counts; computing them once
per build beats calling `where().length` per item.

Then create `test/dashboard/transaction_filters_test.dart` — a pure unit test, no pumping:
  - **the coverage test**: for EVERY `TransactionType` value, build a transaction of that type
    and assert at least one non-`all` `Filters` value matches it. This single loop is the bug
    sketch 011 found, made permanent.
  - assert `Filters.escrow.matches` is true for both `escrow` and `escrowRelease`.
  - assert `Filters.failed.matches` is true for both `failed` and `cancelled`.
  - assert `Filters.all.matches` is true for an arbitrary transaction.
  - **the no-orphan test**: assert the set of `Filters.values` minus `all` equals
    `primary + overflowTypes + overflowStatuses`. A filter that exists but appears in no UI
    group is unreachable in a different way, and this is the gate that catches it.
  - assert `Filters.primary` is exactly `[sent, received, mint, jobs]` in that order — the
    ROADMAP locks the order, so pin it.
  - assert `filterCounts` over a mixed list returns the expected count for at least `sent`,
    `escrow` (spanning two types) and `failed` (spanning two statuses).
  </action>
  <verify>
    <automated>flutter test test/dashboard/transaction_filters_test.dart</automated>
    <automated>flutter analyze lib/dashboard/home/widgets/transactions_slim_view.dart</automated>
  </verify>
  <done>
Every `TransactionType` value is matched by at least one filter; escrow still spans both escrow
types; no filter is orphaned from a UI group; the primary order is pinned; analyze is clean.
  </done>

<risk>
**Freeze rule (phase-wide, from `37639d5`).** The only value this plan derives from layout is the
`compact` boolean. Everything else is a fixed literal or a 4-pt token. `FittedBox(fit: scaleDown)`
and `AutoSizeText` are both banned in this file — the existing `FittedBox` around the segmented
button is being deleted, not moved.

**Do not touch `theme.dart`'s `textButtonTheme`.** It is shared app-wide and editing it regresses
every bare `TextButton` in the app. Chip and menu styling is local `ButtonStyle` / `Container`
decoration only — the pattern `lib/theme/nav_chip_style.dart` established.

**Density trap.** `nav_chip_style.dart` records that desktop's ambient `adaptivePlatformDensity`
is `compact`, whose `-8` adjustment silently shrank a nominally-40px chip to 32. This bar sizes
chips with explicit `SizedBox` / `AnimatedContainer` heights rather than button `minimumSize`, so
the trap does not apply — but if you reach for a `TextButton` here, pin
`visualDensity: VisualDensity.standard` as that file does.
</risk>
