<objective>
The half of the calldata that is NOT a plain send: an `approve`, an unlimited
allowance, a token this wallet cannot vouch for, and a token call that also
moves native currency. All four land on ONE new content widget whose whole job
is to say what it can read and admit what it cannot. Purpose: give the
honest-uncertainty cases a real surface before plan 03 routes unknown calls and
signature requests into it. Output: `lib/reown/dapp_call_details.dart` and the
approve/unverified decode.

**Why a second widget and not more parameters on `SendTransactionDetails`:**
settled in plan 01's objective. It asserts "this amount leaves you, in this
unit". That sentence is false for every case in this plan.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| dApp -> `tx['data']` / `tx['value']` | attacker chooses the selector, the arguments and the native value together; every string rendered downstream is read as a claim the wallet is making |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-30-06 | Elevation of privilege | `approve` at max-uint256 | critical | mitigate | Single `2^255` comparison raises an explicit unlimited-spending `GWWarningNote`; the main drain vector in the wild, tested at the sentinel and just below it |
| T-30-07 | Spoofing | an unknown token rendered with a guessed decimal amount | high | mitigate | unverifiedToken prints raw base units only, labelled unverified, beside the full contract address; a test pins that null/empty/garbage decimals never becomes 18 |
| T-30-08 | Information disclosure (misleading) | native `value` hidden behind a token figure | high | mitigate | Non-zero `value` forces the unverifiedToken kind and its own native row — both figures on screen, neither summarised away |
| T-30-09 | Spoofing | attacker-supplied text reaching the drawer | medium | mitigate | `DappCallDetails` renders only wallet-authored headlines/warnings plus addresses and digits derived from calldata; no contract-supplied string (`symbol()`, `name()`) is ever fetched or rendered |
| T-30-10 | Repudiation | an approve rendered through the send hero | medium | mitigate | `approve` is structurally barred from `SendTransactionDetails`; a widget test asserts no "You send" row appears on an approve |
</threat_model>
