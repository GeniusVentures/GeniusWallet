<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| dApp -> walletKit session request | `event.params`, `tx['data']`, `tx['to']`, `tx['value']` are wholly attacker-controlled |
| decoder -> drawer -> `signAndSendTransaction` | what is rendered is what the user believes they authorise; the same `tx` map travels by reference to `hexToBytes(tx['data'])` |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-30-01 | Tampering | `summarizeTransaction` reading `tx` | critical | mitigate | Read-only by construction; Task 3's before/after map equality test fails on any in-place write |
| T-30-02 | Spoofing | token symbol shown next to an amount | high | mitigate | Symbol and decimals come ONLY from `WalletDetailsCubit.state.coins`, never from calldata and never from an RPC `symbol()` call — a lookalike or unicode-crafted symbol from a hostile contract cannot reach the screen (D-01) |
| T-30-03 | Spoofing | a wrong-decimals guess renders a confident wrong amount | high | mitigate | A coin with null/unparseable `decimals` is UNRESOLVED and falls out of the decoded path; 18 is never assumed (D-02) |
| T-30-04 | Tampering | calldata whose selector matches `transfer` on a contract that is not a standard ERC-20 | medium | mitigate | A decode is only promoted to a confident "You send N SYM" when `tx['to']` independently resolves in the wallet's own coins list; otherwise it stays on the undecoded path |
| T-30-SC | Tampering | dependency supply chain | low | accept | No package is added — `pubspec.yaml`/`pubspec.lock` are untouched; plan 04's gate greps the diff to prove it |
</threat_model>
