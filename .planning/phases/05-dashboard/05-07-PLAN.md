## The load-bearing finding this plan is built on

The planner investigated whether the retry can actually recover both conditions. **It cannot, if it
reuses the pull-to-refresh dispatches unchanged.** Evidence, read at HEAD:

- The branch fires on `subscribeToWalletStatus == AppStatus.error` **OR**
  `accountStatus == AppStatus.error` (`dashboard_screen.dart:68-69`).
- `accountStatus` is written in exactly three places — `app_bloc.dart:164`, `:168`, `:170` — and all
  three are inside `_onFetchAccount`, the handler for `FetchAccount`. A repo-wide grep for
  `accountStatus` returns no other writer.
- `_onLoadWallets` (`app_bloc.dart:65-125`) writes only `subscribeToWalletStatus` (`:66`, `:77`,
  `:120`). **It never touches `accountStatus`, transitively or otherwise** — it awaits
  `api.getWallets()`, merges SGNUS wallets, and hands off to `transactionsCubit.loadInitial` /
  `walletDetailsCubit.loadInitial`; none of those re-enter `AppBloc`.
- Consequently a retry that dispatched only `LoadWallets()` would leave `accountStatus` pinned at
  `error`, the branch would re-render, and the button would visibly do nothing.

**And the account leg is the only reachable one.** `_onLoadWallets` has no `try`/`catch` and emits
`AppStatus.error` for `subscribeToWalletStatus` nowhere in the file; a throw from `api.getWallets()`
escapes to the bloc's error sink leaving the status at `loading`. So in shipped code today the error
branch can only be reached via `accountStatus` — precisely the leg `LoadWallets()` cannot clear.
The retry MUST dispatch `FetchAccount()`. (It dispatches `LoadWallets()` too, so it stays correct if
the wallet leg ever becomes reachable. Making it reachable is **out of scope** — that is an
`app_bloc.dart` behavior change, and this phase's goal clause is "keeps every behavior develop
shipped". Recorded here so the observation is not lost.)

## Correction to the briefing's scope note

The planning briefing stated that `_onRefresh` "is an instance method of `DashboardScreenState` ...
so it is in scope" from the error branch. **That is not what the file says.** `DashboardScreenState`
ends at `:80`; `_onRefresh` is at `:218-225`, inside `class OneColumnDashBoardView extends
StatelessWidget` (`:215`). It is not in scope at the error branch, and reaching it would mean
constructing a widget just to call a method on it. The reuse intent behind the briefing is correct
and is honoured — by hoisting the function to file scope (Dart's privacy unit is the library, and
both callers live in this one file) rather than by duplicating its two dispatches.
