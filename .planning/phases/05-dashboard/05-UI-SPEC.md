> Visual and interaction contract for the dashboard: balances/holdings, transactions, markets, and
> news. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Framing.** Like Phases 2-4, this is a **port of an already-authored, adopted design system** —
not a design exercise. Every visual value below is extracted from Alex's `GeniusWallet-3514`
reference worktree and Phases 2-4's already-landed token/component/theme layers (theme wiring and

screen by screen, while carrying forward the 12 findings this phase's traceability names (8, 9,
10, 14, 17, 18, 29, 30-34) unregressed.**

## 1. The single most important finding — Alex's `dashboard_screen.dart` is NOT the re-skin reference

Verified by direct inspection, not assumed: Alex's `GeniusWallet-3514/lib/dashboard/home/view/dashboard_screen.dart`
is a **structural redesign**, not a token-only re-skin of develop's dashboard. It replaces
develop's 5-area responsive grid (balance overview / SGNUS contributions / price chart / markets /
transactions, each its own card, arranged 1/2/3-column by breakpoint) with a completely different
information architecture: a single-column mobile-first layout — hero balance with an animated
number and a fabricated 24h delta, a 4-icon pill action row (Send/Receive/Bridge/Buy), an
Assets/NFTs segmented-track tab switcher, an inline asset search field, and an NFT grid.

**This is disqualified as a structural reference for three independent reasons, each already
decided by REQUIREMENTS.md:**

1. **WIRE-9** — the 24h delta is `balance * 0.024`, a fabricated number (`_HeroBalance`, line
   ~150-151). WIRE-01 forbids porting any `WIRE-N` stub.
2. **WIRE-8** — the NFTs tab (`_NftsSliver`) renders 6 hardcoded placeholder tiles with no real
   data source. WIRE-02 explicitly places the NFTs tab out of scope for this milestone.
3. **WIRE-7** — the `$` prefix on the hero balance comes from `GWCurrency.symbol`
   (`lib/preferences/gw_currency.dart`), Alex-only currency-picker code develop doesn't have.
   WIRE-02 explicitly places `lib/preferences/` out of scope.

Beyond the three WIRE items, the screen also drops develop's SGNUS connection widget, SGNUS
connection status, GNUS/Minions balance-unit toggle, and `SubmitJobDashboardButton` entirely —
features Alex's fork evidently doesn't carry forward. Porting this screen's structure would
therefore not just restructure the IA (forbidden by the GAP treatment decision, REQUIREMENTS.md
§"Design Gaps") — it would silently delete working develop capability.

**Binding rule: develop's existing 5-area dashboard IA is locked for this phase.**
`OverviewDashboardView`, `ContributionsDashboardView`, `ChartDashboardView`,
`MarketsDashboardView`, `TransactionsDashboardView`, and their responsive 1/2/3-column arrangement
(`OneColumnDashBoardView` / `ResponsiveDashboardView._twoColumnLayout` /
`ResponsiveDashboardView._threeColumnLayout` in `lib/dashboard/home/view/dashboard_screen.dart`)
keep their exact structure, order, and behavior. Only their **visual treatment** — colors,
typography, spacing, card decoration, component primitives — changes, per §4 below.

**What CAN be taken from Alex's `dashboard_screen.dart` despite the structural disqualification:**
isolated visual/token choices that don't require adopting the surrounding structure — the balance
typography (`GeniusWalletTypography.numericDisplay`, tabular figures), the `GWAnimatedNumber`
component itself (count-up animation, no behavior attached), `GWDecorations.heroGlow` behind a
large numeric balance, and `GWDecorations.surface()`/`surfaceSheen` card treatment. These are
named explicitly per-widget in §4.1.

**OPEN QUESTION FOR PRODUCT (recorded, not decided here):** should a future milestone adopt Alex's
mobile-first hero-balance + Assets/NFTs tab IA, once NFTs (WIRE-8) and multi-currency (WIRE-7) are
real features? That is a restructuring decision with product ownership, explicitly out of this
phase's scope per the GAP treatment rule ("Out of scope... moving or reordering items, changing
information architecture... If applying the design language requires one of these to look right,
stop, leave that part as-is, and record it for product rather than deciding it here").

### 2.1 Binding rules for this phase's re-skin

- **No behavior change is needed for any of the 12** — all are either already correct (11/12) or
  describe code that doesn't exist on develop (1/12, finding 30). The re-skin's job is to touch
  every one of these files' **visuals** without disturbing the logic verified above. Re-run this
  verification (a quick read of the same line ranges) before closing any plan that edits these
  files, per the same discipline Phase 4's §4.1 established.

  retry mechanism behind findings 8, 18, and (indirectly) the markets dashboard widget.** Its retry
  wiring is already correct everywhere in this phase's scope (§2 table). Its **visuals** are the

- **Criterion 5's overflow/crash requirements are already met** by findings 30, 32, 33 above — the
  re-skin must preserve every `Flexible`/`overflow: TextOverflow.ellipsis` wrap and every

## 7. Spacing, Typography, Color (inherited from Phases 2-4 — this phase adds no new tokens)

All re-skinned surfaces in this phase consume Phases 2-3's token classes exclusively
(`GeniusWalletConsts`, `GeniusWalletTypography`, `GeniusWalletColors`, `GeniusWalletElevation`,
`GeniusWalletDecorations`) and Phase 4's `GWColors` ThemeExtension access path (`Theme.of(context)
.extension<GWColors>() ?? GWColors.dark()`) for any live-reskinning `const`-instanced widget — the
same non-negotiable discipline Phase 3 §8 and Phase 4 §8 established. **Zero raw hex, zero ad-hoc
`Color(0x...)`, zero raw px typography, zero `Colors.white`/`Colors.red`/`Colors.grey[N]` survives
in any file this phase touches** — every substitution table in §3-§4 above names the exact token
replacing each raw value found.

**Every surface this phase touches must be specified for BOTH light and dark appearance — this is
a gate, not a nicety** (Phase 4 §8's same standing rule; the theme is wired, so there is no more
excuse for a dark-only assumption). Card decorations (`GWDecorations.surface`/`surfaceSheen`),
`gw.textPrimary`/`textSecondary` (context-resolved, not the static backward-compat fallback),
and `GeniusWalletColors.statusError`/`brandGreen`/`brandPrimary` all already flip correctly; the
one thing to verify per file is that no `Colors.white`/`Colors.grey[900]`/hardcoded dark constant
(`deepBlueCardColor`, `deepBlueMenu`, `deepBlueTertiary`) survives the re-skin (this phase's
version of Phase 4 §8's `deepBlueCardColor` trap — the same trap, found again in `coins_screen.dart`,
`transaction_displays.dart`, and `crypto_news_screen.dart`'s `Scaffold` background).

**Accent (`brandPrimary`, 10%) — reserved for, this phase:** the selected Assets/Markets filter
segment (`SegmentedButton` in `TransactionsSlimView`), `GWTextField`/`GWSelect` focus borders (the
markets search field), the GNUS/Minions toggle's selected state, retry buttons'
`GWButton(variant: primary)` fill. **Never** a whole-card background, never every icon on a
dashboard row — the same reservation discipline every prior phase established.

**Secondary brand (`brandGreen`/`brandSecondary`) — reserved for:** the received-transaction arrow
badge (§3.3), the loading spinner's left dot (§3.2), positive-delta indicators if any survive from
§1's disqualified reference (none currently exist on develop's locked IA — no delta indicator ships
this phase; if one is added later it is a new decision, not this contract's).

**Destructive (`statusError`) — reserved for:** "No funds available" text, transaction/purchase
failure states, image-load error icons, the markets missing-data debug placeholder. Never used for
a routine informational icon (e.g. the news card's default error icon before this substitution was
plain-`Icons.error`-red, which happened to coincide — now it's `statusError` deliberately, not by
accident).
