## The fixture is a deliverable, not a nicety

`05-VERIFICATION.md`'s B1 entry states it plainly: fixing the slot alone does **not** close this
gap. Without a fixture, criterion 5 moves from *failed* to *unverifiable*, not to *verified*.

This project has been bitten by precisely this twice in two days:

- The `GWEmptyState` overflow survived **six** human walks because every walk used the `cw8`/`jvr`
  mock-holdings injectors to get a populated wallet, and a populated transactions list renders rows
  rather than the empty state. The fixtures that made walking possible made one entire state
  invisible.
- B1 has never been walkable **at all** — it needs a live SGNUS connection plus `isProcessing`.

So Task 1 ships the fixture, and it ships **before** the layout fix, so the executor and the walker
can see the defect before it is repaired. That ordering is deliberate: it converts a disputed
arithmetic claim into an observation.

## Why a structural B1 fix, and not e3r's compact-tier approach

The audit's investigating agent computed "passes by 3px". The refuting agent recomputed against
Flutter SDK source and got "**~26px idle and ~55px processing**" — the correction went in the
**worse** direction, by roughly 29px. Two careful agents, ~29px apart, on the same code.

`WalletsOverview`'s intrinsic height is not derivable from constants the way `GWEmptyState`'s was.
Its six children include an FFI-polled `AutoSizeText` at `fontSize: 48`, a `ToggleButtons` row, a
`TextButton.icon` whose icon is one of three different animations, a `Wrap` that grows by ~30px the
moment `isProcessing` flips (the `Loading` spinner is `size: 50` — `loading.dart:26`), and a 48px
CTA that appears only when the selected wallet address matches the live SGNUS connection. Any
threshold constant chosen here would be a number nobody can re-derive, fitted to a measurement two
agents already disagreed about.

**So do not pick a number.** Give the content somewhere to go:

```
LayoutBuilder -> SingleChildScrollView -> ConstrainedBox(minHeight: incoming maxHeight) -> the existing Column
```

- **When there is room** the rendering is unchanged, and provably so rather than hopefully so: the
  `minHeight` fed back in is the *exact same* bound the Column receives today, `mainAxisSize` stays
  `max`, and `RenderFlex` computes its centering leftover from the constrained size — so the six
  children still center in the same box. Nothing about the visual result depends on a new constant.
- **When there is not** the Column's `maxHeight` is unbounded, so it takes the height it needs and
  the scroll view supplies the offset. There is no slot height at which this overflows.

This is the `260721-e3r` philosophy (fix the CLASS of bug, stay pixel-identical where there is room)
applied with the tool that suits *this* widget's shape.

**Known interaction, checked and load-bearing for the walk.** `OneColumnDashBoardView` wraps its
`ListView` in a `RefreshIndicator` (`dashboard_screen.dart:265-266`), so the new inner scroll view
is a same-axis nested scrollable. When its content fits,
`ScrollPhysics.shouldAcceptUserOffset` is false (min and max scroll extent are equal), `Scrollable`
calls `setCanDrag(false)` and installs **no** drag recognizer — so it does not enter the gesture
arena and pull-to-refresh behaves exactly as it does today. When the content does not fit, the
inner view scrolls, which is the desired behavior in the only state where it differs. The walk
verifies this rather than trusting it.

## B2: a container/skin fix, and one structural correction

The gap's own `missing` list says: *route both branches through `GWErrorState` / `GWEmptyState`
inside `DashboardScrollContainer`, matching the four sibling panels.* That is what Task 3 does, with
develop's strings passed in explicitly as `title:` so they survive byte-for-byte.

**UI-SPEC §6 is binding and this plan does not test it.** "Failed to load market coins" and "No
market data available" are develop's strings; §6 marks both `unchanged`. Neither component's default
wording may be substituted, and neither string may be reconciled toward a component default. §6's
own dashboard-error row exists because that exact mistake was made once already — and a second-hand
summary of §6 then cost this project two reporting cycles. The strings are inputs here, not
outputs.

**One structural correction is required, not optional.** `FutureStateWidget`
(`custom_future_builder.dart:35-56`) renders its error path as
`Center > Column [ error, if (onRetry != null) SizedBox(12) + GWButton('Retry') ]`. If `error:`
becomes the card, the appended Retry lands **outside** it — the tile would keep a card containing
only the message, with a naked button underneath. So the retry moves *into* the card:
`GWErrorState(onRetry: _retry)` renders the identical chrome (`gw_error_state.dart:62-69` is the
same `GWButton(primary, Icons.refresh, 'Retry')` pair), and `onRetry:` is dropped from the
`FutureStateWidget` call so exactly one Retry exists. Same callback, same label, same chrome, one
button, inside the card. Recorded here as a deliberate deviation from a pure container swap.

**And the error chrome must not itself overflow.** `GWErrorState` is *not* adaptive — `e3r` gave the
compact tier to `GWEmptyState` only. With a retry it needs roughly `24+24` padding `+ 72` circle
`+ 16 + 24` title `+ 16 + 48` button ≈ **224px**. The Markets slot is 326px in the one-column layout
(`maxHeight: 350` minus 24px of container padding) and 356px+ in three-column, but in the
**two-column** layout it is `Expanded` inside a Column that also holds the chart, beneath a 300px
overview row — at an ordinary ~600px window height that lands near 114px. Shipping a guaranteed new
RenderFlex in the plan that closes a RenderFlex gap is not defensible, so the error branch gets the
same scroll-safe wrapper Task 2 introduces, as a small private widget in this file.

`GWEmptyState` deliberately does **not** get that wrapper: it already adapts, and wrapping it in a
scroll view would hand its `LayoutBuilder` an infinite `maxHeight`, silently disabling the compact
tier `e3r` just shipped and forcing a 192px full layout into a 114px card. The asymmetry is correct
and is recorded in the source.
