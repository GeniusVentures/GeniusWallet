<objective>
Finish the extraction pass and close the phase.

`GWScreen` already exists and is used **twice** while ~28 files hand-roll a `Scaffold`. That looks
like an obvious 20-site migration, and it is not. `GWScreen` supplies a `SafeArea`, a
`SingleChildScrollView`, a 1200px `ConstrainedBox`, a `Center`, fixed horizontal and vertical
padding, and a background colour. Wrapping a screen that does not already have exactly that shape
changes its layout — and Phase 22's invariant is that nothing changes what the app does or how it
looks.

So the deliverable is an **audit plus the migrations the audit justifies**, not a blanket migration.
Nothing is dropped: every one of the ~28 sites gets a recorded judgement, and the ones that cannot
move carry a written note of what would need to change, for whoever picks it up.

Purpose: adopt the shared screen wrapper wherever it is free, and hand over an honest list of where
it is not.
Output: the audit, the justified migrations, and the phase closeout record.
</objective>

This repo has a recorded, walk-driven finding that is directly relevant: a screen whose CTAs were
glued to the window bezel at narrow widths, because `ConstrainedBox(maxWidth:)` only binds when the
viewport is *wider* than it — below that, constraints collapse to the raw viewport width and a
stretch column runs edge to edge with zero gutter. `GWScreen` has both a `ConstrainedBox` and a
`Padding`, so it is already correct on that point. But it means any migration must be checked at a
**narrow** width, not only at desktop width, or the class of bug this repo has already shipped once
goes unnoticed.

    Verdict rules:
      - **EQUIVALENT** — adopting `GWScreen` with its defaults produces the identical widget tree
        shape. Migrate in Task 2.
      - **EQUIVALENT WITH EXPLICIT ARGUMENTS** — adopting it produces the same result if specific

        `centerContent: false`). Also migrate, passing those arguments explicitly. Do not accept a
        default that differs from the current behaviour just because it looks nicer.
      - **NOT EQUIVALENT** — adopting it would change layout, or the screen needs a `Scaffold`
        feature `GWScreen` does not expose (drawer, `bottomSheet`, custom `Scaffold` keys). Record
        one line on what would have to change. Do **not** migrate it, and do **not** widen `GWScreen`
        with parameters to accommodate it — a wrapper that grows a flag per screen has stopped being
        a wrapper.

    Exclude from the audit, and say so: `gw_screen.dart` itself, and any `Scaffold` that is not a
    screen (a drawer host, an overlay host, a splash, a dev-only surface). Note that some `Scaffold`
    occurrences sit in files that are route shells rather than screens; those are Phase 23's routing
    work, not this plan's.

    If the EQUIVALENT plus EQUIVALENT-WITH-ARGUMENTS count comes out small — say fewer than five —
    that is a legitimate finding and it must be reported as such rather than talked up. The right
    answer to "20+ screens hand-roll a Scaffold" may be that `GWScreen`'s defaults do not match this
    app's screens, in which case the useful output of this plan is the audit itself plus a
    recommendation about what the shared wrapper should actually look like.

    No code changes in this task.
