<objective>
Move the app's colour reads from the static palette class onto the semantic accessor built in 23-01.
The parity layer means each rewrite is a prefix change and nothing else — the value read is identical
by construction and proven so by 23-01's parity test.

Do this with an AST rewriter, not a regex. A regex over 260+ sites in ~80 files will eventually match
inside a string, a doc comment, or a longer identifier, and the failure will be silent.

**No package install is required, and none is permitted on the critical path.** `package:analyzer` is
already present in `.dart_tool/package_config.json` as a transitive dependency of `build_runner`
(confirmed at planning time: 223 resolved packages, `analyzer` among them). A script under `tool/`
can `import 'package:analyzer/...'` and `dart run` will resolve it with **zero change to
`pubspec.yaml` and zero change to `pubspec.lock`**. `Workiva/dart_codemod` is the fallback only if
the direct approach proves unworkable, and taking it would require a blocking human package gate —
so do not plan on it.

Purpose: leave exactly one way for application code to read a colour.
Output: a reusable AST rewriter in `tool/`, the bulk of the call sites migrated, a residue list for
23-03, and a walked confirmation that the appearance toggle still flows everywhere.
</objective>

  <action>
    Write `tool/codemod_colors.dart` as a plain Dart script using `package:analyzer` directly.

    Parse each file **unresolved** — `parseString` / `parseFile` is enough. Type resolution is not
    needed for a static-member-access rewrite, and unresolved parsing is dramatically faster and needs
    no analysis-context setup. Visit the AST and rewrite only `PrefixedIdentifier` and `PropertyAccess`
    nodes whose prefix is the legacy palette class identifier and whose property name appears in the
    token map. Because it matches AST nodes, an occurrence inside a string literal, a doc comment, or a
    longer identifier cannot match. That is the entire reason for this approach over a regex, and it is
    also a large part of what replaces the missing golden safety net — the tool is incapable of
    producing the class of error a picture would have caught.

    Apply edits back-to-front by offset so earlier rewrites do not invalidate later offsets.

    **Hard refusals — skip and report, never rewrite:**
      - Any occurrence inside a `const` expression or a `const` constructor invocation. `context.gw.x`
        is a runtime read; substituting it there produces "invalid constant value". 22-05 deliberately
        added `const` constructors that sit on exactly these sites in four known files.
      - Any occurrence with no `BuildContext` in scope: static fields, top-level variables, field
        initialisers, and any class that is not a widget (controllers, painters, models).
      - Anything inside `lib/theme/` itself. That is the token layer; it reads its own primitives and
        must keep doing so.
      - Anything under `test/`. Six test files import the legacy palette directly
        (`test/banxa/order_card_test.dart`, `test/banxa/order_details_card_test.dart`,
        `test/dashboard/transaction_filter_rail_test.dart`, `test/theme/nav_chip_style_test.dart`,
        `test/theme/theme_contrast_test.dart`, `test/tokens/coin_page_components_test.dart`). They are
        23-04's problem, not this plan's — a test asserting a token identity is legitimately reading
        the primitive layer today.

    Emit a machine-readable refusal report: path, line, symbol, reason. That report is Task 3's input,
    so make it complete rather than pretty.

    Support `--dry-run` (default) and `--apply <path>`, plus `--self-test` proving on a small inline
    fixture that the tool rewrites a plain access, refuses a `const` one, and does not match an
    identically-spelled occurrence inside a string literal or a comment. That self-test is the only
    thing standing between "the tool is correct" and "the tool ran without erroring".

    Run the dry-run across `lib/` and read the whole report before applying anything. If the refusal
    count exceeds roughly a third of the token map's total, stop and say so in the SUMMARY before any
    diff lands — that changes the shape of 23-03 and the developer should hear it before, not after.
  </action>
