<objective>
Close the residue 23-02 could not rewrite, then fix the colour sites that are actually **wrong** —
not merely untokenized. Three named offenders, measured 2026-07-28:

- `lib/components/toast/toast_widget.dart` — a fully inverted light-mode palette. Toasts are how the
  app reports success and failure; unreadable ones in light mode are a real defect.
- `lib/components/buttons/gw_button.dart` — a design-system component hardcoding a raw white
  foreground. A primitive that cannot flip is the worst possible place for this bug, because every
  consumer inherits it.
- `lib/reown/` — the heaviest raw-colour concentration in the app (~74 references across 6 files as
  measured; re-measure, since 23-02 already migrated some), in the dApp connection surface.

as a private message widget, and the fork does not carry the documented light-mode amber contrast fix
that lives at `gw_warning_note.dart:17-21`.

Purpose: make both appearance modes correct where they currently are not, with numbers rather than
opinions.
Output: the residue closed, three offenders fixed, one forked widget deleted, a contrast record, and
new assertions in the repo's existing contrast test file.
</objective>

  <action>
    Work the residue list. Each refusal has one of three shapes and one correct treatment:

    **Const-expression sites.** The enclosing expression is `const` and the accessor is a runtime
    read. Drop the `const` and migrate. Dropping a `const` costs a rebuild-identity optimisation and
    buys appearance correctness; that trade is correct every time here. If a widget is genuinely
    hot-path and losing `const` matters, say so in the SUMMARY rather than leaving the colour behind.

    **Context-free sites** — static fields, top-level constants, controllers, painters, models. Two
    treatments, chosen per site:
      - If the value is consumed by a widget, push the read down into that widget's `build` and let
        the widget read it itself. This is the preferred fix and is usually small.
      - If it genuinely has no widget (a pure data class holding a display colour), leave it reading
        the primitive layer and **record it**. 23-04 needs that list: it is the allowlist of consumers
        that must be served by a narrow named accessor once the primitives go private. Do not invent a
        service locator or a global to manufacture a context — that is an unrequested abstraction and
        it reintroduces the caching bug this whole migration exists to remove.

    **`lib/theme/` sites.** Leave them. That is the token layer reading its own primitives.

    Commit per directory, as 23-02 did. Nothing in this task is a visual fix — the values are equal by
    parity, so any rendering change here is a mistake, not an improvement. If you find yourself
    choosing a *different* token than the site had, stop: that is Task 2 or Task 3 work, and it needs a
    measured ratio, not a judgement call buried in a residue pass.
  </action>

    default, hover, pressed, disabled, and any loading state — in both modes. Disabled states must

    **Measure; do not eyeball.** For each foreground/background pair you touch, compute the WCAG ratio
    in both modes and record it in `23-03-CONTRAST.md`: component, state, mode, foreground value,

    pair below its threshold is not done.

    `contrastRatio` and `themeFor` helpers. For the button, follow the existing `GWButton secondary`
    group's shape: pump the real widget, pull the painted colour out of the tree with
    `tester.widget<...>`, and assert both **identity** against the token and **ratio** against its
    background. Identity is what catches a future repaint back onto a wrong-but-passing colour; the
    ratio alone does not, and the file itself documents a case where exactly that assumption failed.

    This is the substitute for a golden, and it is a better one here: a golden would prove a picture
    changed. These assertions prove the change is *correct*, and they keep proving it.
