<objective>
Build the layer the colour migration needs, and land it as a change that paints nothing differently.

The repo has two colour systems. `GWColors` is a `ThemeExtension` with **21** fields. The legacy
static palette in `lib/theme/genius_wallet_colors.dart` carries roughly **46 public members** (a raw
`static` count today reads 65 including the private `_xDark`/`_xLight` primitive pairs — count the
*public* surface yourself in Task 1 rather than trusting either number) and roughly **260-288** call
sites outside `lib/theme/`. It is already internally layered: private raw values with public
appearance-aware getters on top, switched by the `GWAppearance` global.

The locked decision is NOT to delete the legacy class but to demote it to the private primitive
layer, keeping `GWColors` semantic — the Material 3 primitive → semantic → component model. That
demotion is impossible while `GWColors` covers only 21 of ~46 names, so this plan closes the gap
first. It changes **no call site**.

Purpose: make the 260+ site migration in 23-02 a mechanical prefix rewrite instead of 260 judgement
calls, and produce the value-equality proof that stands in for the golden baseline this phase does
not have.
Output: `GWColors` at full name parity, a `context.gw` accessor, a parity test, and a token map.
</objective>

      | legacy name | GWColors field | already exists? | light value | dark value | appearance-aware? | call sites | const-risk |

    Rules:
      - **Name parity is the goal.** If `GWColors` already has a field for a concept under a
        different name, prefer keeping the legacy spelling as the `GWColors` field name so the rewrite
        is a pure prefix change. A rename inside the migration turns a mechanical codemod into 260
        individual decisions.
      - **Distinguish three kinds of member.** (a) `static const` fixed values — brand, status,
        gradient stops. (b) `static Color get` appearance-aware getters backed by a private
        dark/light pair. (c) derived values built with `withAlpha`/`withValues` off another token.
        Kind (b) becomes two seeded values in `dark()`/`light()`. Kind (c) keeps its derivation
        expression inside the factories — do not flatten it to a literal, that loses the relationship.
      - **Private members stay private.** The private raw pairs are the primitive layer; they are the
        thing being preserved, not migrated. They get no rows.
      - **Record the call-site count per legacy name** (`grep -c` per symbol). Re-measure; the
        recorded figures are 288 (2026-07-28 context) and 260 (a coarser grep at planning time), and
        both are estimates. Record what you actually count.
      - **Flag every `static const` member.** Those are usable in `const` expressions today;
        `context.gw.x` is not. Every such site is a potential "invalid constant value" in 23-02, and
        22-05 added new `const` constructors sitting on exactly these. Four files are already known:
        `lib/components/loading/gw_spinner.dart`, `lib/components/registration_header.dart`,
        `lib/submit_job/view/submit_job_screen.dart`, `lib/tokens/token_info_screen.dart`. This
        column is the single most useful thing in the document.

    Change no code in this task. The map is the deliverable.

    Add a `BuildContext` extension exposing `context.gw`, returning the registered `GWColors`.

    Two rules make it safe:

      1. **Provide a fallback, never a null-assertion.** If the extension is absent, return a sensible
         default (`GWColors.dark()`, matching the app's default appearance) rather than throwing. A
         widget should render slightly wrong in an unusual host, not crash. This matters concretely:
         several existing widget tests pump a bare `MaterialApp` without the app's theme —
         `test/components/gw_card_hover_test.dart` supplies `ThemeData(extensions: [GWColors.dark()])`
         explicitly, but others do not, and a hard assertion would break them all at once.
      2. **Never cache the result.** The accessor reads inside `build`. Document on the extension that
         storing its result in a controller, painter or model is forbidden — that is the documented
         failure where a screen keeps rendering the previous brightness after an appearance switch.

    Keep it in its own small file under `lib/theme/` rather than appending to `gw_colors.dart`. The
    extension is API surface for the whole app; `gw_colors.dart` is the token definition. They will be
    edited by different people for different reasons.

    Add two cases to the parity test:
      - `context.gw` inside a widget wrapped in the app's real theme returns the same values as
        `Theme.of(context).extension<GWColors>()`;
      - `context.gw` inside a bare `MaterialApp` with no extension registered returns the fallback and
        does not throw.

    Note for the test author: `MaterialApp` wraps content in an implicit `AnimatedTheme`, so a test
    that switches the `GWColors` host across sequential `pumpWidget` calls needs `pumpAndSettle()`,
    not a bare `pump()`, or it reads the pre-transition value. That is a recorded finding from Phase
    09-01 in this repo — do not rediscover it.

    Change **no call site** in this plan. Both accessors are live from here; 23-02 does the migration.
  </action>

| Boundary | Description |
|----------|-------------|
| theme registration → every widget | If `GWColors` is not registered, every widget silently falls back; nothing warns |
| token values → accessibility | These values encode measured WCAG ratios; a mis-seeded value is an a11y regression that compiles and looks plausible |
| parity test → the whole phase | With no golden baseline, this test is the only thing standing between 23-02 and an undetectable repaint |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-23-01 | Tampering | seeded values in `GWColors.dark()`/`light()` | critical | mitigate | Seed by reading existing private primitives, never by retyping hex. Parity test asserts every field in both modes; acceptance requires confirming the diff introduces no new hex literal. |
| T-23-02 | Repudiation | a parity test that passes vacuously | high | mitigate | Field-count assertion ties the test to the class: a field added to one side and not the other fails rather than being skipped. Both modes exercised via `themeFor`. |
