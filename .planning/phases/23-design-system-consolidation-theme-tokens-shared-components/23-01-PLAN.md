<objective>
Build the layer the colour migration needs, and land it as a change that paints nothing differently.

Today the repo has two colour systems. `GWColors` is a `ThemeExtension` with **21** fields.
`GeniusWalletColors` is a static class with roughly **46** public members and **288** call sites
outside `lib/theme/` — and it is already internally layered: private `_xDark`/`_xLight` raw values
with public appearance-aware getters on top, switched by the `GWAppearance` global.

The locked decision is not to delete `GeniusWalletColors` but to demote it to the private primitive
layer, keeping `GWColors` as the semantic layer — the Material 3 primitive → semantic → component
model. That demotion is impossible while `GWColors` covers only 21 of 46 names, so this plan closes
the gap first.

Migration mechanics are taken from research: field-for-field **name parity** so call sites change
only in prefix, seeded from the existing palette so rendering is byte-identical, accessor with a
fallback, and the CI gate landing last. This plan does the first three. It changes **no call site**.

Purpose: make the 288-site migration in 23-02 a mechanical prefix rewrite instead of 288 judgement calls.
Output: `GWColors` at full name parity, a `context.gw` accessor, a parity test, and a token map.
</objective>

  <action>
    Produce the map that 23-02's codemod will drive from. One row per **public** member of
    `GeniusWalletColors`, with columns:

      | legacy name | GWColors field | already exists? | light value | dark value | appearance-aware? | call sites | notes |

    Rules for filling it in:
      - **Name parity is the goal.** If `GWColors` already has a field for a concept under a
        different name, prefer keeping the legacy spelling as the `GWColors` field name so the
        rewrite is a pure prefix change. A rename inside the migration turns a mechanical codemod
        into 288 individual decisions.
      - **Distinguish the three kinds of member.** (a) `static const` fixed values — brand, status,
        gradient stops. (b) `static Color get` appearance-aware getters backed by a private
        `_xDark`/`_xLight` pair. (c) derived values built with `withAlpha`/`withValues` off another
        token. Kind (b) becomes two seeded values in `dark()`/`light()`. Kind (c) can stay derived
        inside the factories — do not flatten it to a literal, that loses the relationship.
      - **Private members stay private.** The `_xDark`/`_xLight` values are the primitive layer and
        are the thing being preserved, not migrated. They do not get rows.
      - **Record the call-site count per legacy name** (`grep -c` per symbol). 23-02 uses this to
        order its work and to know when it is done. The total across all rows should approximate the
        288 measured on 2026-07-28.
      - **Flag every member that is `static const`.** Those are usable in `const` expressions today;
        `context.gw.x` is not. Every such site is a potential "invalid constant value" error in
        23-02, and 22-05 added new `const` constructors that may sit on exactly these. This column is
        the single most useful thing in the document.

    Do not change any code in this task. The map is the deliverable.
  </action>

  <action>
    Add a `BuildContext` extension exposing `context.gw`, returning the registered `GWColors`.

    `context.gw` is an established pattern rather than an anti-pattern — `theme_tailor` generates
    exactly such accessors and open Flutter issue #160597 asks for `ThemeExtension.of<T>(context)`
    in the framework itself. Two rules make it safe:

      1. **Provide a fallback, never `!`.** If the extension is absent, return a sensible default
         (`GWColors.dark()` matching the app's default appearance) rather than throwing. A widget
         should render slightly wrong in an unusual host, not crash. This matters concretely: every
         widget test that pumps a bare `MaterialApp` without the app's theme currently works, and a
         `!` would break all of them at once.
      2. **Never cache the result.** The accessor reads inside `build`. Document on the extension
         that storing its result in a controller, painter or model is forbidden — that is the
         documented failure where a screen keeps rendering the previous brightness after an
         appearance switch.

    Keep it in its own small file under `lib/theme/` rather than appending to `gw_colors.dart`; the
    extension is API surface for the whole app while `gw_colors.dart` is the token definition, and
    they will be edited by different people for different reasons.

    Add two cases to the parity test:
      - `context.gw` inside a widget wrapped in the app's real theme returns the same values as
        `Theme.of(context).extension<GWColors>()`.
      - `context.gw` inside a bare `MaterialApp` with no extension registered returns the fallback
        and does **not** throw.

    Note for the test author: `MaterialApp` wraps content in an implicit `AnimatedTheme`, so a test
    that switches the `GWColors` host across sequential `pumpWidget` calls needs `pumpAndSettle()`,
    not a bare `pump()`, or it reads the pre-transition value. That is a recorded finding from
    Phase 09-01 in this repo — do not rediscover it.

    Change **no call site** in this plan. Both accessors are live from here; 23-02 does the migration.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| theme registration -> every widget | If `GWColors` is not registered, every widget silently falls back; nothing warns |
| token values -> accessibility | These values encode measured WCAG ratios; a mis-seeded value is an a11y regression that compiles and looks plausible |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-22-35 | Tampering | seeded values in `GWColors.dark()`/`light()` | high | mitigate | Seed by reading the existing private primitives, never by retyping hex. A parity test asserts every field in both modes, and the 22-07 goldens must be byte-identical. |
| T-22-36 | Information Disclosure | lost WCAG rationale comments | medium | mitigate | Carrying over each token's doc comment, including measured ratios and `ponytail:` ceilings, is an explicit acceptance criterion. A contrast fix without its reason gets undone. |
| T-22-37 | Denial of Service | `context.gw` throwing on a missing extension | high | mitigate | Fallback instead of `!`, with a test that pumps a bare `MaterialApp` and asserts no throw. |
| T-22-38 | Tampering | `ThemeData.copyWith` silently dropping extensions | high | accept | `theme.dart` contains none today and this plan adds none; the hazard is documented in-plan and in the file so a future edit is informed. Accepted because adding a guard would be an unrequested abstraction. |
| T-22-39 | Spoofing | a cached theme value surviving an appearance switch | medium | mitigate | The accessor's doc comment forbids caching; the extension is trivially cheap to re-read inside `build`. |
</threat_model>
