> gsd-ui-researcher, verified by gsd-ui-checker.
>
> **RE-SKIN ONLY (09-CONTEXT.md D-01/D-02/D-03, authoritative).** This phase does NOT touch
> behaviour, wiring, the KYC redirect, or the buy state machine. It locks how the shipped

## Spacing Scale

The established `GeniusWalletConsts.space*` set (already on develop). No new values.

| Token | Value | Usage on these surfaces |
|-------|-------|--------------------------|
| space2 | 4px | Icon-to-text gaps inside badges/pills |
| space4 | 8px | Label → field gap (`GWTextField`'s own convention); row internal gaps |
| space6 | 12px | Card internal row gaps; banner/notice padding |
| space8 | 16px | Card padding baseline (`GWCard` default); page horizontal padding on narrow |
| space10 | 20px | Buy-screen column padding; `horizontalDesktopPadding` companion |
| space12 | 24px | Section breaks; error/empty-state icon-to-title gap (full size) |
| space16 | 32px | Page-header → content gap (matches Transactions/Markets/News) |

**Exceptions:** none. Every literal `EdgeInsets.all(...)`/`SizedBox(height: ...)` in the six
in-scope files must round to the nearest token above — e.g. `banxa_buy_screen.dart`'s
`EdgeInsetsGeometry.all(20.0)` → `space10` (already exact), `checkout_qr.dart`'s
`EdgeInsets.all(24)`/`EdgeInsets.all(32.0)` (KYC linux branch) → `space12`, KYC/payment Linux
branches' `EdgeInsets.all(32.0)` → round down to `space12` (24px) rather than adding a new
`space16`-adjacent literal for a single screen.

**Radius:** cards use `radiusLg` (15px, `GWCard` default / `borderRadiusCard`) — NOT the current
`order_card.dart`'s hand-set `BorderRadius.circular(12)` (that becomes `GWCard`'s default, so the
explicit radius argument is simply dropped). Buttons use `radiusPill` (48px, `GWButton`'s own
shape) — NOT the current status pill's `BorderRadius.circular(20)` or the action buttons'
`BorderRadius.circular(8)`, both replaced wholesale by `GWButton`/badge components below.

## Typography

| Role | Size | Weight | Line Height | Usage on these surfaces |
|------|------|--------|-------------|--------------------------|
| Heading | 24px (`headlineLg`) | 600 | 32/24 (1.33) | Page titles via `GWPageHeader`/back-arrow AppBar title ("Buy Crypto", "My Orders", "Order Details") |
| Title | 18px (`titleLg`) | 600 | 24/18 (1.33) | Order-card headline ("Order #…"), empty/error-state titles, KYC/payment Linux-fallback headline (replaces the current raw `Theme.of(context).textTheme.headlineMedium`) |
| Body | 16px (`bodyLg`/`bodyMd`) | 400 | 24/16 (1.5) | Field values, order detail rows, quote lines, disclaimer body, "Waiting for payment…" status line |
| Body small | 14px (`bodySm`) | 400 | 20/14 (1.43) | Secondary/meta text: order dates, wallet-address caption, helper text |
| Label | 13px (`labelMd`) | 500 | 18/13 (1.38) | Field labels (`GWTextField`'s own label row), status badge text, order-info row labels ("Fiat:", "Crypto:", "Payment:") |

Weights used: **regular (400)** + **semibold (600)**, with **medium (500)** on labels/badges only
(matches the existing `labelMd` component-internal convention, same as Phase 8's typography
table — not a third free-standing weight).

No numeric-display exception is needed on these surfaces (unlike Swap's locked 38px hero amount)
— Banxa's amounts are body-weight inline values, not a hero editing field.

### ⚠ Accepted deviation — the generic 4-size / 2-weight limit does not apply here

`gsd-ui-checker` BLOCKED this table on 2026-07-27 against its standard rule (max 4 font sizes, max
2 weights). **The block was reviewed and overridden**, with the evidence:

1. **This ramp is not invented here.** All five roles are shipped tokens in
   `lib/theme/genius_wallet_typography.dart`, which carries a *larger* ramp than this table uses —
   sizes 32/28/24/20/18/16/14/13 across weights 700/600/500/400. This spec is a **subset** of it.
2. **The ramp was settled in Phase 02**, whose entire purpose was establishing design tokens, and
   it has been cited by every frontend UI-SPEC since — phases 02, 03, 04, 05, 06 and 08 all use
   `headlineLg` / `titleLg` / `bodySm` / `labelMd` and passed the same checker.
3. **Complying would cause the harm the spec exists to prevent.** Dropping the 500 weight or the
   13px tier for Banxa alone would make it the ONE surface in the app whose labels and badges render
   differently from Transactions, Markets, News and Swap — a visible inconsistency, introduced by a
   phase whose governing rule (`PROJECT.md` §65) is *"Re-skin, never restructure."* Changing the
   app-wide type ramp is restructuring the design system, and it is out of scope for this phase.

The checker's rule is a sound default for a greenfield design system. It is the wrong instrument
for a re-skin phase applying an established one. If the ramp is ever genuinely too wide, that is a
design-system decision for its own phase — not a Banxa side effect.

**All other five dimensions passed** (copywriting, visuals, color, spacing, registry safety), and
the checker independently confirmed every cited token exists in shipped code.

## Color

60/30/10 discipline, all via the appearance-aware `GWColors` extension (dark / light) — the same
tokens Phase 5 (Transactions/Markets) and Phase 8 (Swap/Bridge) already ship:

| Role | Token (dark / light) | Usage |
|------|----------------------|-------|
| Dominant (60%) | `surfaceBase` — `#0B0D12` / `#DCE0E6` | Scaffold background on every in-scope screen |
| Secondary (30%) | `surfaceElevated` — `#0C0E14` / `#FFFFFF` | Order cards, quote card, order-detail card, buy-screen form fields |
| Accent (10%) | brand CTA gradient `#0AD89C → #0AAEE6` (`GeniusWalletGradient.brandCta`, via `GWButtonVariant.gradient`) | **Only** the money-moving primary CTA per screen: "Create Order", "Complete Payment", "Copy Link" (checkout QR's primary action) |
| Destructive | `statusError` (`GeniusWalletColors.statusError`, appearance-aware via `GWColors.statusError`) | Declined/cancelled/failed order status, error banners, error states |
| Warning | `GeniusWalletColors.statusWarning` (`#FFC42E`, currently mode-invariant — no `GWColors.statusWarning` field exists yet, unlike success/error) | Pending/pendingPayment order status badge, KYC-cancelled banner |
| Success | `statusSuccess` (appearance-aware) | Completed order status badge/banner |
| Secondary text | `textSecondary` | Field labels, order meta rows, helper/disclaimer text |

**Accent reserved for:** the one primary money-moving CTA per screen (Create Order / Complete
Payment / Retry-fetch-currencies / Copy checkout Link) — **never** for "See Details" (tertiary),
"Retry Order" (secondary/outline), the KYC/Refresh/New-Order AppBar icon actions, or any status
badge. Status badges use the **semantic** success/warning/error/slate ladder below, not the brand
gradient — a completed order is not a call to action.

**Status → color mapping (order status, one ladder reused across `order_card.dart`,
`order_details_card.dart`, and `order_details_page.dart`'s banner — mirrors the transaction-badge
precedent, sketch 011 "Scheme 1 Restrained"):**

| Status (`order.status`, case-insensitive) | Token | Badge/text |
|---|---|---|
| `completed` | `statusSuccess` | green, filled-tint pill background (`statusSuccess.withAlpha(31)`) + colored text, mirrors `GWErrorBanner`'s own recipe inverted to success |
| `pendingpayment` / `pending` / `inprogress` | `GeniusWalletColors.statusWarning` | amber tint background + colored text |
| `declined` / `cancelled` / `expired` / `failed` | `statusError` | red tint background + colored text |
| anything else (unknown status string) | `textSecondary` on `gw.surfaceMenu` | slate/neutral — never falls back to `Colors.grey` |

This directly replaces `order_card.dart`'s `_getStatusColor()` (today: `Colors.green` /
`Colors.orange` / `Colors.red` / `Colors.grey`, opaque, no tint) and
`order_details_card.dart`'s two-way `Colors.green : Colors.orange` ternary (today has **no**
red/error branch at all — a completed-vs-not-completed binary that paints a declined or expired
order the same amber as a merely-pending one). Extending it to the full 4-bucket ladder is
in-scope re-skin, not new behavior: the status **string** is unchanged, only its **paint** gains
the branch it was missing.

**Banner (order_details_page.dart's `_bannerColor`/`_bannerText`, sourced from
`BanxaHelpers.getBannerInfo()`):** `banxa_helpers.dart` is out of scope (D-06) and its pastel
`Colors.amber.shade100`/`Colors.red.shade100`/`Colors.green.shade100` literals stay as they are
at the source. **Do not paint those literals as an opaque solid fill** (today's
`order_details_card.dart:42` does exactly that, which reads as a wrong, undertinted block against
a dark card and has no defined text color of its own). Instead, `order_details_page.dart`
(in-scope per the addendum below) must classify the **same** three status strings it already
switches on (`cancel` / `failure`+`failed` / `success`+`completed`) into the semantic ladder above
(warning / error / success) and hand `order_details_card.dart` a semantic token, not the helper's
raw pastel `Color`. Render as a tinted banner using the `GWErrorBanner` recipe (≈12% alpha fill,
`radiusMd`, colored icon + colored text) — the same container language already shipped for error
banners, now generalized to all three severities. This is Claude's discretion on exact mechanism
(new enum param on `OrderDetailCard` vs. re-deriving inside it) — the visual contract is fixed,
the plumbing is not.

**WCAG note (hard project rule, all phases):** every pairing above must hold AA in both modes and
in every state, including disabled. `statusWarning` (`#FFC42E`) has **no light/dark split today**
— verify its contrast against both `surfaceElevated` light and dark during the phase walk before
shipping it as running text/badge-text color; if it fails AA as text, use it as the tint/icon
color only and keep the label in `gw.textPrimary` (the same fallback `GWErrorBanner` would use if
its own token failed — check, don't assume the sketch-era literal transfers).

### Orders history (`banxa_orders_history.dart`) — list + two real empty situations

Same "two distinct empty situations" discipline Phase 12 established for Transactions
(`sketch 028`): a **never-purchased** wallet and a **filtered-to-nothing** result read
differently.

- **Never purchased** (no orders at all, no filter applied): `GWEmptyState` with the "New Order"
  action (Copywriting table above) — the only path forward is creating one.
- **Filtered to nothing** (a status/date filter narrows `orders` to zero from a non-empty base):
  same `GWEmptyState` shell, message swaps to **"No orders match this filter."**, and
  `actionLabel` becomes **"Clear Filter"** (resets `selectedStatus`/`startDate`/`endDate`) instead
  of "New Order" — do not offer "New Order" when the user's actual problem is an over-narrow
  filter. This is a small, additive branch on top of the existing `applyFilters` call, not a new
  capability (Claude's discretion on the exact `orders.isEmpty` condition split — the cubit
  already carries enough state to distinguish "zero total" from "zero after filter" via whatever
  the unfiltered baseline is, or the filter values themselves being non-default).
- Grid stays `GridView.builder` with `OrderCard` — no layout change, only the card's own re-skin
  above.

### Order details (`order_details_page.dart` + `order_details_card.dart`)
