<objective>
Make `/buy` the buy page, on the app's shared page frame, with the order history beside it - and
remove every element the code cannot honestly supply.

Purpose: `router.dart:80` maps `/buy` to `OrdersPage`. A user who taps "Buy GNUS" expecting to buy
is shown a list of things they have already bought; the buy form is at `/createOrder` and the only
route to it is a small `+` on that list (`banxa_orders_history.dart:192`). Separately, this is the
last surface in the app still using bare Material `DropdownMenu` and `TextField`.

Output: a two-column buy page - form left, orders rail right - on the same frame Transactions,
Markets and News share, built from components that already ship.

Design: `.planning/sketches/167-banxa-buy-flow/final.html` (approved 2026-07-30).
Rationale and the rejected alternatives: `.planning/sketches/167-banxa-buy-flow/DECISION.md`.
</objective>

<constraints>
- **Do not create git commits.** `AGENTS.md:23` forbids it in this project.
- **Do NOT add a verification status anywhere.** `BanxaApiService.submitKYC`
  (`banxa_api_services.dart:36`) posts KYC data and returns `accountId` + `accountReference`;
  nothing stores or reads back whether the user is verified. A repo-wide search for `isVerified` /
  `kycStatus` / `verificationStatus` finds only the onboarding recovery-phrase flow. The header
  carries an **action** (`Verify with Banxa` → `context.push('/kyc')`), never a pill, a badge or a
  colour that implies a state.
- **Do NOT make the quote live.** `getQuote()` is explicitly triggered and guards on `canGetQuote`
  (`create_order_cubit.dart:148`). Adding a debounce on amount/selection change is a cubit
  behaviour change that also touches Banxa's rate limits, and is out of this plan's fence.
- **Do NOT touch the KYC redirect logic.** `09-OUTSTANDING.md` criterion 2 is a live blocker in
  `kyc_registration.dart` / `banxa_payment.dart`; 09-06 proved it byte-identical to what shipped
  before Phase 9. It is a behaviour fix and is not this plan.
- **No new shared components.** Everything composes from what ships. The orders rail is a
  `StatelessWidget` local to this feature - it is one consumer, under the Rule of Three
  (`AGENTS.md:53`).
- Every `if` braced, body on its own line (`AGENTS.md:32`). `tool/check_brace_style.sh --count`
  stays at 0.
- No raw colour literals. `tool/check_raw_colors.sh --count` stays at 0. Read colours through
  `context.gw` / `GWColors`.
- Widgets, not `_buildFoo()` helpers (`AGENTS.md:49`).
- No em dashes in user-facing copy. Use " - " (space hyphen space).
- `lib/navigation/router.dart` is shared; change only the one `/buy` builder.
</constraints>

<task type="auto" tdd="true">
  <name>Task 1: Per-status order counts, derived from the list the filters already read</name>
  <files>lib/banxa/banxa_order/banxa_order_state.dart, lib/banxa/banxa_order/banxa_order_cubit.dart, test/banxa/order_status_counts_test.dart</files>
  <behavior>
    - With no orders loaded, every count is zero and no count is null.
    - The all-count equals the total number of loaded orders.
    - A count for a status bucket equals the number of orders `applyFilters` returns for that
      bucket, for every one of the four buckets.
    - Orders whose raw status string is unrecognised fall in the neutral bucket rather than being
      dropped, so the four bucket counts always sum to the all-count.
    - Counts are computed from the FULL list, not the filtered one, so selecting a filter does not
      change the numbers shown on the other filters.
  </behavior>
  <action>
Counts are a derivation, not a new source: `OrdersState.orders` already holds the full list
(`banxa_order_state.dart:7`) and `applyFilters` already narrows it by `status`
(`banxa_order_cubit.dart:87-95`).

Add a getter on `OrdersState` returning the count per `OrderStatusTone`, keyed by the tone enum
already defined in `order_status_style.dart:13`, plus a total. Derive each order's tone through
`orderStatusTone(order.status)` rather than matching status strings again - the switch at
`order_status_style.dart:18-30` is the single ladder 09-01 established, and re-deriving it here is
how the two would drift.

**Compute from `orders`, never from `filteredOrders`.** If the counts read the filtered list, then
selecting "Pending" would recompute every other count to zero, and the chips would contradict
themselves the moment one is tapped.

Bucket-count summation is the load-bearing property: `orderStatusTone`'s `default` returns neutral,
so no order can be lost. Assert that the four bucket counts sum to the total, in a test that feeds
an order with a status string the ladder does not name.

Write `test/banxa/order_status_counts_test.dart`. Build `OrdersState` directly with hand-made
`Order` fixtures - no cubit pump is needed for a pure getter. Reuse the fixture helpers 09-01 put
in `test/banxa/`.
  </action>
</task>

      → Padding.fromLTRB(12, GeniusWalletConsts.space32, 12, GeniusWalletConsts.space8)
        → ConstrainedBox(maxWidth: GeniusBreakpoints.xxl)
          → Column(crossAxisAlignment: stretch)

The `Padding` sits OUTSIDE the `ConstrainedBox`, not inside. `transactions_screen.dart:60-70`
explains why and says not to simplify the two into one: nested the other way the content box comes
out 24px narrower and quietly disagrees with the other tabs' arithmetic.

Header: `GWPageHeader(title: 'Buy GNUS', subtitle: 'Powered by Banxa', trailing: <verify button>)`.
The trailing is a `GWButton` at `GWButtonSize.sm`, label `Verify with Banxa`, pushing `/kyc`. It is
an action - give it no status colour, no dot, no pill.

**Replace the three `DropdownMenu`s with `GWSelect`** (`:174`, `:196`, `:218`). The existing
`ValueKey(state.selectedX)` on each is there to force a rebuild when the cubit's selection changes
underneath; carry that behaviour across rather than dropping it. Keep every call into the cubit
unchanged - `selectFiat`, `selectCrypto`, `selectPaymentMethod`.

**Replace the two `TextField`s with `GWTextField`** (`:240`, `:323`). The amount field keeps
`setAmountText` as its `onChanged` and keeps the controller-sync guard at `:89-91`, which exists
because the cubit can rewrite the amount.

**Layout.** A `LayoutBuilder` at `GeniusBreakpoints.large`: at or above, a `Row` with the form and
the rail each in an `Expanded`, `crossAxisAlignment: start`, `space8` between; below, a `Column` in
the same order. Do not use `IntrinsicHeight` here - the two columns are unrelated in height and
forcing them to match would stretch whichever is shorter for no reason.

**The quote grid renders in both states.** A `GWDetailGrid` with three rows - You get, Rate, Banxa
fee. When `state.quote == null`, each value is a single em-dash-free placeholder (`-`) in
`gw.textPrimary38`; when it is non-null, the real values in `gw.textPrimary`. Rendering the grid in
both states is what keeps the card's height stable, so the rail beside it does not shift when a
quote lands.

**One CTA, two rungs.** A single `GWButton(variant: gradient, size: lg)`. Read the label and the
enablement from state, never from a local flag:

    quote == null  → label 'Get quote', onPressed enabled when canGetQuote,  action getQuote()
    quote != null  → label 'Buy GNUS',  onPressed enabled when canCreateOrder, action createOrder()

Both guards already exist at `create_order_state.dart:153-155`; read them, do not restate the
conditions. When the quote is present, add the line "You will finish payment on Banxa." under the
button in `bodySm` / `gw.textSecondary`.

Keep the existing loading and error surfaces the file already has - `isLoadingOverlay`,
`errorMessage`, and the disclaimer dialog at `:341`. This plan changes chrome, inputs and layout,
not the order lifecycle.

height rather than letting it size itself - `09-OUTSTANDING.md` records that `GWEmptyState`

has never been observed at a real window size. Bounding it here removes that unknown for this
surface.
