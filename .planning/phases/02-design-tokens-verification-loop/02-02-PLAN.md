<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| build-time define → shipped binary | `GW_DEV_TOOLS` is attacker-irrelevant but developer-settable; the question is whether it can leak dev affordances into a release build of a self-custody wallet. |
| dev tooling → wallet state | `DevToolsWidget` triggers test transactions/swaps/buys against real app state. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-04 | Elevation of Privilege | `kShowDevTools` reaching a release build | high | mitigate | Task 2 ANDs the flag with `kDebugMode` at the call site, so `--dart-define=GW_DEV_TOOLS=true` on a release build is inert — the tree-shaken const folds the branch away. The automated gate greps for the conjunction specifically, and greps that the bare debug-only guard is gone. This is the reason UI-SPEC §8 forbids using `kShowDevTools` alone as a guard. |
| T-02-05 | Spoofing | Fabricated wallet/transaction data mistaken for real data | medium | mitigate | This plan is the mitigation: the `Dev` row (test transaction / swap / buy) is off by default, so a reviewer walking a debug build cannot accidentally inject or mistake test data. The onboarding `Mock` button (fake wallet + 20 fake transactions) does not exist on develop and is gated in Phase 6 by this same flag. |
| T-02-06 | Repudiation | Dev-triggered transactions in logs | low | accept | `DevToolsWidget` predates the redesign, is unchanged by this plan, and is now strictly harder to reach than before. No new capability is introduced. |
</threat_model>
