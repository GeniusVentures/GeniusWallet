<objective>
Append the redesign's new token vocabulary to the three theme files develop already ships, WITHOUT
changing what a single existing symbol resolves to. This is the riskiest plan in the phase: these
three files are imported by every un-ported screen, and the design branch's versions of them keep
develop's symbol names while silently repointing them at new values. Porting those repointings is
exactly how the app re-skins in one step — the failure mode this whole milestone exists to avoid.

The rule, from UI-SPEC §1.2, governs every line of this plan:

> **Additive-only, this phase.** A symbol lands in Phase 2 only if it is a *new* name that no
> currently-shipping screen references. Any name that already resolves to a value a screen depends
> on today keeps that exact value until the phase that ports the screen consuming it changes it on
> purpose.

Purpose: the vocabulary has to exist before anything can be skinned (ROADMAP: "Nothing can be
skinned before the vocabulary exists"), and it has to land invisibly (ROADMAP criterion 2).
Output: three appended files, zero behavior change, `theme.dart` untouched.
</objective>

<why_zero_deletions_is_the_gate>
Read this before starting. It is the reasoning the whole plan rests on.

For `genius_wallet_colors.dart` and `genius_wallet_gradient.dart` the port is a pure insertion:
new members are added inside the existing class body, before its closing brace. Nothing existing is
edited. That yields a mechanical, non-negotiable proof:

- **`git diff --numstat` reports 0 deleted lines** ⇒ no existing line was rewritten, so no existing
  symbol's literal value changed.
- **The file still compiles** ⇒ no existing symbol was shadowed or duplicated, because two members
  with the same name in one Dart class is a compile error.

Those two facts together are sufficient. If deletions appear in either file, the port is wrong —
stop and re-do it as an append, do not rationalise the deletion.

`genius_wallet_consts.dart` is the one exception and is handled differently: Task 2 deliberately
re-points 6 alias lines, which registers as deletions. Those 6 are provably no-ops (each new target
holds the identical number), so that file is gated by per-alias value resolution instead. `appBarHeight`
is NOT one of them.
</why_zero_deletions_is_the_gate>
