> verified by gsd-ui-checker.

## 1. Coexistence Mechanism — the crux of this phase

### 1.1 The collision

`lib/theme/` has 4 files on develop today (`genius_wallet_colors.dart`, `genius_wallet_consts.dart`,
`genius_wallet_gradient.dart`, `theme.dart`) and the design branch **rewrites all four and adds 7
more**. Every un-ported screen already imports `GeniusWalletColors`, `GeniusWalletConsts`,
`GeniusWalletGradient`, and consumes `getThemeData()` (via `MaterialApp(theme: ...)` in
`main.dart`). A wholesale file replacement of any of the four existing files re-skins the whole app
in one step — the exact failure mode this milestone exists to avoid.

Verified per-file, by diffing develop against `GeniusWallet-3514`:

| File | Collision shape | Verdict for Phase 2 |
|------|------------------|----------------------|
| `genius_wallet_colors.dart` | Design keeps every develop symbol name (`lightGreenPrimary`, `deepBlueCardColor`, `btnGradientBlue`, `borderGrey`, …) but **repoints them** to new hex values via a "Backwards-compatibility aliases" + "Legacy constants" block. Also adds ~35 new semantic names (`brandPrimary`, `surfaceBase`, `textPrimary`, …) that don't exist on develop. | **Split.** Port only the new semantic block additively (new static members appended to the existing class). Do **not** port the alias/legacy-constants block — that block is what silently reskins every screen already using those 16 names. |
| `genius_wallet_consts.dart` | Design adds new `space*`/`radius*` tokens, then aliases develop's 6 old names onto them. 5 of 6 aliases resolve to develop's *current* raw value (`horizontalPadding=20`, `borderRadiusButton=48`, …) — a genuine no-op. **`appBarHeight` changes 60→65** — a real visual change, still in active use (`responsive_overlay.dart`). | **Split.** Port the new `space*`/`radius*` block additively. Port the 5 verified-identical aliases (safe, provably no-op). **Exclude `appBarHeight` from the alias block** — keep develop's `appBarHeight = 60` untouched this phase; note the 60→65 bump as a decision for whichever phase re-skins the shell header (Phase 4). |
| `genius_wallet_gradient.dart` | Design's `greenBlueGreenGradient` (used today in `lib/squid_router/swap_settings_drawer.dart` and `lib/screens/banxa_buy_screen.dart`) is redefined as a "legacy alias" pointing at the new `brandCta` gradient — different colors (`gradientGreen→gradientBlue` vs develop's `btnGradientBlue→btnGradientGreen`) **and** a different direction (left→right vs top→bottom). | **Split.** Add `brandCta`, `brandBorder`, `heroWash` as new static members on the existing class. Leave `greenBlueGreenGradient` at develop's current definition, untouched. |
| `theme.dart` | Single exported function `getThemeData()`, called once from `MaterialApp(theme: ...)`. Design's version replaces `ColorScheme`, every button/appbar/nav/checkbox/input theme, and switches `brightness` off `GWAppearance` — plus **drops `floatingLabelBehavior: FloatingLabelBehavior.always`** (finding 36). This is a 100%-collision file: there is no additive way to touch it without re-theming every Material widget in the app. | **Do not touch.** `theme.dart` stays byte-identical to develop's current version for the whole of Phase 2. `floatingLabelBehavior: always` survives for free because the file is untouched (success criterion 5). `theme.dart` becomes the design's version screen-by-screen-adjacent, when the shell (Phase 4) is skinned — that is where `GWAppearance`-driven `brightness` and the new `ColorScheme` actually get consumed. |
| 7 new files (`genius_wallet_typography.dart`, `genius_wallet_elevation.dart`, `genius_wallet_motion.dart`, `genius_wallet_font_size.dart`, `genius_wallet_decorations.dart`, `genius_wallet_text.dart`, `gw_appearance.dart`) | No develop equivalent — new class names, new file paths. | **Port wholesale**, verbatim except the two adaptation notes in §1.3. Zero collision risk. |

### 1.2 The mechanism, stated as a rule

> **Additive-only, this phase.** A symbol lands in Phase 2 only if it is a *new* name that no
> currently-shipping screen references. Any name that already resolves to a value a screen depends
> on today keeps that exact value until the phase that ports the screen consuming it changes it on
> purpose. `theme.dart` — the one file where "new vs. old" can't be separated symbol-by-symbol
> because it's a single function replacing the whole Material theme — is simply not touched.

This directly satisfies ROADMAP Phase 2 success criterion #2 ("every existing screen renders
exactly as it did before... tokens coexist; nothing is skinned yet") because:
- No existing screen's imports change.
- No existing symbol's resolved value changes (the one exception, `appBarHeight`, is explicitly
  excluded — see table above).
- `theme.dart`, which every Material widget in the app reads from, is untouched.

### 1.3 Adaptation notes for the 7 additive files

Two mechanical changes are required when porting verbatim (both because develop's dependency
choices differ from the design branch's, not because of any coexistence risk):

1. **`gw_appearance.dart`** imports `package:hive_flutter/hive_flutter.dart` (classic Hive). Develop
   uses `hive_ce_flutter` (PROJECT.md: "develop uses `hive_ce`; develop's data layer wins"). Change
   the import to `package:hive_ce_flutter/hive_flutter.dart` — the `Hive.box()` / `ValueNotifier`
   API surface used by `GWAppearance` is identical between the two packages, so no other line
   changes.
2. **`hive/constants/cache.dart`** does not yet have `preferencesBoxName` / `appearanceModeKey` on
   develop. Add both as new top-level `const String` (additive — develop has 16 other box/key
   constants in this file already; append, don't reorder). Add `await Hive.openBox(preferencesBoxName);`
   to `hive/init.dart`'s `initHive()` (additive line — every other box-open call in that function is
   independent and order-insensitive for this addition). Without this, `GWAppearance.load()` throws
   on the un-opened box the first time anything touches it.
3. **`genius_wallet_decorations.dart`**'s `GWCanvasBackground` widget references
   `assets/images/textures/noise.png`, an asset this phase does **not** bundle (`DS-04`/`d8db88c`
   owns `assets/images/textures/` and lands in Phase 3). Port `GWDecorations` (the `BoxDecoration`
   helpers: `surface()`, `pill()`, `actionCircle()`, `heroGlow`) — none of those touch the texture
   asset. Port `GWCanvasBackground` as a class (it compiles fine unreferenced) but **do not
   instantiate it anywhere in Phase 2** — instantiating it without the bundled asset either throws
   or silently renders a blank/missing-asset icon, which is itself a Phase-3-owned bug (DS-04),
   not a Phase 2 concern. The probe surface (§4) must not use it.

### 1.4 `pubspec.yaml`

Add `google_fonts: ^6.2.1` (pinned to the version the design branch already validated). This is a
new dependency, not a version bump of anything develop already depends on — zero collision risk to
existing screens (nothing on develop currently calls `GoogleFonts.*`).

### Justification (checker Dimension 5 — spacing/radius): accept source values, do not consolidate

The checker blocked because the spacing values above (12px, 20px, 40px) fall outside its default
"standard set" (4/8/16/24/32/48/64) and because `radiusBase`/`radiusLg` (10px/15px) aren't
multiples of 4. Verified against source and resolved as **(b) — justify and accept**, not
consolidate:

- **Spacing is not invented — it's copied.** Every value in the table above is
  `DESIGN_SYSTEM.md` §3.3's own token table verbatim: `space2`=4px … `space32`=64px, including
  `space6`=12px, `space10`=20px, `space20`=40px, none of which the design system treats as
  exceptions — they're core rungs of its own scale, called out with explicit "common use" roles
  (`space10` = "Mobile horizontal page padding"; `space20` = "Desktop horizontal/vertical page
  padding"). `gnus-tokens.json`'s `spacing` set mirrors the same 10 values 1:1 (Tokens Studio
  export, migration v1.4). Consolidating them to the checker's 7-value subset would mean the ported
  app pads mobile screens and desktop screens identically — a real, visible divergence from both
  the design system and the marketing site it shares tokens with (`DESIGN_SYSTEM.md` §1 Principle 1:
  "One palette, two surfaces... Tokens are identical").
- **The grid constraint the checker cares about — 4pt alignment — is fully met.** 4, 8, 12, 16, 20,
  24, 32, 40, 48, 64 are all exact multiples of 4 (`DESIGN_SYSTEM.md` §1 Principle 4: "4-pt grid.
  All spacing is a multiple of 4"). The checker's "standard set" is a stricter *subset* of the 4pt
  grid, not the grid rule itself — this system simply uses more rungs of the same grid than the
  checker's default heuristic assumes. No value here breaks 4pt alignment.
- **Radius is not spacing and doesn't participate in grid alignment.** `DESIGN_SYSTEM.md` §3.4
  states the radius scale's base explicitly: "The base is **10 px**, matching the website's
  `--radius: .625rem`" — `radiusBase`=10px and `radiusLg`=15px are direct, deliberate ports of a
  rem-based web design token (`0.625rem` × 16 = 10px), not a grid-derived layout value. Confirmed
  identical in `gnus-tokens.json` §`radius`: `"base": {"value": "10"}`, `"lg": {"value": "15"}`
  (lines 43, 45) — both branches agree, so this isn't drift or an invented value, it's the one
  number the adopted system specifies. Consolidating `radiusBase`/`radiusLg` to a 4pt-aligned value
  (e.g. 8px/16px) would visibly change every card, modal, button and text-field corner from the
  shape the marketing site already ships — again the opposite of this milestone's goal.
- **Nothing here was invented.** Every spacing and radius value traces to a specific
  `DESIGN_SYSTEM.md` §3.3/§3.4 row and its `gnus-tokens.json` mirror; none is a Phase-2-only
  addition. Accepted as-is.

### Justification (checker Dimension 4 — typography): accept source values, do not consolidate

The checker blocked on 8 unique sizes (13/14/16/18/20/24/28/32px) and 4 unique weights
(400/500/600/700) against its default max-4-sizes/max-2-weights heuristic. Recount confirmed
accurate against the table above — no correction needed, the checker counted right. Verified
against source and resolved as **(b) — justify and accept**, not consolidate:

- **The scale is not ours to choose — it's `DESIGN_SYSTEM.md` §3.2's own table, v1.0 Adopted,**
  shared with the gnus.ai marketing site (`DESIGN_SYSTEM.md` §1 Principle 1: "Tokens are
  identical — only the surface role flips"; Principle 2: "Never hardcode... If a token is missing,
  add it here first"). `gnus-tokens.json`'s `typography` set mirrors all 13 styles verbatim
  (lines 60–72), including the exact size/weight/line-height/tracking per style — both branches
  agree, so nothing here is a Phase-2 invention. Consolidating to 4 sizes / 2 weights would produce
  a type scale that is neither the marketing site's nor the designer's — a fabrication this
  milestone exists specifically to avoid (see the port framing at the top of this document).
- **13 named styles, not 13 arbitrary sizes.** The apparent "8 sizes" collapses to a smaller
  effective set once duplication is accounted for: `bodyLg`/`bodyMd` are both 16px/400 (identical —
  `DESIGN_SYSTEM.md` §3.2 notes body was "bumped 14→16... now equals `body/lg`" in v1.4), and
  `displayLg`/`numericDisplay` share 32px/700, `headlineLg`/`numericHeadline` share 24px/600,
  `bodySm`/`numericBody` share weight-differentiated variants at 14px. The numeric duplicates are
  deliberate, not scale bloat.
- **The numeric variants exist for a wallet-specific reason: tabular figures.** `numericDisplay`,
  `numericHeadline`, `numericBody` are the same visual sizes as their proportional counterparts but
  render with `FontFeature.tabularFigures()` so balances, addresses and amounts align column-wise
  (`DESIGN_SYSTEM.md` §6.5 "Numbers & money": "Always wrap balances in `numeric/*` styles to get
  tabular figures"; §3.2 rule: "Always use `numeric/*` styles when displaying balances, addresses,
  percentages, or anything that should align column-wise"). Removing them to hit a weight/size cap
  would mean crypto amounts in this wallet render with proportional (non-monospaced) digits —
  a real usability regression for a financial app, not a cosmetic one.
- **`DESIGN_SYSTEM.md` §3.2 itself treats "don't add new sizes" as the actual discipline** ("Don't
  introduce new sizes. If a design needs a new size, add it to this table first... snap to the
  nearest rung, never 15/22") — i.e. the adopted system already enforces a closed, deliberate scale;
  it's just a 13-style scale, not a 4-style one. This phase ports that closed scale unchanged.
- Nothing here was invented — every style traces to a specific `DESIGN_SYSTEM.md` §3.2 row and its
  `gnus-tokens.json` mirror. Accepted as-is.

## 7. Verification Protocol (BLD-02) — this phase establishes it

There is no working `flutter test`. Every criterion below is checked by **running the app** in a
Windows debug build and observing it — this is the loop every later phase inherits.

**Run recipe** (record verbatim in the plan, this is the standing command for the rest of the
milestone):
```
CMAKE_ARGUMENTS="-DCMAKE_BUILD_TYPE=Release -DGENIUS_DEPENDENCY_BRANCH=develop -Dc-ares_DIR=C:/Users/User/Documents/Projects/GNUS/thirdparty/build/Windows/Release/cares/lib/cmake/c-ares" flutter run -d windows --debug
```
(`CMAKE_BUILD_TYPE=Release` is deliberate — the multi-config generator's `--config` drives the
actual build type; the dependency downloader keys off `CMAKE_BUILD_TYPE`.)

**Checks, mapped to ROADMAP Phase 2 success criteria:**

1. **Hot reload + debugger.** With the app running from the recipe above, edit a new token value
   (e.g. `GeniusWalletMotion.base`'s duration) and hot-reload (`r` in the terminal or the IDE hot
   reload button) — confirm the change applies without a full restart. Set a breakpoint in
   `getThemeData()` or the probe surface's `build()` and confirm the Dart debugger attaches and
   hits it.
2. **No-visual-change walk.** With the app running normally (`GW_DEV_TOOLS` unset), walk every
   currently-reachable screen top to bottom (onboarding → dashboard → token detail → send → swap →
   buy → settings, whatever `go_router` currently exposes) and confirm pixel-for-pixel parity with
   the pre-Phase-2 build — no color shift, no spacing shift, no crash on any route transition. The
   one intentional exception is `appBarHeight`, which does **not** change this phase (§2) — so
   there should be literally zero observable difference.
3. **Token + appearance probe.** See §4/§8 below — open the probe surface, confirm the new tokens
   render, and confirm `GWAppearance.instance.setMode(...)` flips it between dark/light live.
4. **Dev-gating.** See §8. Confirm the `Dev` header row is absent in a normal `flutter run -d
   windows --debug` and present with `--dart-define=GW_DEV_TOOLS=true`.
5. **`floatingLabelBehavior`.** Open any existing screen with a text field (e.g. the PIN/legacy
   onboarding, or any `TextFormField` reachable today) and confirm the label stays pinned above the
   field rather than sitting inside it as placeholder text. This should hold automatically since
   `theme.dart` is untouched (§1.1) — the check exists to catch a regression, not because a change
   is expected.

`flutter analyze` remains a **gate** (must report 0 new errors introduced by this phase's files) but
is never itself evidence of criteria 2–5 — those require the human visual walk above.

## 8. Dev-Tools Gating (BLD-03) — decided approach, not open

Carries commit `f3fd16f` from `ui-redesign-3.514-develop` (already in this repo's history).

**Mechanism** (port verbatim, this is settled):
- New file `lib/dev/dev_flags.dart`:
  ```dart
  const bool kShowDevTools = bool.fromEnvironment('GW_DEV_TOOLS');
  ```
- Every call site combines it with `kDebugMode`: `if (kDebugMode && kShowDevTools) ...` — so it can
  never reach a release build regardless of the define.
- Enable with: `flutter run -d windows --debug --dart-define=GW_DEV_TOOLS=true`.

**What actually exists on develop today to gate:** only
`lib/components/overlay/responsive_overlay.dart:94` —
```dart
if (kDebugMode) const DevToolsWidget(),
```
becomes
```dart
if (kDebugMode && kShowDevTools) const DevToolsWidget(),
```
This is the only call site in Phase 2's scope. The onboarding "Design gallery" + "Mock" buttons
(`wallet_creation_screen.dart`) are **redesign-only** — develop's current `wallet_creation_screen.dart`
has no dev buttons at all, so there is nothing to gate there yet. That half of BEH-02/BLD-03 lands
naturally when Phase 6 (Onboarding) ports `wallet_creation_screen.dart` and `lib/dev/mock_mode.dart`
together — carry the same `kShowDevTools` flag forward at that point rather than reintroducing a
bare `kDebugMode` check.

**Probe surface entry point:** add one more gated call site, inside `DevToolsWidget` (or immediately
adjacent to it in `responsive_overlay.dart`), for the token probe route (§7 item 3 / §9). Reuse
`kShowDevTools` — do not invent a second flag.

## 9. Probe Surface Spec

A new, additive screen + route whose only job is to prove the token layer resolves and flips at
runtime, without any un-ported screen depending on it.

- **File:** new, e.g. `lib/dev/token_probe_screen.dart`.
- **Route:** new `go_router` route, e.g. `/dev/token-probe`. Additive registration only — do not
  reorder or modify any existing route entry.
- **Reachability:** only from the gated dev-tools surface (§8) — never from a normal build, never
  from any existing screen's nav.
- **Content:** a `Scaffold` (not `AppScreenView` — that's an existing develop widget with its own
