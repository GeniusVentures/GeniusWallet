# gnus_* RPC contract, v1 (draft 2026-10-26)

Owner: the GeniusWallet side, GSD milestone v4.0. Canonical copy: GeniusWallet
`.planning/research/v4.0-gnus-rpc-contract.md` (branch `claude/gsd-dashboard-bridge-milestone-b6a5e7`
until merged). The copy in the side-session notes folder mirrors it for the dashboard session.
gnus-dashboard consumes it. `window.gnus.version` bumps on any breaking change.

Status: DRAFT. Decisions marked (D) were taken by the wallet session overnight on Braian's standing
instruction to answer GSD questions itself; Braian can overturn any of them.

## 1. Shape

One call shape on every transport, EIP-1193 style:

```ts
request({ method: string, params?: object }): Promise<result>
// rejects with { code: number, message: string, data?: object }
on(event: string, handler: (payload) => void): void
removeListener(event: string, handler): void
```

- `params` is always an object (named params), never a positional array.
- Amounts are decimal strings, never JS numbers (u64 and 1e18 values overflow `Number`).
- Addresses are lowercase strings with `0x`. Two formats exist and are never mixed:
  - `sdkAddress`: `0x` + 128 hex. The GeniusSDK account (node identity, earns, owns jobs).
  - `evmAddress`: `0x` + 40 hex. The EVM wallet that pays (burns GNUS via `bridgeOut`).
  An SDK address cannot be derived from an EVM address. The dashboard must key "my jobs" and
  "earnings" on `sdkAddress` and show the EVM payer only as a label.

## 2. Transports and detection

| Where the dashboard runs | Transport | Detection |
|---|---|---|
| Inside GeniusWallet (WebView) | Injected `window.gnus` | `window.gnus?.isGeniusWallet === true` |
| Normal browser | WalletConnect session with GeniusWallet | no `window.gnus` |

Rules:

- (D) One provider per session. If `window.gnus` exists, the dashboard does not mount or open
  Web3Modal/WalletConnect at all, and never calls `bridgeOut` or `/api/processing/*` itself.
- In-wallet readiness: on Android, iOS and macOS the shim can only be injected after page start, so
  the dashboard waits for the `gnus#initialized` window event if `window.gnus` is absent at load,
  for up to 3 s, before falling back to the browser path. Windows and Linux inject at document start.
- `window.gnus.version` = contract version string, `"1"`.
- The wallet's WebView user agent ends with ` GeniusWallet/<app version> gnus/<contract version>`, so the
  page knows it is inside the wallet before `window.gnus` arrives and waits for `gnus#initialized`
  instead of guessing.
- WalletConnect (D): the `gnus_*` methods and events ride the `eip155` namespace as
  **optional** methods/events, on chain `eip155:80002` (Polygon Amoy, where `bridgeOut` lives)
  plus the wallet's GNUS chains. The wallet approves a gnus session only if the proposal asks for
  `gnus_*` methods it implements. Payload is identical to the injected path:
  `session_request` with `{ method, params }`; events go out as `session_event` on chain `eip155:80002`
  (sign-client silently drops events whose chainId the session did not approve). `params` is the same
  JSON object as on the injected path.
- Over WalletConnect a request can time out (wallet closed, phone backgrounded). The dashboard shows
  a "wallet offline" state on timeout, not a spinner. WalletConnect requests need an expiry between
  300 s and 7 days: use 60 s on the page side for reads (request expiry 300 s) and a 900 s expiry for
  `gnus_submitJob` and the first connect call (they wait on a human). A submit that expires on the page
  may still complete in the wallet: recover it with `gnus_getJob({ idempotencyKey })`.
- WalletConnect approval (D, 2026-10-28): a proposal is a gnus proposal when its eip155 required or optional
  methods include any `gnus_*` method in section 3 (`gnus_getAddress` is retired). The wallet approves exactly
  those methods, on top of its EVM methods, with the requested events among `gnus_accountsChanged`,
  `gnus_networkChanged` and `gnus_jobUpdated`, and chains that always include `eip155:80002`. A proposal that
  asks for no gnus method is approved as an ordinary dApp session and can call none. Approving the session
  grants nothing by itself: the first `gnus_*` call from the origin still opens the connect prompt.
- WalletConnect origin (D, 2026-10-28): the caller is the origin of the proposal's `metadata.url`, the value
  Reown Verify compares with its attestation, checked once at the proposal. VALID is approved. SCAM and INVALID
  are rejected with a reason. UNKNOWN is rejected in release builds, for every method, reads included; a dev
  build accepts it only for `http://localhost` and `http://127.0.0.1`. So the page sets `metadata.url` to its
  own origin and has that domain verified in its Reown Cloud project. A restored session whose origin the
  wallet would no longer accept gets `4100`.
- WalletConnect encoding (D, 2026-10-28): the Dart client's `JsonRpcError` carries only a code and a message,
  and a null result cannot be sent. When an error has `data`, its WalletConnect `message` is the JSON text
  `{"message": "...", "data": {...}}`. The page parses the message; if it is a JSON object with a string
  `message`, that is the error's message and `data` is its data, otherwise the message is plain text. A null
  result (`gnus_getJob` with no record) is sent as `{}`, and the page reads `{}` as null. No other result in
  this contract is an empty object.
- WalletConnect request lifetime (D, 2026-10-28): reown_sign expires a wallet-side pending request after 5
  minutes whatever expiry the page set. The wallet raises it to 11 minutes (the 10 minute prompt timeout plus
  60 s) for every `gnus_*` request. A reply that cannot be delivered (page expired, session gone, offline) is
  dropped, not retried; recover a submit with `gnus_getJob({ idempotencyKey })`.

## 3. Methods

### `gnus_getAccounts` (read, no prompt)

Params: none. Result:

```json
{
  "node": {
    "sdkAddress": "0x<128 hex>",
    "linkedEvm": "0x<40 hex> | null",
    "role": "main | child | none",
    "main": "0x<128 hex> | null"
  },
  "payer": { "evmAddress": "0x<40 hex> | null", "canSign": true },
  "switching": false,
  "network": { "sdk": "<SDK network name, e.g. staging>", "evmChainId": 80002 },
  "version": "1",
  "unit": { "symbol": "GNUS", "decimals": 18 }
}
```

- `node` is the account the node runs as ("Earn with this account"). `payer` is the wallet that
  pays ("Sending from"). They can differ by design.
- `payer.canSign` is false exactly when `gnus_submitJob` would refuse the payer with `-32012`. It says
  nothing about the balance (`-32011`).
- `payoutAddress` is intentionally absent: the SDK has no getter (SDK dependency SDK-PAYOUT).
- Replaces the spike's `gnus_getAddress`, which is retired.
- `network.evmChainId` is `null` when the wallet has no EVM network selected; `network.sdk` is `null` when the
  SDK network is unknown. The same holds in `gnus_estimate` and `gnus_networkChanged`.
- In-wallet detection: with the GeniusWallet user-agent marker the page waits for `gnus#initialized` without
  falling back to WalletConnect, but after 10 s it shows a "wallet not ready" state while it keeps waiting.
- `version` is the contract version on every transport (over WalletConnect there is no `window.gnus.version`).
- `unit` describes every amount in this contract: amounts are integer base units as decimal strings;
  display = amount / 10^decimals. `decimals` is the GNUS token decimals the wallet uses for `bridgeOut`
  (the example value is illustrative; read it, never hardcode it).

### `gnus_estimate` (read, no prompt)

Params: `{ "job": <processing-definition object> }`. The job object is the SDK's current
processing-definition schema (`inputs`/`outputs`/`passes`, see SuperGenius
`test/src/processing_schema/posenet-processing-job.json`), passed as an object, not a string. The old
`data/model/input` shape is not accepted. A job larger than 5 MiB encoded, or nested deeper than 32
levels, is `-32602`.

Result:

```json
{
  "cost": "<decimal string: the exact amount the wallet would burn, base units>",
  "gas": { "gasPriceGwei": "<decimal string>", "symbol": "<native coin symbol>" },
  "balance": "<decimal string: payer's GNUS balance, same units as cost>",
  "network": { "sdk": "...", "evmChainId": 80002 }
}
```

- `gas` is the bridge transaction's gas price in gwei on the payer's chain (what the wallet can estimate
  before signing), not a total fee; null when it cannot be estimated (the call still succeeds). Show it as a
  network fee rate, never add it to `cost`.
- Wallet-side units (2026-10-27): the SDK cost is burned as whole GNUS, the payer balance is held in whole
  GNUS and the node SGNUS balance has 6 decimals. The wallet converts all of them, in one place, to base
  units of `unit.decimals` (18, the GNUS token's decimals) before answering, so every GNUS amount in this
  contract uses the same unit.
- A zero or failed SDK cost is an error (`-32010`), never `cost: "0"`.
- (D, 2026-10-27) `balance` is null when the payer's balance cannot be read; the estimate still succeeds.
  A submit with an unreadable balance fails closed with `-32603` and `data.reason: "balance_unavailable"`.
- Open question U1: the wallet burns the SDK cost integer as-is; the current dashboard multiplies the
  estimate by 1e18. Until the SDK documents its unit, the wallet's behaviour (burn as-is) is the
  reference: `cost` is in base units and the dashboard displays it with `unit.decimals`, never re-scaled.

### `gnus_submitJob` (spend, native confirm every time)

Params: `{ "job": <processing-definition object>, "idempotencyKey": "<client uuid>" }`.

The wallet does the whole flow atomically, under its existing bridge gate: estimate, show a native
confirm (origin, cost, gas, payer, node account), burn via `bridgeOut` from the payer, then
`GeniusSDKProcess` as the node account. The dashboard never burns by itself.

Result:

```json
{
  "jobId": "<string | null>",
  "burnTxHash": "0x<64 hex>",
  "sdkAddress": "0x<128 hex>",
  "status": "submitted | bridgedNotProcessed | unconfirmed"
}
```

- `jobId` is null until the SDK returns one from Process (SDK dependency SDK-JOBID). Without it,
  `gnus_getJob` cannot work and "my jobs" is keyed on `burnTxHash`.
- `bridgedNotProcessed`: the burn succeeded and Process failed. Funds are spent. The dashboard shows
  a recoverable state keyed by `burnTxHash`; the wallet keeps the record.
- Same `idempotencyKey` within 24 h returns the first call's result instead of burning again (covers
  reloads, double clicks and WalletConnect requests that time out on the page but still reach the
  wallet). Generate the key when the user reaches the review step and persist it before calling, not
  per click. Same key with a different job body: `-32602` with `data.reason: "idempotency_key_reused"`.
- A second submit from one origin while one is in flight: `-32005` with `data.reason: "submit_in_flight"`.
- Rejected confirm: `4001`. A confirm left unanswered for 10 minutes is a rejection too, nothing burned.
- (D, 2026-10-27) The wallet writes the job record at burn time as `bridgedNotProcessed` and moves it to
  `submitted` when Process succeeds, so a wallet killed mid-submit shows the recoverable state.
- (D, 2026-10-28) Before the burn the wallet durably writes a submit intent for `origin|idempotencyKey`.
  If that write fails nothing burns and the call is `-32603`. If the wallet later holds an intent for the
  key but no job record (killed mid-submit, or every record write failed), a same-key submit never burns
  again: it is `-32603` with `data.reason: "submission_outcome_unknown"` and `data` = `{ idempotencyKey,
  burnTxHash, sdkAddress, payer, cost, createdAt }` (`burnTxHash` null when the burn was never recorded;
  every field but `idempotencyKey` null when the intent is unreadable). The page shows the spend as
  unconfirmed and points the user to the wallet; a fresh key is a new submit.
- (D, 2026-10-28) The burn is signed locally and its hash written onto the intent before it is
  broadcast; if that write fails nothing is sent and the call is `-32603` (the key stays blocked). A
  send the node refuses after signing is the `submission_outcome_unknown` error with `burnTxHash` set.
  A send that gets no answer is settled by its receipt for about 75 s: success goes on to Process,
  a revert is `-32013` (nothing burned, the key may be reused), and no receipt is a result with
  `status: "unconfirmed"`, recorded as a job, Process not run. A burn that fails before signing is
  `-32013` and the key may be reused.
- (D, 2026-10-28) An intent with no settled job record blocks its key at any age, past the 24 h
  window too; an `unconfirmed` job does not settle it. After 24 h such a key is
  `submission_outcome_unknown`.

### `gnus_listJobs` (read, no prompt)

Params: `{ "limit"?: 1-100 (default 20), "cursor"?: string }`. Jobs the wallet submitted for the
current node account (from the wallet's own record until the SDK has a per-account history).

Result: `{ "jobs": [Job], "nextCursor": string | null }`, with

```json
Job = {
  "jobId": "<string | null>",
  "burnTxHash": "0x...",
  "sdkAddress": "0x<128 hex>",
  "origin": "<origin that submitted it>",
  "idempotencyKey": "<the key the submit carried>",
  "submittedAt": "<ISO 8601>",
  "cost": "<decimal string>",
  "status": "submitted | queued | processing | completed | failed | bridgedNotProcessed | unconfirmed | unknown | pending"
}
```

`status` is `submitted`, `bridgedNotProcessed` or `unconfirmed` until SDK-STATUS lands; then the live
states. (D, 2026-10-28) `unconfirmed`: the burn was sent and the network neither confirmed nor reverted
it in time; the GNUS may be spent and the job did not start. Check `burnTxHash` on chain.
(D, 2026-10-28) `pending` appears only from `gnus_getJob({ idempotencyKey })`: the wallet recorded the
submit but not its outcome (still in flight, or the wallet stopped mid-submit). On a pending job
`burnTxHash` is null until the burn is signed, `jobId` is null, and the other fields are null only when
the wallet's record is unreadable.
(D, 2026-10-27) Only the current node account's jobs are listed.

### `gnus_getJob` (read, no prompt)

Params: exactly one of `{ "jobId": string }`, `{ "burnTxHash": string }`, `{ "idempotencyKey": string }`
(the last lets a reloaded page find a submit whose response it never saw). Result: `Job` plus
`{ "result": { "cids": [string], "data"?: object } | null, "error"?: string }`.
Needs SDK-JOBID and SDK-STATUS/SDK-RESULT; until then it returns the wallet's own record with
`result: null`.
(D, 2026-10-27) The result is `null` when no record matches for the current node account. A lookup by
`idempotencyKey` only finds keys sent from the same origin.
(D, 2026-10-28) A lookup by `idempotencyKey` with no job record returns the pending submit, if any,
with `status: "pending"` (see `Job`), so a page can recover after a crash.

### `gnus_getEarnings` (read, no prompt)

Params: `{ "includeChildren"?: false }`. Result:

```json
{
  "sdkAddress": "0x<128 hex>",
  "balance": "<decimal string: node account's SGNUS balance>",
  "processing": { "isProcessing": true, "jobsProcessed": "<decimal string | null>" },
  "earned": { "total": "<decimal string | null>", "history": [ { "at": "...", "amount": "...", "jobId": "..." } ] | null }
}
```

- `balance` and `processing.isProcessing` are available now.
- `jobsProcessed`, `earned.*` are null until SDK-EARNINGS lands. The dashboard must render null as
  "not available yet", never as 0.
- (D) `includeChildren` is accepted but ignored in v1 (returns the node account only). Aggregating
  children waits on SDK-EARNINGS.

## 4. Events

| Event | Payload | When |
|---|---|---|
| `gnus_accountsChanged` | the `gnus_getAccounts` result | node or payer account changed, or `switching` flipped |
| `gnus_networkChanged` | `{ sdk, evmChainId }` | SDK network or EVM chain changed |
| `gnus_jobUpdated` | `Job` | a job's status changed (wallet-polled until SDK pushes) |
| `disconnect` | `{ code, message }` | WebView closing, or WalletConnect session ended |

(D, 2026-10-28) Over WalletConnect, `disconnect` is the session's own end: the page receives `session_delete`
(with the wallet's reason code and message) or `session_expire`, and emits `disconnect` itself. The wallet
sends no `disconnect` as a `session_event`, because a deleted session cannot carry one. The other events go out
as `session_event` on `eip155:80002`, only for the names the session approved.

## 5. Errors

| Code | Meaning |
|---|---|
| 4001 | User rejected the confirm |
| 4100 | Origin not allowed, or permission not granted for this origin |
| 4200 | Method not supported |
| 4900 | Wallet not ready (SDK not initialized). Same meaning family as EIP-1193 "Disconnected" |
| -32602 | Invalid params (bad job schema, bad address, out-of-range limit) |
| -32603 | Internal error |
| -32005 | Busy. `data.reason` is `rate_limited`, `confirm_open` or `submit_in_flight` |
| -32010 | Cost unavailable (SDK returned 0 or failed; `data.reason` when the SDK provides one). On `gnus_submitJob` also when the burn's gas estimate fails, before any confirm, except a chain with no bridgeOut, which is `-32013` (D, 2026-10-28) |
| -32011 | Insufficient GNUS balance for `cost` |
| -32012 | Payer cannot sign (watch-only, `sgnus` row, or child without key) |
| -32013 | Bridge (burn) failed; nothing spent |
| -32014 | Burn succeeded, Process failed; `data.burnTxHash` set (same as `status: bridgedNotProcessed`) |
| -32015 | Account switch in progress (`switching: true`); retry after `gnus_accountsChanged`. Not 4901, which EIP-1193 reserves for "chain disconnected" |

(D, 2026-10-27) The `data.reason` values the wallet sends:

| Code | `data.reason` |
|---|---|
| -32012 | `no_wallet`, `view_only`, `child`, `not_earning`, `wrong_network` |
| -32011 | `no_gnus`, `gnus_elsewhere` |
| -32603 | `balance_unavailable`, `checking`, `missing_data`, `submission_outcome_unknown` (a same-key submit whose earlier outcome was never recorded; it may have burned, so nothing burns again) |
| -32015 | `account_changed`: the account, wallet or network changed while the confirm was open; nothing was burned |
| -32013 | `bridge_unavailable`: this network has no GNUS bridge; nothing was signed (D, 2026-10-28) |

## 6. Security rules the wallet enforces (dashboard can rely on them)

- Origins: exact scheme+host+port allowlist, one pinned https origin per network in release builds
  (D); `http://localhost:<port>` only in dev builds. The wallet keys every caller on its transport
  (WebView or WalletConnect) plus its canonical origin: scheme and host lowercased, default port
  dropped, no path, query or fragment. Anything not http(s), or with userinfo, is `4100`. The same
  origin over the other transport is a different caller with its own connection. The bridge drops
  any reply whose origin changed between request and reply.
- (D, 2026-10-28) WalletConnect origins are checked with Reown Verify (section 2), not with the WebView
  allowlist, and fail closed when Verify cannot vouch for the page.
- Top frame only. Messages from iframes never reach the bridge.
- Top-level navigation is locked to the allowlist; popups and `target=_blank` open in the system
  browser.
- Per-origin permission: the first call from an origin asks the user to connect (like
  `eth_requestAccounts`). Reads after that need no prompt; every `gnus_submitJob` prompts. So the
  dashboard's first call (normally `gnus_getAccounts`) can wait on a human: give it no timeout and show a
  "confirm in your wallet" state. Rejecting the connect prompt returns `4001`. Revoking forgets the origin, so
  its next call prompts again; `4100` is an origin outside the allowlist or a call in flight at the revoke.
- Prompt limits (D, 2026-10-28): the connect prompt, like the confirm, is a rejection (`4001`) after 10
  minutes unanswered. One prompt may be open in the wallet at a time, from any origin, and at most 3 per
  minute per origin: a call that needs another prompt gets `-32005` with `data.reason` `confirm_open`
  or `rate_limited` and no dialog.
  A `gnus_submitJob` whose origin is revoked before its burn is sent answers `4100` and burns nothing.
- No method returns keys, mnemonics or anything derived from them.

## 7. SDK dependencies (not wallet work)

| Id | Need | Blocks |
|---|---|---|
| SDK-CA | CA bundle path is the CI runner path baked into the binary, so the price request fails and cost is always 0 | `gnus_estimate`, `gnus_submitJob` live |
| SDK-COSTERR | `GeniusSDKGetCost` returns a bare 0 for every failure; needs error codes | `-32010` `data.reason` |
| SDK-JOBID | `GeniusSDKProcess` returns only a status code; needs a job id | `jobId`, `gnus_getJob` |
| SDK-STATUS | per-job status query (today only node-wide status) | live `Job.status` |
| SDK-RESULT | result query by job id (today `GetTaskResult` takes a task id nobody returns) | `gnus_getJob.result` |
| SDK-EARNINGS | per-account processed-job and earnings history | `gnus_getEarnings.earned`, `jobsProcessed` |
| SDK-PAYOUT | payout address getter | `node.payoutAddress` (future) |
| SDK-ASYNC | async or thread-safe cost/process calls (the wallet will move them off the UI isolate either way) | UI freeze of 100-800 ms per estimate |

## 8. Open questions

- U1: cost units (see `gnus_estimate`).
- U2: can a browser user with MetaMask and no GeniusWallet submit jobs? (D) Not via this contract:
  the dashboard needs a GeniusWallet provider to submit. Browser-only users get read-only views.
- U3: phone pays, desktop earns (two devices). Out of v1; needs an account-link step signed on both
  sides.
- U4: who mints a given burn on the SuperGenius side (which account a payment credits). Today the
  wallet's bridge mints to the node's selected SDK account; the contract assumes that.
- U5: recovering `bridgedNotProcessed`. Repeating `gnus_submitJob` with the same idempotency key returns
  the first result and never re-runs Process. Whether Process can be re-run for an existing burn is
  unknown (wallet todo 2026-07-29 "can requestGeniusSDKProcess be recalled after a successful bridge").
  If it can, v1 adds `gnus_retryProcess({ burnTxHash })` with its own confirm; until then the dashboard
  shows the burn hash and points the user to the wallet.
